# Listening to Many Channels Implementation Plan (plan 22)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One action starts a node-wide mix of every demodulator (or those of the sources named) and plays it on the page; while a channel is heard its row and outline light up and the mix's row names it, and a channel can be muted in the mix without touching its demodulator.

**Architecture:** A leaseless job of the new `JobKind::Mix` (source `node`, tuning 0/0) runs one node of the new `mix` stage in `zeta-dsp`. The stage has no graph inputs: every 500 ms it asks a new `StageContext::mix_inputs` hook for the running jobs' audio outputs, and on a 20 ms tick it drains each receiver into a per-input queue, sums what each queue gives, soft-limits and publishes. Its event output says who is active. The page holds one event socket on the mix in a new `mix.js`, and muting is a `graph_put` of the stage's `muted` param.

**Tech Stack:** Rust 2024 (tokio with paused time, serde, schemars, clap), `FileSource` fixtures (`zeta-source-file`, feature `test-fixtures`), `zeta_dsp::fixtures::nbfm_modulate`, the `Radio` fixture copied from `crates/zeta-core/tests/plan_start.rs`, Playwright (`crates/zeta-ui/tests/e2e/ui.py`), vanilla ES modules in `crates/zeta-ui/web`.

**Spec:** `docs/superpowers/specs/2026-11-01-audio-mix-design.md` (read it first; section numbers below refer to it). Where this plan departs from it, "Rulings on the spec" at the end says why.

## Review Focus

1. **The page's ops feed must not read the mix's stream.** `agent.js:299` finds the ops stream as the first with `provenance.source === "node"`, and a mix's streams now match that too. With a mix running, the transcript must keep showing ops. Pinned in Task 5 (`scenario_listen_to_all_starts_one_mix_and_plays`, its ops-line assertion).
2. **Listen to all pressed twice at once makes one mix.** Two concurrent `mix_start`s must answer one id, or a double click leaves a second mix running for good. Pinned in Task 2 (`concurrent_mix_starts_answer_one_job`).
3. **A channel retuned or restarted mid-transmission does not flicker.** Its input keeps its place across the stream swap and across the one poll where the job shows no outputs. Pinned in Task 1 (`a_restarted_input_keeps_its_place_and_does_not_flicker`).
4. **A node restart with a transcript on the mix.** The order must be demodulators, mix, then what is attached to the mix, or the attached job fails `input job <id> not running`. Pinned in Task 2 (`a_restart_resumes_the_mix_after_its_jobs_and_before_its_transcribe`).
5. **Stopping the playing mix from its row.** Playback ends, the Listen button returns, the event socket closes and no row stays lit. Pinned in Task 5 (`scenario_stopping_the_mix_ends_playback_and_lights`).

  - `pub fn soft_limit(x: f32) -> f32`: `x` inside ±0.8, else `sign(x) * (0.8 + 0.2 * tanh((|x| - 0.8) / 0.2))`.
- `run` with no `ctx.mix_inputs` is `StageError::Failed("mix needs a node's job list")`. It ends only on cancel: nothing about its inputs ends it.

The loop is one `tokio::time::interval(20 ms)` with `MissedTickBehavior::Burst`, no tasks and no `select!` over receivers (the cancel is the only other arm). Each tick, in this order:

1. Every 25th tick (the first included), poll the hook. Keep the inputs on `params.sources` (`None`: all). A new job is subscribed. A job whose `stream` differs drains its old receiver and swaps to the new one, keeping queue and `active`. A failed `subscribe` (the old run's stream already gone) keeps the input with the receiver it has and retries next poll. A job missing from **two consecutive** polls is dropped (one poll can catch a relaunch between `record_running` and `e.outputs`: `launch.rs:231, 339-343`). `center_hz` is refreshed and the mute re-evaluated (`source` equal, `abs_diff <= CHANNEL_MATCH_HZ`); becoming muted clears the queue.
2. Drain each receiver with `try_recv` until `Empty`. `Lagged(n)` goes to `crate::note_lag("mix", n)`; `Closed` leaves the receiver empty until the poll swaps it. A frame not at 48 000 Hz mono marks the input skipped (one line in `skipped`: `<job> <source> <center_hz> Hz: <rate> Hz, <channels> channels`), and its frames are ignored while it stays on that stream. A muted input's samples are discarded. Otherwise the samples are appended, `last_heard` (a `tokio::time::Instant`) is set and `last` updated. Then the cap: samples over 200 ms lose their oldest, added to `dropped_ms`.
3. Feeding: an idle input with samples becomes feeding at `now + PREBUFFER_MS`. A feeding input past that time gives up to 960 samples. Its queue running dry makes it idle again; samples arriving within 100 ms of drying count one `underruns`.
4. Sum to the longest contribution, `soft_limit` each sample, publish one audio frame if any input gave samples. The frame's provenance is the output stream's (found as `stream_in.rs:113-122` does), with the span below.
5. An input is active while `now - last_heard < 500 ms`. A changed set (sorted by `center_hz`) publishes the event. Note `{"mix": {...}}` at the start of `run` (the empty state, since a record's context survives a restart), on a changed set, and on a poll when `inputs`, `muted`, `dropped_ms`, `skipped`, `underruns` or `last` changed. Every note writes the job's file (`node/mod.rs:544`), so never note per tick.

Span: the first frame after a tick with no frame starts at the wall clock (`SystemTime`); each later frame starts at the previous frame's end. If that differs from the wall clock by more than 100 ms, re-anchor. The end is the start plus `n / 48 000` s.

## Rulings on the spec

1. **Frame spans (§4.2 "the tick's wall-clock span").** Wall-clock tick spans jitter by milliseconds, so a continuous tone would never pass §5's "no gaps in its frames' spans", and a `transcribe` on the mix keys on spans. Ruled: a burst anchors at the wall clock and then runs by sample count, re-anchoring after a silent tick or 100 ms of disagreement.
2. **Prebuffer (§4.2).** 40 ms stays the start; Task 3 sets the value from 40, 60 or 80 ms by measurement, ceiling 80 ms because of the 200 ms cap at 100 ms blocks. Failing at 80 ms goes back to the operator.
3. **`FileSource` pacing (not in the spec).** Summed sleeps make a recording run slow against the mix's clock and fail §5 whatever the prebuffer. Fixed in Task 3, a change outside the code the spec names.
4. **The ops feed (not in the spec).** The `node` placeholder collides with `agent.js:299`'s lookup of the ops stream. Fixed by also requiring no `provenance.job`; the guide says so.
5. **`job_retune` "by kind" (§4.1).** A mute's `graph_put` sets `operator_graph`, and that test runs before the kind's, so the refusal would change after a first mute. The kind is tested first.
6. **`job_context.mix` "starts empty" (§4.2).** A record's context survives a `graph_put` and a restart, so the stage notes an empty state when it starts.
7. **An added field.** `job_context.mix.underruns` is beyond §4.2's list: "silence that lies" applies to an input starved mid-burst too, and the field check needs it.
8. **"Same set" (§4.1).** `null` matches only `null`; a list matches as a set, so a list naming every source is another mix. `sources: []` is refused rather than making a mix of nothing.
9. **An input's identity across a recovery (§4.2).** A retune or `graph_put` keeps the input through one poll's absence, the only window a live relaunch has. A fault's recovery takes seconds and the job is `failed` meanwhile, so its input is dropped and joins again; by then its queue is empty and its hangover over, so the only visible difference is `inputs`.
