ZetaSDR mudmap

The short version of the architecture map: what plugs into a node, over which wire, set up by which flag, and whether it has to sit on the node's host. As of 2026-11-04 (plan26-zeta). Generated by docs/architecture/mudmap.py.

Local, remote or either

  • Local: it has to be on the node's host. That means anything the node opens directly: a USB radio (through its worker child), a Unix socket, a child process, a file.
  • Remote: it is on another host by nature (KiwiSDR, a VRT sender, another node, SondeHub). The node is the client.
  • Either: it is reached by URL, so localhost and another host work the same way. All the clients, the LLM and the ACMA register are in this group.

Two rules cover most cases. A USB radio on another machine is attached by running a node on that machine and adding it here with --source-node. Speech that needs a GPU elsewhere goes through --stt-node to the node that has the GPU. Every flag that wires something in (--source-*, --plugin, --knowledge-acma, --stt-*, --llm-*, --modes-dir, --themes-dir) belongs to the serving node and must be repeated on every start. A client using --node passes none of them.

There are two MCP directions. zeta-mcp makes the node an MCP server for Claude Code and similar clients. With --knowledge-acma, the node is an MCP client of the register. There are also two agent paths. zeta ask runs the tool loop wherever it is started. POST /ask (the page's agent pane) runs it inside the node, so the node's own --llm-url must reach the LLM.

How a model drives the node: who runs the loop, and the doors in

A configured LLM never touches the node. It answers with tool calls, and zeta's own loop executes each one behind a gate that code enforces. An external coding agent such as Claude Code is a client with the secret. It runs its own loop, calls the node over HTTP the way any script does, and is held only by the guide's rules and the operator's approval of its tool calls.
