# ZetaSDR agent guide

ZetaSDR is an agentic SDR runtime. You drive it through a small typed operation set. The CLI form and the JSON form of every operation are equivalent: `zeta <group> <verb> --flag value` and `{"op": "<name>", ...}` do the same thing.

## Rules

- One unit per field: frequencies and bandwidths are integers in hertz in fields ending `_hz`, rates are in baud in fields ending `_baud`, times are integer nanoseconds since the UNIX epoch in fields ending `_ns`, durations are integer milliseconds in fields ending `_ms`, gains are decibels in fields ending `_db`.
- Every field is required and unknown fields are rejected.
- Call operations, do not explain.
- Errors carry `error`, the offending `field`, the acceptable range and, when the value looks like dropped zeros, `suggested`. Use it. A `why` of `insufficient bandwidth: ...` names the source's measured ceiling, not a decoder gap: narrow the request or move to a wider radio rather than wait for a mode, and report it to the operator, who can pin or re-measure the cap. Never delete or edit the node's state files.
- Unknown signals are reported as unknown, never guessed.
- Ids are never invented: `source` values come from `source list`, `job` values from `job list`.
- Radios: when the request names a radio (a source id as a whole word), use it. Otherwise use the default radio the request's context names (`## This request` in the system prompt); with none, follow the `## This request` paragraph (under `focus` with no radio in focus, list the free radios and ask; under `focus-fallback`, the first free); without that section (an MCP client), the first free id `source_free` gives. The policy decides when the default radio cannot take the band (it does not cover it, a job or a pin holds it, it is faulted): under `focus`, the default, use only the default radio; start nothing, say why, name the free radios and ask which to use; never start on another unnamed radio (the gate answers `policy`). Under `focus-fallback`, use the first free radio in the preference order and say which and why. Under `free-first`, use the first free radio. Under `ask`, ask before starting. Never stop or replace a job to free a radio.
- Jobs belong to the operator: never `job_stop` a job or put one in `replace` unless the request names it, the run allows it or, for `job_stop`, you started it in this run. A `conflict` is reported with its holders; the operator decides.
- For a kind on every channel of a plan use `plan_start`, never one `job_start` per channel.
- Plan ids come from `channel_plans`: read it before naming a plan. A band with no plan takes one `job_start` per measured station; never invent a plan.
- To stop every job, or every job of a source, kind or plan, use `jobs_stop`, never one `job_stop` per job.
- For a named set use `set_start`, never its members by hand; set ids come from `set_list`.

## Running the node

Every command takes these global flags:

- `--state-dir PATH`: where jobs and captures persist (default `$XDG_STATE_HOME/zetasdr`, else `~/.local/state/zetasdr`). Pass the same directory on every invocation.
- `--source-file ID=PATH.sigmf-meta[,tune_min_hz=N,tune_max_hz=M]`: attach a SigMF recording as source `ID`. With the range it plays as a radio tunable over `N`-`M` Hz (its `tune_min_hz`/`tune_max_hz` in `source list`): a band inside the range moves the capture's centre there, the samples staying the recording's (a test and demo aid); without it only the recording's own band is accepted.
- `--source-kiwi ID=HOST:PORT[/PASSWORD]`: attach a KiwiSDR receiver (0-30 MHz, at most 12 kHz wide) as source `ID`; the port is required and the password is never printed. Without `/PASSWORD` the password comes from `ZETA_KIWI_PASSWORD_<ID>` (`ID` upper-cased, other characters as `_`), which keeps it out of `ps`; the flag wins when both are given.
- `--source-position ID=LAT,LON[,ALT_M]`: where source `ID` is (degrees, metres; repeatable); a source that reports its own position (a KiwiSDR with GPS) overrides it. The station (`station_set`) stays the node's.
- `--source-node ID=SOURCE@URL[,max_bandwidth_hz=N]`: use source `SOURCE` of another ZetaSDR node, `URL` being its `http://HOST:PORT` (a `zeta serve --listen` node), as source `ID`. The node's secret comes from `ZETA_NODE_SECRET_<ID>` (`ID` mapped as for Kiwi passwords) and is never printed; without it the command is a usage error (exit 1). A remote source ships narrowband by default: `bandwidth_hz` is capped at 250 000 Hz (or the remote source's own maximum when smaller) unless `max_bandwidth_hz=N` (1-20 000 000) widens it explicitly. Each tune holds a `passthrough` job on the other node, so its `source list` and `job list` show who is using the source; the job is stopped when the tuning changes or this process exits normally (a killed process leaves it running; stop it there with `job stop`).
- `--source-vrt ID=udp://ADDR:PORT`: receive VITA 49.2 (VRT) packets, one per UDP datagram, on `ADDR:PORT` as source `ID`; `ADDR` must be a LAN address (`0.0.0.0` listens on every interface). The sender sets the frequency and rate: a job's band must lie inside the sender's last context packet (`source list` shows it as `current`; a job started before any context packet waits up to 1.5 s for one), otherwise the job fails with `unsupported` saying where the sender is; retune the sender, not the job. Packets that do not decode are skipped.
- `--source-soapy ID=ARGS`: attach a SoapySDR device as source `ID`, `ARGS` being SoapySDR device arguments such as `driver=hackrf,serial=...`. The device runs in a `zeta soapy-worker` child the node spawns and respawns: a driver crash or an unplugged device faults the source (`source list` shows `fault`, jobs on it fail with `source <id>: <fault>`) and never ends the node. The node then respawns the worker and waits for the device; when it is back it restores the pin and the gain and relaunches every job that failed with that fault under its own id, the `watch` and its decoders and an attached `transcribe` included, logging `zeta: source <id>: recovered: ...`. `worker` in `source list` shows the child's pid, how many times it was respawned and `transport` (`path` `shm`, a shared-memory ring the node creates per spawn, or `pipe`; `format`, `cf32` or `sc16`: a device whose samples are 16-bit puts them on the ring unconverted, half the bytes and twice the time in the same ring, and the node converts them; a worker of another protocol or ring version is refused with a fault naming both) with `transport_dropped`, `attachment` (`usb:<bus>-<path>@<speed>`, the link's negotiated speed in Mb/s, `null` where it cannot be told) and `link_measure` (the figures of the latest hello and the speed they were measured at). At open the worker probes the rates the device offers and reports the first clean one as `max_bandwidth_hz: {measured: N}`: a request wider than it is refused `out_of_range` with `why: insufficient bandwidth: ...`. A measured cap is cached in `sources/<id>.json` and passed to every respawn; a probe with no clean rate measures nothing and keeps the driver's cap. A `max_rate_hz=N` item in `ARGS` (zeta's own, like `gain=`) asserts a cap and skips the probe; it is read from `ARGS` at every start, never cached. It is the remedy when the journal shows `rate cap not measured: no rung clean` or, at every open, `rate probe: device lost at <rate>`. A device whose link carries more than one sample depth (a B2xx: `sc16`, `sc12` and the lossy `sc8`; `capabilities.depths`, each `{bits, lossless, max_bandwidth_hz}`) has each probed at open, and the top-level `max_bandwidth_hz` is the figure for the depth in force (`depth` in `source list`): the narrowest lossless one that measures as wide as the widest (a lossless depth carries all the converter gives, so a narrower one that streams as wide is the same fidelity in fewer bytes; one that measured narrower or was never measured clean does not win, so the source's bandwidth never shrinks under a resumed job) unless `bits=N` in `ARGS` asks for another (the only way to a lossy one; a `scan` takes a lossy depth for its run with `bits`). Three more items in `ARGS` are zeta's own: `settle_ms=N` (0-10000) is how long a tune takes to settle after the device returns from it, in place of the radio's (1 ms on the B2xx family, 10 ms for a radio zeta has not measured), `usable=F` (0.5-1) the part of a capture the front end passes flat, in place of 0.9, and `bits=N`. A fourth, `antenna=NAME`, picks the receive port by the device's own name for it (a LimeSDR's `LNAW`, a B2xx's `RX2`), set when the device opens and logged as `zeta: antenna for <id>: <NAME>`; a name the device does not list refuses to attach the source, naming the ones it has, and without the item the driver chooses the port, which is not always the one the antenna is on (a radio that hears nothing on a band another radio hears is the sign). While a tune blocks the reader the device overflows, and that is counted as `stats.tune_gaps`, not as `overflows`: `overflows` stays the figure for loss while streaming. A start that has no cached figures measures first, and says so: the journal reads `measuring what this radio's link can sustain (up to about <N> s; the host will be busy; max_rate_hz= skips it)` and, when the worker says hello, `measured in <N> s` (a B210's three depths take about 70-110 s, within the 150 s the node waits for the hello). A node's very first start shows only those two lines, since it serves after its sources' first hello; a respawn (a replug, a link-speed change, `source_measure`) also shows `worker.starting` (`what`, `detail`, `step`, `of`, `eta_ms`) in `source list`, a notice on the source's tab and the feed's `measuring` and `measured` events, and its line opens the parentheses with the reason (`link speed changed (<old> to <new>)` or `as asked`). `max_rate_hz=N` asserts the cap and skips the probe. The measured figures are cached in `sources/<id>.json` with the link's speed (`measured_at_speed`): a source measures again by itself only when its negotiated speed differs from the one its figures were measured at (a USB 3 radio on a USB 2 port, or the reverse); another port at the same speed keeps the cache. To measure again otherwise (the system stutters after devices were added around the radio, a new cable, a faster host), `source_measure`; an agent reports `insufficient bandwidth` to the operator, asks before stopping a job to measure, and never deletes or edits state files. A device absent at startup is attached faulted when the host has seen it before, else the flag is refused (exit 1). `zeta soapy-worker --id ID --args ARGS` is what the node spawns; it is not run by hand. The worker inherits the node's environment (the driver reads `UHD_IMAGES_DIR`, `SOAPY_SDR_PLUGIN_PATH`) minus the secrets: every `ZETA_*` variable whose name contains `SECRET`, `PASSWORD` or `KEY` (`ZETA_SECRET`, `ZETA_NODE_SECRET_<ID>`, `ZETA_KIWI_PASSWORD_<ID>`, `ZETA_STT_NODE_SECRET`, `ZETA_LLM_KEY` among them). A `gain=DB` item in `ARGS` is zeta's own: automatic gain is turned off and the overall receive gain set to `DB` dB when the device opens (logged with the device's range as `zeta: gain for <id>: ...`), and a `DB` outside that range refuses to attach the source (exit 1); without it the driver's default gain is used, which on a USRP is its minimum. A gain set live with `source_set_gain` is persisted and wins over `gain=` on the next start. `ppm=N` corrects the device's frequency error: the hardware is tuned `N` parts per million higher than every frequency zeta reports, so a device that reads high by `N` ppm (a carrier on 146.975 MHz seen at 146.9754) reads true. `zeta soapy find [--filter ARGS]` lists the devices attached to this machine as JSON. Only in a zeta built with `RUSTFLAGS="--cfg soapy"` (needs libsoapysdr-dev); otherwise both exit 1 saying so.
- `--soapy-in-process`: open `--source-soapy` devices inside the node instead of a worker child; for diagnosis only, as a driver crash then ends the node.
- `--ring-budget-mb N` (env `ZETA_RING_BUDGET_MB`): memory budget for one source's IQ history (default a quarter of RAM, at most 4 GiB). The ring keeps 10 s at narrow rates and shrinks to as little as 1 s at wide ones (a ring holds 8 bytes per sample, so 16 Msps gets 8 s of a 1 GiB budget); `iq read` and `classify` spans older than that fail `too_old`. A gap in the capture (the source lost samples) does not clear the history: it is kept in segments, and a span that crosses a gap fails `gap` with its `gap_start_ns` and `gap_end_ns` (the last sample before and the first after), so read either side of it. `source_list`'s `ring` gives `seconds` (the size), `held_s` (the seconds of samples held, at most `seconds`, less while the ring fills), `run_s` (the seconds in the newest contiguous run, after the last gap: the longest span ending now that an `iq read` can serve) and `gaps` (how many are in the history). The size chosen is logged to stderr as `zeta: ring for <source>: <s> s at <rate> Hz (<MB> MB)`.
- `--bursts-keep-mb N` (env `ZETA_BURSTS_KEEP_MB`) and `--bursts-keep-days N` (env `ZETA_BURSTS_KEEP_DAYS`): how much the burst capture store keeps (defaults 256 MB and 7 days; zero is a usage error). Expiry removes the oldest unpinned captures until the unpinned rest fit the megabytes, then every unpinned capture written more than the days ago; it runs when `zeta serve` opens (a one-shot expires at open only when given one of these flags while no serve owns the state directory, so a plain one-shot never drops what serve's policy keeps) and after each write, and a capture just written is spared by its own write. A pinned capture is never expired. `--bursts-trial-mb N` (env `ZETA_BURSTS_TRIAL_MB`, default 64 MB) is the separate budget of the trial slices a `choose` job records: they expire oldest first against it alone, and neither kind ever expires the other. An unreadable `bursts/index.json` is moved aside as `index.json.broken-<ulid>` and the index rebuilt from the `.sigmf-meta` files (pins are lost), logged as `zeta: bursts: index unreadable (<e>); moved aside`. All three belong to the serving node: with `--node` they are a usage error (exit 1).
- `--knowledge-acma URL[,reach_km=N][,propagation=PATH]` (env `ZETA_KNOWLEDGE_ACMA`): attach the ACMA licence register service (an MCP server over HTTP): the service's `http://HOST:PORT` (a trailing `/mcp` is accepted) as the `acma` knowledge provider of `knowledge_lookup` and `classify`. `reach_km=N` (a positive number) replaces the search bound's kilometres. `propagation=PATH` names a JSON file holding any of the propagation estimate's assumptions (`k_factor`, `beyond_horizon_db_per_km`, `off_beam_default_db`, `ground_wave_km`, `skywave_min_hz`, `skywave_max_hz`, `in_range_floor_dbm`, `search_margin`, `assumed_site_height_m`; the rest keep their defaults), read at start: a file that cannot be read or parsed, names another field, or breaks a rule (every number finite, `k_factor` above 0, `ground_wave_km` above 0, `beyond_horizon_db_per_km`, `off_beam_default_db` and `assumed_site_height_m` at least 0, `search_margin` at least 1, `skywave_min_hz` not above `skywave_max_hz`) is a usage error naming the file and the field. Every register answer echoes the assumptions it used in `assumptions`. The options come in any order, each once. The service is probed once at startup (one-shot commands pay at most 5 s when the host is unreachable); an unreachable one is logged as `zeta: knowledge acma: <url> unreachable: <e>` and the provider still attaches, giving no allocations until it answers. Needs `station set` for distances. It belongs to the serving node: with `--node` it is a usage error (exit 1).
- `--run-dir PATH` (env `ZETA_RUN_DIR`): the directory under which each external program run (a program row fed through a fifo) makes its own `external-<random>` subdirectory, mode 0700, removed when the run ends (default `<state-dir>/run`; a packaged install sets it in its unit file, for example `/opt/<package>/var/run` or the system temp directory). It is made with mode 0700 when missing; `serve` exits at startup naming it when it is not a directory or cannot be written.
- `--registers-dir DIR` (env `ZETA_REGISTERS_DIR`): the operator's register queries, one `<provider>/<id>.json` file each, read after the built-in ones (no default; a missing directory is no error). A query with a built-in query's provider and `id` replaces it. A query is a row like those in `registers/acma/`: `id`, `provider`, `name`, `call` (only `execute_sql`), `sql` (a `SELECT` or `WITH` with `{name}` placeholders and no `;`), `params` (each a `name` and a `kind`, `number` or `id`: only numbers and register ids are ever substituted), `limit` and the result `columns` it must return. A directory with a file that does not load is reported at startup as `zeta: registers: <file>: <field>: <error>; using the built-in register queries`. `zeta registers check [PROVIDER] [--center-hz HZ] [--bandwidth-hz HZ]` (local only; no radio needed) runs every query against the `--knowledge-acma` register with sample values (a signal at 400.5 MHz, 1 MHz wide, unless the flags give another; the station's position when one is set in the state directory; for a query that takes a register id, the ids of the first `candidates` row) and prints `<provider>/<id>: ok <rows> rows <ms> ms`, `<provider>/<id>: fail: <reason>` or `<provider>/<id>: skipped: <reason>` for each, then `<provider>: skipped <n> of <total> queries (<q> quiet band, <d> not runnable)` when any was skipped (a quiet band, with no `candidates` row to take a register id from, is no failure; a skip the check cannot run, such as a `candidates` row without the id column, fails it), then `<provider>: answer <ms> ms of <deadline> ms` for one whole answer. A register that does not answer is `<provider>: unreachable: <reason>` alone, and with no register it prints `no register configured`. It exits 0 only when nothing failed.
- `--plugin KIND=PATH`: register the program at absolute `PATH` as stage kind `KIND` (lowercase, not a built-in kind). It is probed at startup; a failed probe exits 1 naming the kind and the reason (a `hello` of a protocol other than 1 or 2 is refused). A plugin runs with a cleared environment: only `PATH`, `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM` and `PYTHONPATH` pass through, and each `ZETA_PLUGIN_ENV_<NAME>` variable reaches it as `<NAME>`; nothing else (no `ZETA_SECRET`) does.
- `--modes-dir PATH`: the operator's decoder mode rows, one `*.json` file each, read after the built-in ones (default `$XDG_CONFIG_HOME/zetasdr/modes`, else `~/.config/zetasdr/modes`; a missing directory is no error). A row with a built-in mode's `id` replaces it. A row that does not parse or validate never stops the node: it is listed `broken` by `modes list` and reported at startup as `zeta: mode <id> (<file>): <field>: <error>`, and a broken file that meant to replace a built-in row leaves that row in force.
- `--handlers-dir PATH`: the operator's handler files, one `*.json` file each, read after the built-in ones (default `$XDG_CONFIG_HOME/zetasdr/handlers`, else `~/.config/zetasdr/handlers`; a missing directory is no error); each adds an external program as a handler of the modes it lists (`handlers/README.md`). A file with a built-in file's `id` replaces it. A file, or a mode entry, that does not load never stops the node (a bad entry breaks only itself): it is reported at startup as `zeta: handler <id> (<file>): <reason>`, and the file's program is looked up at startup and on a reload that reads a new or edited file, never run (`zeta: handlers: <program>: found <path> (handler <id>)`, or `zeta: handlers: <program>: missing (<hint>; <url>) — modes: <ids>`, the handler then unavailable).
- `--sets-dir PATH`: the operator's named sets, one `*.json` file each, read after the built-in ones (`airband`, `airband_vhf`, `airband_vhf_and_sos`, `ais`, `pagers_au`; default `$XDG_CONFIG_HOME/zetasdr/sets`, else `~/.config/zetasdr/sets`; a missing directory is no error). A set with a built-in set's `id` replaces it. A serving node reads the directory again whenever its files have changed: a file added, edited or removed is in force at the next `set_list`, `set_start` or `set_stop`, with no restart, and a set already running keeps the jobs it started (`set_stop` stops them whatever its file now says; the next `set_start` runs the file as it stands). A set names roles (`radios`), never sources, and never carries `source` or `replace` on a member. A set that does not parse or validate never stops the node: it is listed `broken` by `zeta sets` (`set_list`) and reported on stderr, at startup and when an edit breaks it, as `zeta: set <id> (<file>): <field>: <error>`, and a broken file that meant to replace a built-in set leaves that set in force.
- `--themes-dir PATH`: the operator's themes, one folder each (default `$XDG_CONFIG_HOME/zetasdr/themes`, else `~/.config/zetasdr/themes`; a missing directory is no error), read after the built-in ones. A theme with a built-in theme's `id` replaces it. A folder that does not validate never stops the node: it is listed `broken` by `themes list` and reported at startup as `zeta: theme <id> (<path>): <field>: <error>`, and a broken folder that meant to replace a built-in theme leaves that theme in force.

Sources and plugins are not persisted: repeat the flags, with the same ids and kinds, on every invocation, `serve` included. A source id may be used once across all the source flags. `source list` shows each source's capability record: `remote` is true for a KiwiSDR, a `--source-node` and a `--source-vrt` source, `push` false for SoapySDR devices, and `fault` names a source that has failed (a full Kiwi, an unplugged device); a job on a faulted source fails with that reason.

There are two ways to run:

- One-shot, `zeta <group> <verb> ...`: opens the node, applies one operation, prints the JSON result and exits (0 on success, 2 with a JSON error). It never resumes jobs: a job started one-shot is persisted as `running` and runs once `zeta serve` starts. `job start --then-tail MAX_FRAMES,TIMEOUT_MS` keeps that one-shot node up after the start, tails the job's audio output when it has one (a demodulator), else its decoder's event stream (the event output of its downstream-most decoder node, never a demod's `squelch` events), then stops the job and prints `[job_result, frames_result, {"stopped": true}]`; add `--keep` to leave it running (`{"stopped": false}`). If the job is not running (e.g. failed) it prints `[job_result, job_record]`, the record's `state` carrying `status` and `reason`, and exits 2; `stream tail` on its own only sees streams of jobs running in the same process, and `job attach` needs its input job running in the same node, so attach against `zeta serve` (`--node`). A one-shot `iq read` or `classify` reads the ring that the command itself fills from the source, waiting up to 5 s for it to cover the span. One-shot commands, read-only ones included, restore the pins and the gain of the sources they attach (so even a one-shot `source list` tunes a pinned radio). One-shot commands, like `zeta serve`, start and probe every `--plugin` program at startup, so with plugins configured even a one-shot `source list` costs one process start per plugin.
- `zeta serve`: resumes persisted jobs and keeps them running until Ctrl-C.
- Against a running node, `zeta --node URL --secret SECRET <group> <verb> ...` (or the `ZETA_NODE` and `ZETA_SECRET` variables): the operation is sent to that node over HTTP and applied there, so jobs started this way keep running; `--state-dir`, the `--source-*` flags, `--plugin`, `--modes-dir`, `--handlers-dir`, `--themes-dir`, `--sets-dir`, `--registers-dir`, `--run-dir`, `--knowledge-acma` and `--bursts-keep-*`, `--bursts-trial-mb` belong to the serving node and are rejected (a usage error, exit 1); `--stt-socket`, `--stt-node`, `--stt-url`, `--stt-url-model`, `--stt-url-languages` and `--soapy-in-process` belong to it too but are ignored, and so are `ZETA_KNOWLEDGE_ACMA`, `ZETA_REGISTERS_DIR`, `ZETA_RUN_DIR`, `ZETA_BURSTS_KEEP_MB`, `ZETA_BURSTS_KEEP_DAYS`, `ZETA_BURSTS_TRIAL_MB` and `ZETA_RING_BUDGET_MB` from the environment. `zeta soapy find` always runs locally; `zeta modes check` and `zeta registers check` are refused (exit 1); `zeta handlers list` lists the serving node's handlers (from its `modes_list`). `--then-tail` is not supported with `--node` yet (a usage error, exit 1): start the job, then `stream list` and `stream tail` against the node. Start that node with `zeta serve --listen PORT` (binds 127.0.0.1) or `--listen ADDR:PORT` (a LAN address) and a secret. `--max-streams N` (env `ZETA_MAX_STREAMS`, default 64) bounds the stream websockets it holds open at once; past that a stream is refused `too many stream connections`. `zeta-mcp --node URL` offers the same operations as MCP tools, and `zeta ask "REQUEST"` lets a local model call them.
- `zeta serve --listen PORT --llm-url URL --llm-model NAME` (the other `--llm-*` flags of `zeta ask` apply too) enables `POST /ask` with `{"request": "TEXT", "max_turns": 8, "allow": {"stop_jobs": false, "replace": false, "delete_captures": false, "accept_signatures": false}}` (`max_turns` 1-32, default 8; `allow` optional, all false by default: without them the agent's `job_stop` and non-empty `replace` calls, its `capture_delete` and `packets_delete` and its `signature_accept`, `signature_reject`, `signature_retract` and `signature_delete` are refused as `not_allowed`; `page_tools` optional, false by default: the web page sends `true`, which adds the page-only `view_set` tool, answered by the agent itself and applied by the page, never by the node): the node runs the agent against itself, so every operation it applies appears on the `ops` stream, and answers the transcript (`request`, `answer`, `calls`, `turns`) as `zeta ask` prints it, plus `allow` as the run had it and `turn_log`, one entry per model completion with its reasoning, content and call count. One run at a time (409 while one is in progress); 503 when serve has no `--llm-url`; a failed run is 502 with the error and the transcript so far; 504 after 300 s.
- `zeta serve --listen PORT --stt-socket PATH` (env `ZETA_STT_SOCKET`; default `$XDG_RUNTIME_DIR/voiced.sock` when that file exists) enables `POST /stt?lang=CODE` (`lang` defaults to `en`): the body is a 16 kHz mono `audio/wav` (at most 4 MiB), the node hands it to the speech daemon at that Unix socket and answers `{"text": "TRANSCRIPT"}`. The daemon is `local-voice` or any daemon speaking its protocol: one line per connection, `file:<absolute wav path>` answered `ok:<text>` or `error:<message>`, and `languages` answered `ok:en,de,...` (a daemon answering `error:` there is taken to know English only). Instead of a daemon, `--stt-node URL` (env `ZETA_STT_NODE`, secret in `ZETA_STT_NODE_SECRET`, never printed) forwards each request to that node's `POST /stt`, and `--stt-url URL` (env `ZETA_STT_URL`; bearer, if any, in `ZETA_STT_URL_KEY`, never printed; `--stt-url-model NAME`, `--stt-url-languages en,de`) posts each utterance as a multipart `file` to a Whisper server's full endpoint URL (an OpenAI-compatible `/v1/audio/transcriptions` or whisper.cpp's `/inference`), so the audio leaves the host; the three flags are exclusive, for every command (exit 1). A forwarded request carries `X-Zeta-Stt-Hop: 1`, and a node that would forward it again answers 508 (`stt forwarding loop`). `GET /stt/languages` answers `{"backend": NAME, "languages": [CODES]}` (503 without a backend). 415 when the body is not WAV, 413 when too large, 422 `{"error": "unsupported", "language", "supported"}` for a language the backend lacks, 502 when the daemon reports an error, 503 when serve has no backend or cannot reach it, 503 `{"error": "busy", "message", "wait_ms"}` when every one of the daemon's 4 slots stayed taken for 30 s (a node forwarding with `--stt-node` reports that as a `busy` drop, not an error), 504 when the daemon does not answer within 30 s of its turn.

`zeta stream save --stream ID --path FILE [--timeout-ms N] --node URL` writes the next video frame to arrive on a stream (a `video_decode` job's `video` stream) as a full-width PNG. It needs a running node; an audio or IQ stream is refused with a pointer to `zeta iq read`.

A video stream on the stream websocket is always PNG in binary mode: `GET /stream/ID?format=binary&video=smooth|sharp|thumb`. `smooth` (the default) is 360 px wide with every line of the field (360 x 288 for PAL: a field is already anamorphic, so its height is not scaled), one frame per field; `sharp` is full width at most 5 a second; `thumb` is 120 px wide with a third of the lines (120 x 96) at most 2 a second. Only the newest frame is sent, and `lagged.missed` counts the frames skipped.

While `zeta serve` runs it owns the state directory (it holds `serve.lock` there). Mutating one-shot commands (`job start`, `job attach`, `job retune`, `job stop`, `jobs stop`, `plan start`, `set start`, `set stop`, `mix start`, `bits start`, `graph put`, `graph start`, `station set`, `station clear`, `handlers policy set`, `capture delete`, `packets delete`, `signature propose`, `signature accept`, `signature reject`, `source ensure`, `source pin`, `source unpin`, `source measure`, `source gain`, and `origin lookup` with `--job`) are then refused with an `other` error naming the server's pid; read-only commands still work. Use `--node` to change a node that `zeta serve` owns.

Every operation the node applies is appended to `ops.log` in the state directory (rotated at 8 MiB) with its caller's transport (read-only operations are logged without their result); `zeta ops tail --lines N` prints the last N (local only). Every `transcript` event of a `transcribe` job is appended to `transcripts.log` in the state directory (rotated at 8 MiB) with the job, its input, the source and the channel's centre; `zeta transcripts tail --lines N [--job ID]` prints the last N (local only). Every event of every job on a source (what the source's feed carries: every decoded frame, detection, transcript, a `watch`'s and an `identify`'s own events, and an `origin_lookup`'s `origin` answer, whether or not a page or a `stream tail` is open; an `fft`'s rows stay out) is appended to `events.log` in the state directory (rotated at 32 MiB) as `t_ns`, `source`, `job`, `channel`, `center_hz`, `bandwidth_hz`, `start_ns`, `end_ns` and the event itself under `event`; `zeta events tail --lines N [--job ID] [--source ID] [--protocol NAME]` prints the last N (local only), so "what did ACARS hear overnight" is `zeta events tail --protocol acars --lines 500` after the fact, and the sites lit for a job are `zeta events tail --protocol origin --job ID`.

## Operations

### source_list

List the sources: id, capabilities, `current` band, `holders` (the rigid lease holders' job ids), `elastic` (the jobs following the capture, see `job_start`), `pin` (the band `source_pin` holds the source at, `null` for none), `fault`, the source's unrecoverable failure (`null` when healthy; a healed fault stays until recovery has seen the jobs end, normally up to one poll after the worker's hello, and a `job_start` in that hold is accepted, its job possibly failing and being relaunched under its id), `bank`, the channel bank shared by the capture's channels (`bin_hz`, `consumers`, `dropped`, the input blocks it dropped because it could not keep up; `null` for none), `gain`, the overall receive gain (`db`, `null` while automatic; `min_db`, `max_db`, `automatic`, `automatic_available`; `null` for a source without adjustable gain), and `stats`, the stream's counters since it opened (`measured_rate_hz`, the rate delivered over the last 10 s, `null` before any; `overflows`, `timeouts`, `restarts`, streams reopened because their samples ran ahead of the clock; `tune_gaps`, overflows the reader's own blocked tune caused, which are not in `overflows`; `null` for a source that keeps none), and `depth`, the sample depth in force on a link that carries more than one (`bits`, `lossless`, `max_bandwidth_hz`, one of `capabilities.depths`; `null` for a source with one), and `worker`, the child process the source runs in (`pid`, `restarts`, `since_ns`; `transport`, how its blocks reach the node: `path` `shm` or `pipe`, `format`, `ring_bytes`, `null` while none runs or from an older worker; and `transport_dropped`, what it could not hand over: ring pieces (2 MiB) the node had not released, or whole blocks its own pump could not take (pipe queue full, broadcast lagging); `attachment`, where its device is attached (`usb:<bus>-<path>@<speed>`, `null` where it cannot tell); and `link_measure`, the figures the latest hello measured (`max_bandwidth_hz`, `depths`) with the link speed they were measured at (`at_speed`), cached for the next start (see `source_measure`); and `starting`, what a worker not yet live is doing (`what` `measuring`, `detail`, `step` of `of`, `eta_ms`: the most time left), `null` otherwise; `null` for a source that runs in the node), and `ring`, the IQ history (`seconds` sized to, `held_s` held now, `run_s` of it in the newest run, `gaps` in it; `null` before the first block; a `classify` or `iq_read` span older than it fails `too_old`, one across a gap in the capture `gap`), and `position` `{lat, lon, alt_m, from}` (`from` `status` when the source reported it, `configured` from `--source-position`) where the source knows where it is, `null` otherwise, and `sweeps`, the scans the source is sweeping for by its own means, which hold no band and are never among `holders` (`sweeps` is always an array, empty when none). A source can sweep when `capabilities.sweep` is set: `min_hz`, `max_hz`, `bin_hz_min`, `rows_per_s_max` and `calibrated` (the levels in dBm); `capabilities.sweep` is `null` for a source that cannot sweep for itself. Jobs on a faulted source fail with `source ID: FAULT` as their reason; a successful tune (`source_ensure`, `job_start`) clears it. A channelised job's `job_context` holds `channel.path`: `bank` (with `bin_hz`) or `direct` (with `reason`, why not the bank).

JSON: `{"op":"source_list"}`

CLI: `zeta source list`

### source_ensure

Check a band against the source and tune it if no job holds it. Takes no lease: an unheld source is tuned directly (a later `job_start` may retune it); a held source is not retuned without `widen`, and the request either fits the current band (`Tuning`) or is a `Conflict`. Runs under the lease manager's per-source gate, so it never interleaves with a job's lease-and-tune. Elastic jobs do not hold the source: a tune relaunches them on the new capture.

- source: string; an id from `source list`
- center_hz: integer (Hz)
- bandwidth_hz: integer (Hz)
- replace: array; ids from `job list` (strings), `[]` for none
- widen: boolean; `true` moves a held capture and restarts every job holding the source on it; `false` never retunes a held source

JSON: `{"op":"source_ensure","source":"<id>","center_hz":144800000,"bandwidth_hz":12500,"replace":[],"widen":false}`

CLI: `zeta source ensure --source <id> --center-hz 144800000 --bandwidth-hz 12500`

`replace`: job ids that hold the source and may be stopped to make room; they are stopped under the source's gate right before the request, so nothing can take the radio in between. A `conflict` lists the holders; decide whether those jobs may stop, then retry with `replace`. The page's elastic job is never a holder, and a stepped scan never makes a conflict (it gives way and waits, see `scan` below), so there is no need to name one. `widen: true` moves a held source's capture to the band (wider, or shifted) when every holder's band and the pin's still lie inside it: a `conflict` lists `widen the capture to <centre>/<width> Hz` when the radio could capture both the request and what it holds. The source is retuned and every job holding it restarts on the new capture under its id: a short gap in each stream, each decoder's state lost, an external decoder's process started again, a transcription or other attached job relaunched on its input. That is the operator's decision, as a stop is: through `ask` it needs the run to allow stops, else it is refused as `not_allowed`; report the option, do not retry. A widened capture lasts until the node restarts (the jobs resume on their own capture); `source_set_capture` makes the wide capture the source's habit. On the CLI, `--widen`.

### source_pin

Pin the source at a band: a rigid lease held by no job (`source_list` shows it as `pin`, never among `holders`), granted like a rigid `job_start`: inside the capture other rigid jobs hold it is leased without a tune, elsewhere it tunes when only elastic jobs hold the source (they are relaunched on the new capture), else it is a `conflict`. Replaces any pin the source had (a conflict keeps the old one). Persisted in the state directory and restored before any job resumes. The result is the capture.

- source: string; an id from `source list`
- center_hz: integer (Hz)
- bandwidth_hz: integer (Hz)
- replace: array; ids from `job list` (strings), `[]` for none

JSON: `{"op":"source_pin","source":"<id>","center_hz":144800000,"bandwidth_hz":12500,"replace":[]}`

CLI: `zeta source pin --source <id> --center-hz 144800000 --bandwidth-hz 12500`

Hold the source at a band without a job: a rigid holder that is not a job, so `replace` cannot name it and a `conflict` offers `unpin source <id> (source_unpin)`. A pin retunes the source to its band (the page's spectrum follows) unless a decoder holds the source inside that band, when it joins the current capture. Persisted; restored before anything else on a restart. Put `center_hz` between two channels of the grid you listen to so the receiver's DC spike falls in a guard band (the UHF CB plan's midpoint 476918750 Hz with 1000000 Hz holds all 80 channels).

### source_unpin

Release the source's pin (see `source_pin`).

- source: string; an id from `source list`

JSON: `{"op":"source_unpin","source":"<id>"}`

CLI: `zeta source unpin --source <id>`

Release the pin; the source idles if nothing else holds it.

### source_measure

Drop the source's cached rate figures and measure its link again: the worker is ended and respawned to probe each sample depth's clean rate, as at a first start (up to a minute or more, the host busy meanwhile; `source_list` shows `worker.starting` while it lasts and faults the source until the new worker's hello, which heals it). The new figures govern tunes at once (`depth`), show in `worker.link_measure` and are cached for the next start; `capabilities` is set once a run: the first hello of the run that differs from it replaces it, and later ones leave it. A source measures again by itself only when its link speed changed; this is the operator's choice after devices were added around the radio. A source with no worker is refused; one held by a rigid or time-shared job or a pin is a `conflict` naming them (elastic jobs never hold it: they fail with the fault and are relaunched at the heal). The result is `ok` once the respawn is under way.

- source: string; an id from `source list`
- replace: array; ids from `job list` (strings), `[]` for none

JSON: `{"op":"source_measure","source":"<id>","replace":[]}`

CLI: `zeta source measure --source <id>`

Link diagnostics (the page's "Run link diagnostics" on a source with a `worker`): drop the source's cached rate figures and measure what its link sustains again, each sample depth probed as at a first start, about a minute with the host busy meanwhile. The figures belong to the link's speed (`worker.attachment`, `usb:<bus>-<path>@<speed>`): a radio whose USB link came back at another speed measures again by itself, so this is for a system that stutters after devices were added around the radio. It is the operator's call: run it only when asked, never with `replace` unless the operator agreed to stop those jobs. While it runs the source is faulted `measuring the link again` and `worker.starting` reports the probe's steps; the new worker's hello heals it and relaunches what failed. The new figures govern tunes at once (`depth`), show in `worker.link_measure` (`max_bandwidth_hz`, `depths`, `at_speed`) and are cached for the next start; `capabilities` is set once a run: the first hello of the run that differs from it replaces it, and later ones leave it, so read `depth` and `worker.link_measure` for the figures in force. Report each depth's rate against the one before. A source without a worker (a recording, a KiwiSDR, another node) answers `source <id> has no worker`; a source a decoder, a scan or a pin holds is a `conflict` naming them (the page's elastic spectrum never holds it).

### source_free

The sources that could take the band now: `free` lists, in id order, every source whose `tune_min_hz..=tune_max_hz` holds both edges of the band and whose `max_bandwidth_hz` its width, with no rigid holder, no fault, and no pin unless the pin's band holds the whole band (a pin admits jobs inside it; elastic jobs never make a source busy); `busy` lists every other source that covers the band with why: `holders`, `elastic`, `pin` and `fault` as `source_list` gives them. A source that cannot cover the band is in neither list. Takes no lease.

- center_hz: integer (Hz)
- bandwidth_hz: integer (Hz)

JSON: `{"op":"source_free","center_hz":144800000,"bandwidth_hz":12500}`

CLI: `zeta source free --center-hz 144800000 --bandwidth-hz 12500`

Ask which radio could take a band before starting a job on it, then start the job on one of the `free` ids. For a `scan`, a source whose `capabilities.sweep` holds the span can be used while a job holds it, whatever `source_free` says. A source a stepped scan holds is free: the scan gives way. A free source is a suggestion, not a reservation: nothing is leased, and the next `job_start` may still conflict. Its `free` list is in id order, which is no preference: the request's default radio and preference order (`## This request`) come first. A source on another node (`--source-node`) can look free here while that node runs its own jobs on it; that surfaces as a `conflict` on `job_start`.

### source_set_gain

Set the source's overall receive gain live; the result is the gain after the change (`source_list` shows it as `gain`). Persisted in the state directory and re-applied when the node opens.

- source: string; an id from `source list`
- gain_db: number or null (dB)

JSON: `{"op":"source_set_gain","source":"<id>","gain_db":null}`

CLI: `zeta source gain --source <id> --db 40`

Set the source's overall receive gain live (`gain_db` in dB within `source list`'s `gain.min_db..=max_db`), or `null` for the driver's automatic gain where `gain.automatic_available`. Persisted: it is re-applied when the node restarts and wins over `gain=` in the device args. A source without adjustable gain (a recording, a KiwiSDR, another node) answers `source has no adjustable gain`. On the CLI, `--auto` passes `null`.

### source_fit

Narrow a held source's capture to the jobs holding it: the source is retuned to its narrowest rate that holds the band bounding every holder and its pin, and each holder restarts on that capture under its id, as after a `source_ensure` with `widen` (the same gap in every stream). The way back from a widened capture, and less work for the host. When the source already runs at that capture nothing restarts. A source nothing holds is refused; one under a scan that does not give way is a `conflict`. The result is the capture.

- source: string; an id from `source list`

JSON: `{"op":"source_fit","source":"<id>"}`

CLI: `zeta source fit --source <id>`

The way back from a widened capture: the source is retuned to the narrowest rate that holds the jobs on it (and its pin) and each of them restarts on it under its id, with the same short gap and lost decoder state as a widen. Use it when the wide view is no longer wanted and the host should work less. Restarting the holders is the operator's decision: through `ask` it needs the run to allow stops, else it is refused as `not_allowed`; report that, do not retry. On the CLI, `zeta source fit --source <id>`.

### source_set_capture

Set how the source's capture is chosen when a rigid job (or a set) tunes it free: `fit` (the default) takes the narrowest rate that holds the job or the set's bounding band; `widest` takes the source's whole `max_bandwidth_hz` about the same centre, so later jobs and a wider view fit beside it without a retune, the source running at its full rate throughout (more CPU and memory). It never moves a capture already held: it applies from the next tune of the free source (also at a restart's resume). An elastic job, a pin, `source_ensure` and a scan's steps tune to their own band whatever it says. Persisted in the state directory; `source_list` shows it as `capture_policy`.

- source: string; an id from `source list`
- policy: string (CapturePolicy: fit|widest)

JSON: `{"op":"source_set_capture","source":"<id>","policy":"fit"}`

CLI: `zeta source capture --source <id> --policy fit`

How wide the source's capture is when a job or a set tunes it free. `fit` (the default) takes the narrowest rate that holds the job or the set's bounding band: the least CPU and memory. `widest` takes the source's whole `max_bandwidth_hz` about the same centre, so the page can zoom out to the radio's full instantaneous width beside the running jobs and a later job megahertz away fits without a restart; the source then runs at its full rate all the time, which costs CPU (the channel bank) and memory (the IQ history) in proportion. It applies from the next time the free source is tuned for a job (stop and start the set, or restart the node); it never moves a capture jobs hold (`source_ensure` with `widen` does that). Persisted. On the CLI, `zeta source capture --source <id> --policy widest`.

### job_start

- kind: string (JobKind: passthrough|spectrum|fm_demod|wfm_demod|am_demod|ssb_demod|aprs_decode|pocsag_decode|rds_decode|acars_decode|adsb_decode|measure|scan|identify|watch|transcribe|mix|capture|packets|ais_decode|ble_decode|dfm_decode|dmr_decode|dvbs_ip_decode|dvbt_decode|flex_decode|gsmr_decode|hfdl_decode|lorawan_decode|lte_decode|m17_decode|m20_decode|p25_decode|rs41_decode|tetra_decode|thread_decode|vdl2_decode|video_decode|wifi_decode|wisun_decode|zigbee_decode|zwave_decode; the built-in kinds and the embedded mode rows, a node's own `schema` adds its operator rows)
- source: string; an id from `source list`
- center_hz: integer (Hz)
- bandwidth_hz: integer (Hz)
- deviation_hz: integer or null (Hz)
- sideband: string or null
- dwell_ms: integer or null; `scan` only, in ms (1-5000)
- average: integer or null; `scan` only, sweeps averaged (1-64)
- bits: integer or null; `scan` only, bits per sample: one of `capabilities.depths[].bits` in `source list`
- method: string or null; `scan` only, `stepped` or `source`; `null` lets the node choose
- bin_hz: integer or null (Hz); `scan` only, the bin width in Hz asked of a source that sweeps for itself (1-1000000)
- audio_policy: string or null; a mode whose row lists `voices` only: `first_active`, `follow` or `all`; `null` is `first_active`
- dwell_scale: integer or null; `identify` only: each tried row's dwell times this (1-6); `null` is 1
- elastic: boolean
- replace: array; ids from `job list` (strings), `[]` for none
- handler: string or null; a mode row's kind only: a handler id of the mode (`modes list`'s `handlers[].id`); `null` for the handler policy's choice
- needs: array; a mode row's kind only: the stream kinds the job must output, among `event`, `packet` and `audio` (`["packet"]` for a job to capture); `[]` for none
- beside: string or null; a running job of a mode row (`job_list`): start a sibling on its band by another `handler` (required); `kind`, `source`, `center_hz` and `bandwidth_hz` must equal that job's; `null` for an ordinary start

JSON: `{"op":"job_start","kind":"passthrough","source":"<id>","center_hz":144800000,"bandwidth_hz":12500,"deviation_hz":null,"sideband":null,"dwell_ms":null,"average":null,"bits":null,"method":null,"bin_hz":null,"audio_policy":null,"dwell_scale":null,"elastic":false,"replace":[],"handler":null,"needs":[],"beside":null}`

CLI: `zeta job start --kind passthrough --source <id> --center-hz 144800000 --bandwidth-hz 12500`

`fm_demod` is narrowband FM voice; `wfm_demod` is wideband broadcast FM (50 us de-emphasis, 15 kHz audio; give it a band of about 200000 Hz). It is mono by default; `stereo: true` on its `wfm_demod` node, set with `graph put` and kept through a retune, makes its audio two channels, L and R, for the whole run: decoded L and R while the 19 kHz pilot is present and strong, both carrying the mono L+R otherwise, as receivers fall back (stereo needs about 20 dB more signal than mono for the same audio SNR). `job_context.wfm` holds `pilot_db` (the locked pilot's power against the multiplex's: over -30 dB the pilot is present, under -36 it is gone; a clean station reads -24 or more), `pilot_snr_db` (the pilot's power against the noise beside it: it falls dB for dB as the station weakens; stereo needs it over 35 dB and drops to mono under 30) and `stereo` (true while L and R are decoded); the two figures are `null` when the band is too narrow to carry stereo. It is noted when `stereo` switches and every 5 s, and cleared (`wfm: null`) by a run without `stereo`. Read them together: `stereo: false` with a low `pilot_db` means no pilot (a mono station, or nothing received); with `pilot_db` over -30 and a low `pilot_snr_db` it means a pilot too weak for clean stereo, so the job plays mono until the signal improves. `am_demod` is AM voice (envelope detector, 5 kHz audio, slow AGC; give it a band of about 10000 Hz). `ssb_demod` is SSB voice (2800 Hz audio, slow AGC; `center_hz` is the suppressed-carrier (dial) frequency, not the middle of the voice band, and the band must cover both sides of it: give it about 6000 Hz). All four output 48 kHz audio, mono unless a `wfm_demod` has `stereo: true`: an audio frame's payload is `{"sample_rate_hz", "channels", "samples": N, "peak"}`, `channels` 1 here (2 for a stereo `wfm_demod`; an attached `transcribe` downmixes it, a `mix` skips it and lists it in `job_context.mix.skipped`), the samples interleaved and `samples` the per-channel count (a frame without `channels` means 1). `fm_demod` shapes its audio as a voice receiver does (a 3.4 kHz low-pass and a 530 us de-emphasis after the discriminator: `audio_lowpass_hz` and `deemphasis_us` on its node, `null` for the flat audio a decoder wants), and every voice demodulator (`fm_demod`, `am_demod`, `ssb_demod`) takes `denoise: true` on its node to run RNNoise on its audio output (off by default; speech only; one 10 ms frame of delay the frames' spans account for; set with `graph put`, kept through a retune; a `transcribe` attached to such a job skips its own `denoise` stage). `fm_demod` and `am_demod` carry an automatic squelch: it opens 6 dB over the channel's tracked noise floor (never taken above -40 dBFS: with no fixed threshold `floor_db` reads at most -40) and closes after 300 ms under it. While closed the job publishes no audio (an attached transcriber idles; `--then-tail` tails the audio, so an idle channel's tail is empty) and the first block and each change publish a `squelch` event (`open`, `power_db`, `floor_db`) on the job's event stream. The demod node's params set it with `graph get` and `graph put`: `squelch_db` is an absolute threshold in dBFS, -120..=0 (`null`, the default, is the automatic one; a value outside the range fails the job with `squelch_db <v> out of range -120..=0`), and `squelch: false` turns it off. `aprs_decode`'s demodulator runs with the squelch off. `fm_demod` on a channel of a plan (`channel_plans`) carries an adjacent-channel guard: its squelch stays closed while a channel `guard_hz` away is more than `guard_db` (12) dB stronger, so a transmission on ch20 does not open ch59 or ch60. The `squelch` event carries `adjacent_db` and `guarded`; once guarded, the gate stays held until the neighbour falls 2 dB under `guard_db`. The job's `job_context` keeps the last `squelch` event under `squelch` (removed when a run has the squelch off), so a client that subscribes after the gate changed reads it there. `graph put` with `guard_hz: null` on the demod node turns it off. `pocsag_decode` decodes POCSAG pagers (512, 1200 and 2400 baud detected automatically) from a 12.5 kHz FM channel into one event per message (`address`, `function`, `kind`, `text`). `flex_decode` runs multimon-ng on the node's host over a 25 000 Hz channel at the measured centre, one event per page like POCSAG; its events carry `access: 'restricted'`. `rds_decode` reads the RDS data of a broadcast FM station (give it the same 200000 Hz band as `wfm_demod`) into events carrying `pi`, `ps` (station name) and `rt` (radio text) as they complete; the first event takes a few seconds. `adsb_decode` decodes Mode S / ADS-B at 1090000000 Hz with `bandwidth_hz` 2400000 (anything under 2000000 is refused) by running dump1090 on the node's host; one event per decoded message (`icao`, `callsign`, `altitude_ft`, `lat`, `lon`, `ground_speed_kt`, `track_deg`), position and identity arriving in separate messages. When the host has no dump1090 the node's startup handler report names it (`zeta: handlers: dump1090: missing (apt install dump1090-fa; <url>) — modes: adsb_decode`; the one command is chosen by the package managers on the host's `PATH`, in the order `apt`, `dnf`, `brew`, `snap`, `flatpak`, from the row's `install` entries, and a row's `script` comes first), `modes_list` shows `adsb_decode` `unavailable` with that line as its `reason`, and `job_start` fails with `mode adsb_decode is unavailable: <reason>`. `acars_decode` decodes ACARS (VHF, AM, 2400 baud MSK) from a 10000 Hz channel on 131550000 Hz (worldwide primary), 131725000 / 131825000 (Europe), 130025000 / 130450000 / 131125000 (North America), 131450000 (Asia) into one event per CRC-clean block (`reg`, `flight`, `label`, `text`, `downlink`: true for a downlink); a downlink whose text is a position report (labels H1, 80, 16, 3L, QQ) also carries `lat`, `lon`, sometimes `alt_ft`, and `position`. `vdl2_decode` decodes VDL Mode 2 (VHF data link, D8PSK) from a 25000 Hz channel on 136975000 Hz worldwide (136725000 / 136775000 / 136825000 / 136875000 in Europe) by running dumpvdl2 on the node's host: one event per AVLC frame keyed on the ICAO address `icao` (`addr_type` tells an aircraft from a ground station), with the ACARS fields (`reg`, `flight`, `label`, `text`) and a `position` on ADS-C reports; On the CLI, omit `--deviation-hz` and `--sideband` for `null`. `scan` sweeps a band wider than one capture: the node steps the source across it in captures of its whole `max_bandwidth_hz`, each step advancing by the capture's usable part (`usable_fraction` in the source's capabilities: 0.9 on a SoapySDR device, `usable=F` in its args to change it; a `--source-node` takes its remote's; 1.0 on the other kinds), takes `dwell_ms` of samples on each (20 ms unless `job_start` asks otherwise, 1-5000; at least four FFT frames and never more than the source's ring holds; `scan.dwell_ms` in its context is the dwell in force, `scan.dwell_ms_asked` the one asked when they differ), and emits `spectrum` rows whose `center_hz` is that step's (frame `channel` `scan/<step index>`), wrapping until stopped. With `average` N (1-64, default 1) each row is the mean power of its step's last N sweeps of the same grid (an even step with the even sweeps of its centre; N is lowered to what an eighth of the node's ring budget holds for every step's rows, and then `scan.average` is the one in force and `scan.average_asked` the one asked), and every row carries `sweeps`, how many it averages so far (1 without averaging; the averages start over when the scan restarts or its grid changes). The look is the operator's choice: many quick looks averaged (20 ms × 16) lower the noise ripple as one 320 ms dwell does while each step is still revisited every sweep; a long look (250 ms × 1) sees a faint steady signal in one dwell; the default (20 ms × 1) is the fastest sweep. With `bits` (one of the source's `capabilities.depths[].bits`; `null`, the default, is the source's own `depth`) the scan holds the source's link at that sample depth for its run, steps at that depth's `max_bandwidth_hz`, and puts the source's own depth back before anything else is granted the source; `scan.bits` and every row's `bits` say the depth in force (on a source with depths). Such a scan does not give way (below). A lossy depth (8 bits on a B210) sweeps faster, but a weak signal beside a strong one in the same capture is lost in its quantisation noise: it is for a coarse survey of occupancy, never for faint signals, and never the default. A `bits` the source does not carry is refused naming its depths. Alternate sweeps shift the step grid down by a quarter of the stride, `step_hz` (the odd sweep has at most one more step), so a step's centre and edges in one sweep fall a quarter of the way into a row of the next and every frequency is seen clean in one of two sweeps, whatever edge mask is under `(1 - u) / 2 + u / 8` for the usable fraction `u` (0.1625 at 0.9, 0.125 at 1.0); `scan.alternate` in the job context gives `shift_hz` and `steps_shifted` (`null` for a one-step span). A scan on a local hardware receiver masks each row's centre notch (`notch_hz`, 50000 Hz), and every scan masks each row's outer edges that the usable fraction leaves unused (`edge_mask`, `(1 - usable_fraction) / 2` of the bins each side: 0.05 on a SoapySDR device, none where the whole capture is usable), never less whatever `edge_mask` its stored node says. A row with masked bins carries `masked: [[lo, hi], ...]` (bin index ranges, `lo` inclusive, `hi` exclusive): those bins are no data, not low power; their `q` is still present. `scan.mask` reports the values in force (a step narrower than four notches gets no notch; a span no wider than one capture's usable part is one step, asking for the span divided by the usable fraction so the unused edges it masks lie outside the span; it does not alternate and masks no more than those edges, since nothing could fill a wider mask in), and `graph get`, edit the `fft` node's `notch_hz`/`edge_mask`, `graph put` changes them (keep `edge_mask` under that bound, 0.1625 on a SoapySDR device, or the two grids' masks overlap). Of the scan's stored `fft` node only `notch_hz`, `edge_mask`, `dwell_ms`, `average` and `bits` are read (`graph put` changes the look as it changes the mask; the scan restarts): its `size`, `window` and `rows_per_s` are information only (the scan derives them per step), and a `graph put` whose graph has no `fft` node is re-expanded with the default mask on the next launch rather than refused. It takes the source back by itself, starting a new sweep, once no rigid job, no pin and no other scan holds it, and then stops the source's elastic jobs as its start does (so an elastic job started beside a running scan is granted and ends at once). A stepped scan started on a source a rigid job or a pin holds returns its id and waits the same way; with `replace` naming the holders it stops them and steps at once. A source delivers only settled samples after a tune (the first block of a new centre is taken after the radio settled), so a step's first row is as good as its later ones; a `--source-node` source takes its far node's, and a KiwiSDR drops the frames still in flight at the old frequency. A source whose `capabilities.sweep` holds the span (`source_list`: `null` for a source that cannot sweep for itself, else `min_hz`, `max_hz`, `bin_hz_min`, `rows_per_s_max`, `calibrated`; a KiwiSDR's waterfall is the first) sweeps for a `scan` itself: `context.scan.method` is `source`, the scan takes no lease and no IQ, leaves the source's capture and its holders alone, runs beside any demodulator on it, and is listed under `sweeps` in `source_list`, never under `holders`. `method` `stepped` forces the stepped scan; `source` never steps; `null` lets the node choose. `bin_hz` asks the source for that bin width (the source picks its zoom and step count from it; the default is the coarser of 6000 Hz and the source's `bin_hz_min`); `dwell_ms` and `average` apply to the source's rows as they do to a stepped scan. `bits` beside `method: source` or beside `bin_hz` is refused (`bits applies to a stepped scan`), and so is a non-empty `replace` beside `method: source` (`replace applies to a stepped scan`). `replace` on a scan is honoured only if the scan has to step: a scan the source sweeps for itself stops nothing; if a refusal makes the scan step, the named jobs are stopped before it takes the radio. A `source` scan has `context.scan` keys `method`, `steps`, `step_hz`, `bin_hz`, `dwell_ms` (`dwell_ms_asked`), `average` (`average_asked`), `alternate`, `mask`, `calibrated`, `waiting` and `timing` (the stepped scan's keys, no tune time, and `rows_per_s`: the rows a second since the last write, the figure to read for a one-view sweep; rewritten at most once a second, re-aims included); while it is `waiting` it holds only `method`, `mask`, `calibrated` and `waiting` (the plan's keys arrive when the source grants the sweep, `timing` after its first sweep); it has no `rate_hz` and no `bits`, and the source masks its own rows (the first pixels of each view are masked as `masked`). On the CLI, `--audio-policy first_active|follow|all`. A mode may have more than one handler (`modes_list`'s `handlers`: the row's own, `builtin` or its program, and each handler file's), all decoding into the row's events; a row with no decoder of its own (`decoder_kind` `null`) has only its handler files'. `handler` names the one to run, an id from the mode's `handlers`; `null` takes the handler policy's choice (`modes_list`'s `handler`; `handler_policy_set`). A row with no decoder of its own and no ready handler is refused as `mode <id> is unavailable: <reason>`, its `modes_list` reason. Name one only when the operator asks for it or two jobs must differ (the same mode on one band by two handlers is two jobs); otherwise leave it `null`. `needs` lists the stream kinds the job must output, among `event`, `packet` and `audio`: `["packet"]` is how a job to capture is asked for, and the policy passes over a handler without them before it reads any ranking. A named handler lacking a needed output is refused as `<mode>: handler <id> outputs no <kind>`. Read which handler a job runs from its record's `handler` (`handler_named` says whether it was asked for), and what it outputs from that handler's `outputs`, never the mode's. Its events carry `handler`, and a packet capture of it records `handler` in its `packets_list` entry and in each packet's comment (`handler=<id>`). On the CLI, `--handler ID` and `--needs packet[,audio]`. `beside` names a running job of a mode and starts a sibling on the same band by another handler, to compare two decoders on one signal or to capture packets from a handler that gives them when the running one gives none. `kind`, `source`, `center_hz` and `bandwidth_hz` must equal that job's (its record's `tuning`), `deviation_hz` and `sideband` must be `null`, `elastic` false and `replace` empty, and `handler` is required: without one the start is refused naming the free ids, `beside needs a handler: one of <ids>`. The named job must be running, not attached, not owned by a controller, not elastic, and of a mode row. A handler the group already runs is a `duplicate` naming that member, `handler <h> already runs beside job <beside> as job <member>`; a job outside the group running that handler on the band is the ordinary `duplicate`. Nothing is tuned and nothing is stopped. Both records carry `group`, the id of the job the first start was beside (the first job gets it once its sibling has launched), so `job_list` shows who runs together. `job_stop` stops one job and leaves the others. Read each job's events and compare. On the CLI, `--beside JOB --handler ID`: the kind, `--source`, `--center-hz` and `--bandwidth-hz` are read from that job when left out, and a value given is sent as given. A node rolled back past this build resumes no jobs, as its records carry `group`.

### job_attach

Attach a job of an attachable `kind` (`transcribe` or `packets`) to the running job `job`. It reads one of that job's output streams instead of the radio, holds no lease, copies the job's `source` and `tuning`, and records it as its `input`. It follows its input through a `job_retune` or a `graph_put` restart: it is relaunched under its own id on the input's new stream once the input runs again (`failed` with the reason when it cannot be). It ends `stopped` when the input job stops or fails for its own reason.  `transcribe` reads the audio of a job whose kind emits audio: the voice demodulators and any mode row whose `outputs` lists `audio` (the last audio output in its graph order when it has several; audio passed between two of its stages does not count). On a node restart it resumes after its input, or is `failed` with `input job <id> not running` when the input does not run.  `packets` captures the frames of a decoder job whose row's `outputs` lists `packet` (`aprs_decode`, a frame row) into a pcapng file Wireshark opens: one packet per decoded frame (link type `ax25_kiss` for APRS, `user0` for a frame row), stamped with the frame's start, its comment `job=<decoder job> handler=<its handler> source=<id> freq_hz=<centre>` (no `handler=` for a kind of no mode row). The job's context names the file as `capture` (with `packets` and `bytes` so far), and `packets_list` lists it with its `handler`; fetch it, also while it is written, at `GET /captures/<id>.pcapng`. A retune of the input closes the file and opens a fresh one at the new centre. `language` is ignored and `stream` must be `null` (`packets reads the job's packet stream: pass stream null`). Refused, nothing started: a job with no packet stream (`job <id> has no packet stream: its kind's outputs list no packet (modes_list)`; `...: handler <id> outputs none (<other> does)` when another handler of its mode gives packets: start that one with `needs: ["packet"]`), an attached job (`packets: job <id> is an attached job: attach to its input <input>`), a job whose row cannot be read now, say after a modes reload (`packets: <kind> has no readable mode row: its access cannot be checked`), a row with `access: restricted` (`packets: <row> is restricted: its capture waits on access control`) and a job already captured (`job <id> is already captured by <packets job>`). A row edited to restricted or made unreadable after the attach (and a modes reload) ends a running capture at its next relaunch (the input's retune, graph put or heal): the `packets` job is `failed` with the same reason, and its input runs on. A capture of a restricted row is never served (`404`, as an unknown id). It does not resume across a node restart: it is listed `stopped` with the note `packet capture does not resume: attach again`, its file kept.

- kind: string (JobKind: passthrough|spectrum|fm_demod|wfm_demod|am_demod|ssb_demod|aprs_decode|pocsag_decode|rds_decode|acars_decode|adsb_decode|measure|scan|identify|watch|transcribe|mix|capture|packets|ais_decode|ble_decode|dfm_decode|dmr_decode|dvbs_ip_decode|dvbt_decode|flex_decode|gsmr_decode|hfdl_decode|lorawan_decode|lte_decode|m17_decode|m20_decode|p25_decode|rs41_decode|tetra_decode|thread_decode|vdl2_decode|video_decode|wifi_decode|wisun_decode|zigbee_decode|zwave_decode; the built-in kinds and the embedded mode rows, a node's own `schema` adds its operator rows)
- job: string; an id from `job list`
- language: string or null
- stream: string or null; a voice of the job, one of its row's `voices` in `modes_list`; `null` for its main audio stream

JSON: `{"op":"job_attach","kind":"transcribe","job":"<id>","language":null,"stream":null}`

CLI: `zeta job attach --kind transcribe --job <id>`

Attach a processing chain to a running job's output instead of the radio: `transcribe` reads the audio of a job whose kind emits audio: the voice demodulators and any mode row whose `outputs` lists `audio` (`m17_decode`). It cleans it (denoise, voice gate) and emits one `transcript` event per utterance (`text`, `language`, `start_ns`, `end_ns`) plus `vad` events as speech starts and stops; it holds no lease, follows its input through a `job_retune` or a `graph_put` (relaunched under its own id) and ends when the input job stops. `language` is a BCP-47 code (`null` means `en`; the backend's languages are in `GET /stt/languages`). To transcribe a station: `job_start` a `wfm_demod` on it, then `job_attach` with `kind: transcribe` and that job's id. The attached job fails with a reason naming the speech backend when the node has none or it cannot serve the language. Every other kind (`identify`, `watch`, the demodulators and decoders) runs on the radio and is refused here as `<kind> is not attachable`. A stage output marked `role: composite` (a video demodulator's composite) is never a job's audio: `job_attach`, the mix and `--then-tail` skip it (a `stream tail` on it still reads it). `stream` names the voice to read of a job whose row lists `voices` (`modes_list`: `slot1`, `slot2`), each on an audio stream with its role; `null` reads the job's main stream as above. To transcribe both slots of a DMR channel, attach twice, once per slot. A role the job lacks is refused naming those it has, `stream: <job> has no voice <role> (it has: slot1, slot2)`, or `stream: <job> has one voice` for a job with none. The attached job's record keeps it as `stream`, each `transcript` event and `transcripts.log` line carries it (`null` for the main stream), and a relaunch (a retune, a restart) reads the same voice. On the CLI, `--stream ROLE`. `packets` captures a decoder's frames for Wireshark: `job_start` an `aprs_decode` (or a frame row) on the channel, then `job_attach` with `kind: packets`, that job's id, `language: null` and `stream: null`; the job's context `capture` (or `packets_list`) gives the id to fetch at `GET /captures/<id>.pcapng`. The file rolls at 256 MiB into a fresh capture, is downloadable while it is written, and does not resume after a node restart (attach again). Stop the `packets` job to close the file; the decoder runs on.

### job_retune

Retune a running job on the radio to a new band under the same id: under the source's gate its lease is moved to `center_hz`/`bandwidth_hz` (inside the current capture it is granted without a tune, whether or not another rigid job's band overlaps it; outside it the source is tuned when no other rigid job or pin holds it, else it is a `conflict` naming the holders and the job is left as it was), its graph is expanded again for the new band at the capture's rate and the job relaunched, `tuning` updated. Applies to a `running` job the node expanded and can re-expand: the four demodulators, the decoders, `measure`, `passthrough` and the mode rows. Refused naming the kind for a stepped `scan` (a `scan` its source sweeps is re-aimed, below), `watch`, `identify`, `spectrum` (elastic or rigid), `mix` (it has no band), a `graph_start` job (it runs on no radio) and `transcribe` (attached: retune its input), and for a job whose graph an operator `graph_put` replaced (it launches as stored: put a new graph or start a new job). A job a controller started (its `owner`: a watch's identify run or its trial) is refused naming the owner, `job <id> is run by <kind> <owner>: stop that job, or start a new one` (once the owner has ended, `job <id> was started by <kind> <owner>, which is not running: stop it, or start a new job`); a `replace` naming one while its owner runs is refused as `job <id> is run by <kind> <owner>: stop that job`. A job that is not running is `job <id> is <state>`; an unknown id is `unknown`. The result is the job's id, as `job_start` answers.  A job of a Send to group (its `group`, from `job_start` with `beside`) with another member running moves with the whole group, as one lease move under the source's gate: every member's handler is settled first (a member whose named handler is no longer ready refuses the retune naming it, `job <id>, a member of the retuned job's group: <reason>`, and nothing moves), then every member's lease moves to the band together (one tune at most; a `conflict` names only the holders outside the group, and every lease is put back), then each member is relaunched on it, the job named first. A member whose relaunch fails is `failed` with its reason and the others run on; each member's attached jobs follow it. A `replace` naming a member is refused, `replace names job <id>, a member of the retuned job's group`, and so is a group with a member whose graph an operator `graph_put` replaced. The result is the id of the job named.  A `scan` its source sweeps for itself (`job_context.scan.method` `source`) is re-aimed instead: under the source's gate the source's running sweep moves to the new span (and `bin_hz`, when given) on what it already holds, the Kiwi's open waterfall socket, without ending it; the job keeps its id, its event stream and its sweep claim, `tuning` and `job_context.scan` follow the source's new plan (`steps`, `step_hz`, `bin_hz`, `alternate`; `timing` is kept) and the averages start afresh (each row's `sweeps` from 1). A source that cannot re-aim has its sweep ended and a new one asked for under the same id. A span the source's `capabilities.sweep` does not hold is refused naming its range, the scan running on as it was; a non-empty `replace` is refused (`replace applies to a stepped scan`: the sweep takes no lease). A stepped scan is `scan is not retunable`.

- job: string; an id from `job list`
- center_hz: integer (Hz)
- bandwidth_hz: integer (Hz)
- bin_hz: integer or null (Hz)
- replace: array; ids from `job list` (strings), `[]` for none

JSON: `{"op":"job_retune","job":"<id>","center_hz":144800000,"bandwidth_hz":12500,"bin_hz":null,"replace":[]}`

CLI: `zeta job retune --job <id> --center-hz 144800000 --bandwidth-hz 12500`

`replace`: as on `job_start`, the holders that may be stopped to make room, stopped under the gate right before the request; a `conflict` offers `retry with replace: [<ids>]` and the page shows the same retry buttons. A demodulator keeps its `squelch`, `squelch_db`, `deviation_hz` and `sideband` through a retune; its adjacent-channel guard (`guard_hz`, `guard_db`, `channel_hz`, the channel node's `wide_hz`) is derived again from the channel plan at the new band, never carried, so a width preset changes what the filter passes and a move to a neighbouring channel takes that channel's geometry; a guard turned off with `graph_put` (`guard_hz: null`) comes back on a retune onto a plan channel. Every attached job (`job_attach`) reading the retuned job is relaunched under its own id once the input runs again (one that cannot relaunch is `failed` with the reason; the retune still succeeds). A job started beside another (`job_start`'s `beside`; its record's `group`) retunes with its group: `job_retune` of any member moves every member to the new band under one gate. A `conflict` names only holders outside the group, and `replace` may not name a member. A member whose relaunch fails is `failed` with the reason and the others stand; a relaunch never puts two members on one handler. Centre the band on the signal's measured centre (`measure`, `classify`), never on a raster: see Fitting a demod to a signal under Field craft. A one-shot `zeta job retune` cannot reach a job `zeta serve` runs (`job <id> is not running in this node`): use `--node`. On the CLI, `--replace ID[,ID]`. A `scan` its source sweeps for itself (`job_context.scan.method` `source`) is re-aimed rather than restarted: the same id and event stream, `tuning` and `job_context.scan` (`steps`, `step_hz`, `bin_hz`, `alternate`) following the source's new plan, the rows of the old span gone and each row's `sweeps` counting from 1 again; `bin_hz` (`--bin-hz`) asks a new bin width with it (`null` keeps the scan's), and is refused on any other job. A span outside the source's `capabilities.sweep` is refused naming its range, `replace` is refused (`replace applies to a stepped scan`), and a stepped scan stays `scan is not retunable`: stop it and start a new one.

### mix_start

Start a mix: a job that sums the audio of every other job with an audio output on `sources` and plays it as one stream, so whatever is talking is heard. It takes no lease, tunes nothing and blocks no job (its record's source is `node`, its band 0); jobs started or stopped later join and leave by themselves within a second. It outputs `audio` and `event` streams; each change of who is talking publishes `{"protocol": "mix", "active": [{"job", "source", "center_hz"}], "t_ns", "summary"}`. Attached jobs, a `watch`'s or `identify`'s own jobs, other mixes and jobs centred on a plan channel that carries no voice (UHF CB ch22 and ch23) are not mixed. With a mix of the same set of sources already running the result is its id; `null` matches only `null`, so a list naming every source is another mix. It runs until stopped, and a node restart resumes it after the jobs it mixes.

- sources: array or null; ids from `source list` (strings), `null` for every source

JSON: `{"op":"mix_start","sources":null}`

CLI: `zeta mix start`

Starts one `mix` job that plays the audio of every job on `sources` (`null`: every source) as one stream, so whatever is talking is heard. It holds no lease, tunes nothing and blocks no job; jobs started or stopped later join and leave by themselves. Its `event` stream publishes `active` (who is talking: `job`, `source`, `center_hz`) when it changes, with a hangover after a channel falls silent. It is idempotent on the same set of sources: a mix of that set already running answers its id (`null` matches only `null`). To mute a channel, `graph get` the mix, edit `muted` on the `mix` node (a list of `{source, center_hz}`), `graph put`, which restarts it under its id.

### packets_list

The confidence is 0.3 without a framing and 0.6 with one. Report the proposal's `id`, `name` and `confidence`.

### signature_accept

Accepting or rejecting is the operator's decision: through `ask` the run needs `allow.accept_signatures` (`zeta ask --allow-signatures`; on the page, `allow signatures on`), else `not_allowed`: report the proposal, do not retry.

- id: string; an id from `signature list`
- name: string or null

JSON: `{"op":"signature_accept","id":"<id>","name":null}`

CLI: `zeta signature accept --id <id> [--name NAME]`

Through `ask` without `allow.accept_signatures` the call is refused as `not_allowed`: report the proposal (its `id`, `name`, `confidence` and `evidence`), do not retry. Never accept a proposal the request did not name. The captures it was learned from are pinned: never expired nor deleted. A record not `proposed` is `other` (`signature <id> is accepted, not proposed`). Accepting a framed signature (a `framing` with a `crc`, and a `symbol_rate_baud`) also writes its decoder row, `learned_<id>` (the id lowercased), to `learned_<id>.json` in the operator's modes directory (`--modes-dir`, else `$XDG_CONFIG_HOME/zetasdr/modes` or `~/.config/zetasdr/modes`) and reloads the rows: a frame row of the signature's band, demodulator and framing with the `opaque` parser, proved by one CRC-clean frame, listed by `modes_list` at once. The record's `decoder` names the row and `decoder_file` its file: start it as `kind` the record's `decoder` (use that field; never build the id). A file already there is never overwritten (`decoder_note`: `row learned_<id> already present: kept as is`), so the operator may edit the row freely (a parser, a subject); with no modes directory (`no modes directory: row not written`) or a failed write (`row not written: <error>`) the signature is still accepted and `decoder` stays `null`. - sideband: string or null
- attach: string or null
- language: string or null
- replace: array; ids from `job list` (strings), `[]` for none

### bits_start

Work a capture's bits: takes every capture of the named capture's `set`, in time order, and starts `capture_in → resample → <demod> → clock_recover → slicer → bit_view` from the named capture's feature record, each `null` taken from the features (`modulation`, one of `fsk`, `psk` and `ook`, from the layer-1 label: `fsk` and `fm` give `fsk`, `psk` and `ook` themselves; `symbol_rate_baud` and `order` from the record, `order` 2 when it has none; fsk takes 2 or 4, psk 2, 4 or 8, ook 2). The capture is resampled to about 8 samples per symbol for fsk and ook, and for psk to the smallest multiple of 4 times the baud that also covers a carrier offset of 2000 Hz (the coarse estimate is unambiguous only within the rate over twice the order), moved to a rate the resampler serves exactly. A signal off the capture's centre whose recorded band reaches past the resampler's passband (its offset plus half its `bandwidth_hz` over 0.45 times that rate) is shifted to its recorded `center_hz` first, unless layer 1 labels the capture `noise`: `capture_in → channel [→ resample] → <demod> → ...`, the `channel` stage at the measured centre with the measured bandwidth × 1.25 (at least 4 × the baud, at most what the capture holds about that centre: its rate less twice the shift) and an output rate the capture rate over a whole divisor (the resampler follows unless that is already the chain rate). 4-fsk and ook take the `early_late` clock; fsk's demodulator is given the record's measured `tone_spacing_hz` (it tracks the tones itself when the record has none); `capture_in` loops, paced, with a 500 ms pause between passes, and the job runs until stopped. Refused with `other`: a field neither the request nor the features give (`no symbol rate measured; give symbol_rate_baud`, `no modulation measured (label <x>); give modulation`), a rate the capture cannot hold (`symbol_rate_baud <r> needs <n> Hz; the capture holds <rate> Hz`, 4 samples per symbol at least; a rate of 0 is `symbol_rate_baud: at least 1`), a measured centre the capture holds under 4 × the baud about (`the measured centre <c> Hz leaves <room> Hz of the capture <lo>..=<hi> Hz about it, under the <floor> Hz the chain needs (4 x <baud> Bd)`), and a set whose captures differ in rate or centre (`capture <id>: <rate> Hz differs from <first>'s <rate> Hz`); an unknown `capture` is `unknown`. The record's kind is `bits`, its source `node`, its band the capture's, `job_context.bits` the plan (`captures`, `modulation`, `symbol_rate_baud`, `order`, `tone_spacing_hz`, `rate_hz`, `center_hz` the centre the chain runs on and `shift_hz` its offset from the capture's, `bandwidth_hz`, `padded_bandwidth_hz` the channel band uncut and `clamped` whether it was cut to the capture, and `channel_rate_hz`, `null` (and `padded_bandwidth_hz` `null`) when the chain does not shift); the slicer's `bits` events are on `job_context.slicer.stream` and `bit_view`'s latest hypotheses in `job_context.bit_view`. Change a running chain with `graph_get`, edit, `graph_put`. The result is the job's id, as `job_start` answers; one-shot `--then-tail` tails the `bits` events. The agent's own `bits_start` jobs count as jobs it started.

- capture: string
- modulation: string or null
- symbol_rate_baud: integer or null
- order: integer or null

JSON: `{"op":"bits_start","capture":"<id>","modulation":null,"symbol_rate_baud":null,"order":null}`

CLI: `zeta bits start --capture <id> [--modulation fsk|psk|ook] [--symbol-rate-baud N] [--order N] [--then-tail MAX_FRAMES,TIMEOUT_MS] [--keep]`

### capture_decode

Replay a stored IQ capture into a decoder mode's graph: check a decoder against a recording, or compare two handlers on the same one. The whole set of `capture` is replayed, once and paced in real time, each capture in start order, into the mode row `kind` expanded for the capture's centre, width and sample rate (no channel bank) behind a `capture_in` node. The job is leaseless: it holds no lease, tunes no radio and its record's source is `node`; its kind is the mode's id, its band the first capture's, `handler` and `handler_named` as `job_start` writes them, its `replay` field the capture named, and `job_context.replay` gives `capture`, `captures` (the set's ids by start time), `source` (the radio that recorded it), `start_ns` (the first capture's start) and `end_ns` (the last one's end). Every decoded event (each event a decoder gives in the mode's envelope) carries `replay: <capture>`, and its events carry the recording's own times (`t_ns`) and go only to the `replay` feed (the event feed of the source `replay`, which no radio may be named), never to a radio's feed or `events.log`. It ends `stopped` once the set has played and the decoder has drained, and never resumes. A job attached to it (`job_attach`) is a replay too: its `replay` is its input's, its events go only to the `replay` feed, no transcript of it reaches `transcripts.log`, no mix reads it, and it never resumes. The result is the job's id, as `job_start` answers.  Refused, nothing started: an unknown `capture` is `unknown`, naming the known ones; a `kind` that is no mode row is `<kind> has no handlers`; a handler that is not ready or lacks packets when asked is refused as by `job_start` (`<mode>: handler <id> is unavailable: <reason>`, `<mode>: handler <id> outputs no packet`, `no_handler`); a mode the recording cannot hold is refused by its expansion (`out_of_range` on `bandwidth_hz` for a band narrower than the mode's handler needs, or wider than its channel rate), and one whose band meets none of the mode's `band.range_hz` is `<kind> works <lo>–<hi>[, …] MHz; the recording is <lo>–<hi> MHz` (a recording cannot be moved); and a replay of the same recording (any capture of its set), mode and handler while one runs is a `duplicate` naming the capture asked for: `capture <id> is already replaying as <kind> via <handler>: job <job>`.

- capture: string; an id from `capture list`: its whole set is replayed, from the first capture
- kind: string; a mode row's id (`modes list`), not a built-in job kind
- handler: string or null; a handler id of the mode (`modes list`'s `handlers[].id`); `null` for the handler policy's choice
- packets: boolean; `true` writes the handler's packets to a capture file from the recording's first sample (it must output `packet`); `false` for none

JSON: `{"op":"capture_decode","capture":"<id>","kind":"aprs_decode","handler":null,"packets":false}`

CLI: `zeta capture decode --capture <id> --kind aprs_decode [--handler ID] [--packets]`

### knowledge_lookup

- center_hz: integer (Hz)
- bandwidth_hz: integer (Hz)

CLI: `zeta knowledge lookup --region AU --center-hz 144800000 --bandwidth-hz 12500`

Three providers answer: the built-in seed signatures; `catalogue`, the 594-signal iNTERCEPT catalogue (Apache-2.0; one signature per frequency range of each signal overlapping the band, `bandwidth_hz` its widest bandwidth, `modulation` the first it lists); and `learned`, the operator's accepted signatures (`signature_accept`) whose band overlaps, with `tier: learned`. Every signature also carries `order`, `tone_spacing_hz`, `burst` (`duty`, `burst_ms`, `period_ms`), `sync` (the framing's sync word, hex), `encoding`, `crc`, `confidence` and `tier`, each `null` for the seed and the catalogue (and for what a learned record lacks: a features-only one has no `sync`, `encoding`, `crc` or `decoder`). A learned signature is the operator's own description of a signal heard before, not a decode: `classify` and `identify` label a later match `learned <name>` (layer 2, confidence the record's times its score), which is consistent with that signal, never proof of it. A signature's `decoder` is the id of the mode (`modes_list`) that proves it, the `kind` to start on the band to decode it; `null` means no mode row proves it yet. `classify` runs only the modes with a quick attempt (APRS, POCSAG, ACARS, RDS, AIS, and frame rows with `identify.quick: frame`) as decode-to-identify. The built-in three have no allocations. With `--knowledge-acma` a fourth provider, `acma`, answers: the register's plan services and assignments overlapping the band, each with licensee, site, distance and bearing from the station, power, role, the decoded emission designator and `reach` (whether a signal from that site can plausibly arrive here). It needs the station (`station set`): without one it gives no distances. One register lookup gives the rows, the reach and the answer's `status` and `as_of` (the register data's date): `status` is `ok` (every register query answered, so no assignment means nothing is licensed there), `partial` (`failed` names each register query that failed and why; with `candidates` among them the licences could not be listed, which is not "nothing licensed") or `unreachable` with its `reason` (no allocations at all, which says nothing about the band); `status` and `as_of` are `null` when no provider describes the band.

### origin_lookup

The licensed transmitters a signal may come from, scored against the band and modulation, seen from the source's vantage. Give `job`, or `source`, `center_hz` and `bandwidth_hz`, never both. By job: the band is the job's (a `bits` job's is its capture's, the capture's source the vantage), `modulation` `null` is read from the job (a decoder row's labels, a demodulator's kind, a `bits` chain's demodulator); the answer is published as one `origin` event on the job's event stream and kept as `job_context.origins`. By band: returned only, `modulation` `null` is unknown. A `mix`, `spectrum` or `scan` job has no band.

- job: string or null; an id from `job list`
- source: string or null; an id from `source list`
- center_hz: integer or null (Hz)
- bandwidth_hz: integer or null (Hz)
- modulation: array or null

JSON: `{"op":"origin_lookup","job":"<id>","source":null,"center_hz":null,"bandwidth_hz":null,"modulation":null}`

CLI: `zeta origin lookup --job ID | --source S --center-hz N --bandwidth-hz N [--modulation fm,fsk]`

Which licensed transmitters a signal may come from. Two forms, never both: `job` alone, or `source`, `center_hz` and `bandwidth_hz` together (anything else is refused `origin_lookup: give job, or source, center_hz and bandwidth_hz`). By job: the band is the job's (an attached job's is its input's; a `bits` job's is its capture's, from the capture's source), and `modulation: null` is read from the job: a decoder row's `modulation` labels (`modes_list`), a demodulator's kind (`fm_demod` reads `fm`, `am_demod` `am`, `ssb_demod` `ssb`, `wfm_demod` `wfm`), a `bits` chain's demodulator (`fsk`, `psk`, `ook`), else none. The answer is also published as one `origin` event on the job's event stream (so on its source's feed and in `events.log`) and kept as `job_context.origins` (the last answer only); a `bits` job's `origin` event stays on the job's own stream, not on a radio's feed or in `events.log`. A `mix`, `spectrum` or `scan` job has no band and is refused naming the kind. By band: a band of no width is refused (`origin_lookup: a band of no width`), the answer is returned only, nothing is published or kept, and `modulation: null` reads as unknown; the op never measures, so run `classify` on the band to score against a measurement. The answer: `origins`, at most 50 lit sites best first, each `{allocation, score, agree, terms, confirmed, heard}`: `allocation` the register row as `knowledge_lookup` gives it; `score` 0..1, the sum of `terms` (`width` 0.4 when the row's width is 0.5-1.5 times the band's, 0.2 within 0.25-4, 0.1 for a row with no width, each scaled by how far inside the band the row's centre sits: in full on the band's centre, falling to 0 for a row that only overlaps the band's edge, so the on-channel site scores above its neighbours; `modulation` 0.4 when the designator fits a label, 0 when it disagrees, 0.2 unknown; `reach` 0.2 at the station falling linearly to 0.1 at the reach limit, so the nearer of two otherwise equal sites scores higher, 0 beyond, 0.1 with no distance), 1 once `confirmed` by a decoded identity; `agree` `fits`, `disagrees` or `unknown` (no designator, or no label). `from` is where the query was made from: `{lat, lon, kind: station}` for a local radio or a recording, and for a remote source (a KiwiSDR) with a `position` (`source_list`) `{lat, lon, kind: source, source}`: the rows are cut to the reach around that receiver and the distances and bearings are from it, not the station. `from` is `null` with `from_note` saying why (`no station set`, or `remote source without a position`: no reach cut, the rows nearest in frequency across the region). `providers` names the providers asked, `register_rows` the rows the register returned (`null` with no register attached), `receivers` and `plans` the rows seen and not scored, and `register_status` the status of the register answer the origins were scored from (`{state, reason, failed}`: `ok`, `partial` naming the failed register queries, or `unreachable` with the reason; `null` when no provider describes the band, and in an answer kept before it was carried). The `origin` event carries the answer's fields with `job` and a `summary`: `<n> sites on <MHz> MHz: <licensee>, <site> <d> km <agree> <score>; ...`, or, with no site lit, `register unreachable: <reason>`, `register could not list licences: <reason>; partial answer: <query>, ... failed` (its `candidates` query failed), `no licensed transmitter on <MHz> MHz`, `register gave no rows`, `no register provider`. A job whose mode row declares `subject.identity` (`aprs_decode`: `src` against the `callsign`, the SSID stripped) confirms a lit site itself: when one of its events carries a callsign equal to a kept origin's (trimmed, case ignored), that origin gets `confirmed` `{field, value}` and score 1, `job_context.origins` is updated and the `origin` event is published again with `summary` `confirmed <value>: <licensee>, <site>`; a callsign matching no origin changes nothing (many stations share a channel), and only origins already kept are matched, so look the job up first. `heard` is `null` or `{last_ns, grade}` and is set only for a job whose mode row declares `subject.station` (`vdl2_decode`: a ground station's own frames, named by `icao`, and any other frame's `dst` names the station it is sent to; `acars_decode`: an uplink is a station's own frame, anonymous `*`). `grade` is `from` when any station's own frame was heard on the channel, else `to` (an aircraft heard here is talking to a station of that address). A heard site means the register's transmitter is on air on this channel, or an aircraft heard here is talking to a station of that address; the site is consistent; which co-sited transmitter it is stays unknown; it is still not `confirmed`, and the score is never changed by it. `from` is stronger evidence than `to`: the station itself was received, not only an aircraft addressing it. The answer and the `origin` event also carry `stations`, the job's tally `{key: {from, to, first_ns, last_ns}}` (frames the station sent, frames addressed to it; `last_ns` is stream time, the wall time on a live radio), and the `summary` then reads like `2 ground stations on <MHz> MHz: <key> heard <n> frames, <key> addressed by <n> frames; <sites>`; the anonymous station `*` (a row whose uplinks carry no station identity, ACARS) reads `uplinks heard <n> frames`, and a count of one reads `1 frame`. The tally is flushed at the run's end and seeded at launch, so a restart continues the counts. The same tally is kept as `job_context.stations`, written at once on a new station or a station's first own frame and otherwise about once a minute, whether or not a lookup has run, and a fresh `origin_lookup` with `job` answers `heard` and `stations` at once; the band form has no job and reports neither. A lit site is a hypothesis, not an identification: report it as "consistent with Example Water Authority at Example Hill", never "it is", unless `confirmed`.

### register_site

Every channel a licence register holds at one of its sites, read from the register now.

- provider: string; a register's provider name (`acma` with `--knowledge-acma`)
- site_id: string; an allocation's `site_id` (from `knowledge_lookup` or `origin_lookup`)

JSON: `{"op":"register_site","provider":"acma","site_id":"<id>"}`

CLI: `zeta register site <provider> <site_id>`

The answer holds `provider`, `site_id`, `channels` by frequency (each `channel` (`center_hz`, `bandwidth_hz`, `role` `tx` or `rx`, `emission` as the register stores it), `licence_no` and `licensee`, `null` where the register holds none) and `as_of` (the register's data date). It reads the register live, every call, so it costs a register lookup and needs the register attached (`--knowledge-acma`, provider `acma`). `site_id` is an allocation's `site_id` (from `knowledge_lookup`, `origin_lookup`, or a register answer's candidate `site.id`); never invent one. An empty `channels` means the register holds nothing at that id, not that the register failed. A provider the node does not have is `unknown` (field `provider`, `known` listing the registers it has); an id that is not a register id (1-64 letters, digits, `/`, `_`, `.` or `-`) is `other` beginning `site_id:`, refused before the register is asked; a register that fails or does not answer is `other` beginning `register_site: <provider>:` with the reason: report it as the register being unreachable, never as an empty site.

### modes_list

The decoder modes the node knows, one row each (`modes/*.json` built in, then the operator's `--modes-dir`), sorted by id, narrowed to `family` and `state` when given (`null` for any).

- family: string or null
- state: string or null
- role: string or null

JSON: `{"op":"modes_list","family":null,"state":null,"role":null}`

CLI: `zeta modes list [--family F] [--state S]`

The decoder modes the node knows, one row each: `id` (the `kind` a decoder job starts with), `name`, `family`, `band` (`bandwidth_hz` the decoder expects, well-known `centers_hz`, `min_hz` the narrowest band it accepts or `null`, `range_hz` where identify and classify try it, one span `[lo, hi]` or a list of spans `[[lo, hi], ...]` (a row of one span is always written `[lo, hi]`), or `null` for anywhere), `modulation` (the layer-1 labels it presents as), `decoder_kind` (`graph`, run in-process, `program`, an external decoder, or `frame`, an in-process frame chain; `null` for a row with no decoder of its own, which only a handler file's entry runs), `file` (`modes/<id>.json` for a built-in row, the path for an operator row), `program`, `checked` (UNIX seconds at which `zeta modes check` last passed the row on this host with every handler found; `null` if never, or for a graph or frame row with no handlers), `subject` (the event field naming what events are about, its table columns and how the page folds it; `null` for none), and `state` ready|broken|unavailable with `reason` (`null` when ready). A broken row's `file` is the file to fix and its `reason` names the field (`<field>: <error>`); an unavailable one names the program it lacks. A ready row may list `missing`: the optional programs it runs without, each `<program>: missing (<hint>; <url>) — <what is lost>` (`voice silent` for a vocoder), `[]` when it lacks none. `outputs` lists the stream kinds a job of the row emits (`event`, `audio`, `packet`; a row listing `audio` gets play and Transcribe on the page, and `job_attach` may attach `transcribe` to its job; a row listing `packet` publishes each frame it decodes as a packet beside its event (an AX.25 frame for `aprs_decode`, the frame's bytes for a frame row), the frames a `job_attach` of `packets` captures; a graph row's are its terminal stages', a program row's `event`, a frame row's `event` and `packet`; empty for a broken row). `handlers` lists every handler of the mode, the row's own first (`builtin` for a graph or frame row, named `built-in`; a program row's first program's file name, `dump1090`; no own handler for a row with no decoder of its own), then each handler file's (`--handlers-dir`) by id: each has `id` (what `job_start`'s `handler` and `handler_policy_set` take), `name`, `in_process`, `outputs`, `state` with `reason`, `missing`, `program`, `checked` (a handler file's from `zeta modes check --handler <id>`), `file` and `extra` (the event fields that handler adds beside the row's). `handler` is the one the policy would pick now (`null` when none is ready). With more than one handler the mode's own fields summarise them: `state` is `ready` when any handler is, `program`, `reason` and `missing` describe the handler `handler` names (the row's own when none is ready), `outputs` is the union over the ready handlers (a capture is possible on the mode, not on every job of it: a job's outputs are its own handler's), and `checked` is the row's own. A row with no decoder of its own (`decoder_kind` `null`) is `ready` while one of its handler files' handlers is, and is otherwise `unavailable` with `reason` `no decoder of its own, and no handler for it is ready` followed by `; <id>: <reason>` for each of its handlers (the missing program, say); its `outputs` are its ready handlers' (`[]` with none), and a start of it always runs, and records, one of them. On the CLI, `zeta handlers list` prints one line per handler of each mode, `<mode> <id> <state> <outputs>`, then `checked=<UNIX seconds>` when a check passed it: this machine's rows and handler files, or with `--node` the serving node's (its programs and checks). `voices` lists the voices a job of the row has beside its main audio stream, each on an audio stream of its own (a DMR row's `slot1` and `slot2`): what `job_attach`'s `stream` may name, and the rows `job_start`'s `audio_policy` applies to; `[]` for a row with one voice. `access` is `'restricted'` on a row whose events carry content a later access control may gate (pager text); such events carry `access: 'restricted'`. `content` is `'network_traffic'` on a row that carries data-network traffic and `null` on the rest: it says what the row carries, nothing reads it yet, and it is not put on events; a job of such a row has `content` in its `job_context` from launch, and a packet capture of its job records it. `family` (and the `family` filter) is one of `tv`, `broadcast`, `aviation`, `maritime`, `satellite`, `two_way`, `cellular_rail`, `pagers`, `iot`, `weather_science`, `amateur_digital`, `amateur_voice`, `hf_utility`, `general`. On the CLI, `--family` and `--state` narrow the list. `zeta modes check [ID] [--strict] [--handler H]` (local only, not with `--node`) runs each row's test on a node over a synthesised capture and prints `<id>: ok`, `<id>: fail: <reason>` or `<id>: skipped: <reason>` (no test, or the program missing: `--strict` makes that a fail); it exits 0 when no row failed. With `--handler H` it runs the test of each mode that has handler `H` (of `ID` only, when given) by a job of that handler, a handler file's printed and recorded as `<id>@<H>`. A row with no decoder of its own is checked by the handler the policy picks, printed and recorded the same way, and is `<id>: skipped: no decoder of its own and no handler ready` when none is ready.

Frame rows: a row with `decoder.kind: frame` decodes framed bursts in-process, with no program. Its `decoder` names the demodulator, `demod: {modulation, symbol_rate_baud, order, tone_spacing_hz}` (`modulation` `fsk`, `psk` or `ook`; `order` 2 when left out, 2 or 4 for fsk, 2, 4 or 8 for psk, 2 for ook; `tone_spacing_hz` `null` for the demodulator's own estimate), the `framing` (the `frame_decode` stage's params, under Stage kinds: sync, length, CRC, line code, whitening, bit order) and the `parser` (`opaque`, the default: the frame's bytes as they are). A job of the row runs `channel → resample → <demod> → clock_recover → slicer → frame_decode` on a band no narrower than `band.min_hz` (else `band.bandwidth_hz`) and publishes one event per cut frame (`sync`, `length_bytes`, `bytes` in hex, `crc_ok`, `payload`) under the row's `protocol` and `summary`; `clock_recover`'s `timing` events go on a separate output. With `identify: {proof: field, field: crc_ok, quick: frame}` a CRC-clean frame proves the row: `classify` runs the chain over the span (evidence `frame <n> B, <crc> ok (<ok>/<frames>)`; a framing without a `crc` never proves) and `identify` runs the row as a child job. `quick: frame` is refused on any other row, and a frame row's `quick` is `frame` or `null`. A bad framing leaves the row broken naming `decoder.framing.<field>`. `zeta modes check` checks a frame row over the `framing` synthesiser family (`test: {kind: synth, family: framing, modulation, symbol_rate_baud, deviation_hz, frames, body_bytes, framing, repeat, expect: {crc_ok: true}, within_ms}`).

### set_list

A set that does not parse or validate is `broken` with its `reason` (`<field>: <error>`, e.g. `members[0].params.hold_ms: ...`) and never stops the node; an operator set with a built-in's `id` replaces it, and a broken one that meant to is listed as `<id>@<file name>`, the built-in staying in force. An instance none of whose jobs runs reads `null`.

JSON: `{"op":"set_list"}`

CLI: `zeta sets`

Read it before naming a set: set ids, their roles (`radios`, each with a `note` saying what radio it needs) and members come from here, and it only reads. ### set_start

Start a named set from `set_list`: each member on the source its role is mapped to, as `plan_start` does for one source, under one lease decision per source. In this order: (1) everything is checked first (an unknown `set` or member id is `unknown`; a broken set, a role a chosen member uses left out of `radios` (`radios.<role>: unmapped`), or two roles on one source whose members that source cannot capture at once are `other`; an unknown source is `unknown` on `radios.<role>`; a set that already runs on another mapping is `other`: `set_stop` it first); a role mapped to `null` gets, roles in the file's order, the first source in `source_list` order that `source_free` lists for the band bounding the role's members and no other role of the request names (while the set runs, the source it runs that role on), none being a `conflict` (`source` the first source covering the band, `holders` every covering source's holders, `options` first `radios.<role>: no free source covers <center> Hz ± <half> Hz; busy: <id> (holders [...]), ...`, then `unpin source <id> (source_unpin)` for each pinned one), or `other` with that text when no source covers the band at all; a member whose kind is a mode row that is not ready (`refused` `other`, `<state>: <reason>`), or a kind this node does not know (`refused` `unknown` on `members[<i>].kind`), or a `watch` member whose `params.modes` names a row this node cannot run or one wider than its band (`refused` `other`, `members[<i>].params.modes[<j>]: ...`), is set aside and the rest go on (a role left with no member is neither tuned nor in the result); a `plan_start` member whose `attach` stage is not ready starts without it and a warning says so (`members[<i>]: <attach>: <reason>; started without attach`); (2) the band bounding each source's members is checked against the source's ranges (`out_of_range` on `radios.<role>`); (3) the gates of every source in use are taken in source-id order and held to the end; (4) a member (a `plan_start` member's channel) whose identical rigid job already runs is `existing`, a `watch` member only when that watch's `detect` params are the member's `params` (a key either leaves out compared at its default), a watch on its band with another policy being `other` (`watch <id> holds this band with other policy; stop it or graph_put it`) with nothing started; a `watch` member starts with its `params` on its `detect` node, with no restart; (5) the `replace` jobs, each holding one of the sources in use, are stopped; (6) every source is decided before any is tuned: a `conflict` on any source is the whole answer, naming the role and the source (`radios.<role> (<source>) is held by [...]`), with nothing tuned or started anywhere; then each source is leased (and tuned when needed) for its bounding band; (7) the members start source by source in the set's role order, each inside its capture, a member's own failure being its `refused` entry; (8) the instance is recorded (`set_list.running`), and `attach` follows each started channel. The result: `radios` (each role's `source` and `capture`), `started` (`member`, `channel` for a plan member, `center_hz`, `job`, `attached`, `attach_error`), `existing` (`member`, `channel`, `center_hz`, `job`, `attached`), `refused` (`member`, `channel`, `error`) and `warnings`. Running the same request twice starts only what is missing.

- set: string; an id from `set_list`
- radios: object; each role of the set (from `set_list`) to an id from `source list`
- members: array or null; member ids of the set (strings), `null` for every member
- replace: array; ids from `job list` (strings), `[]` for none

JSON: `{"op":"set_start","set":"airband","radios":{"second":"<id>","wide":"<id>"},"members":null,"replace":[]}`

CLI: `zeta set start --set airband [--radio wide=<id>,second=<id>] [--members acars,adsb] [--replace ID,ID] (no --radio: every role null, the node picks)`

One call starts a whole set; never start its members by hand. Map every role the chosen members use to a source from `source_list` that can capture the role's band (the role's `note` says what it needs), or to `null` to let the node pick the first free one, and report the picks from the result's `radios`. A watch member on a band another watch holds with another policy is `other` naming that watch: report it, never stop or `graph_put` that watch unasked. A `conflict` names the role and the source with the holders, and nothing started anywhere (a `null` role the node could not fill too, `options[0]` `radios.<role>: no free source covers ...`): report it; the operator decides, and `members` narrows the next request to what is free. `replace`: as on `job_start`, never a job the request did not name. A `null` role keeps the source it picked while the set runs. Read the four lists: `started`, `existing` (already running, skipped), `refused` (a member this node cannot run, `unavailable` or `unknown`, such as a decoder whose program is missing, or a start that failed; the others went on) and `warnings` (repeat them). A set's watch member decodes every channel of a span: its `job_context.watch` (`cap`, `known`, `cooled`) and `decoding` events say how, see "Decoding every channel of a band" in the field craft. Run it again to complete a partial set: running members are `existing`.

### set_stop

Stop the jobs of a set's running instance that still run, those on a radio first and then those attached to them, and drop the instance. Jobs the instance did not start are left alone. The result lists `stopped`, `ended` (jobs that no longer ran when asked, such as one stopped by hand) and `failed` (`job`, `error`; the others go on). When a stop fails the instance is kept, so a second `set_stop` can finish it. A set that does not run stops nothing.

- set: string; an id from `set_list`

JSON: `{"op":"set_stop","set":"airband"}`

CLI: `zeta set stop --set airband`

Stops only the jobs the set's instance started; jobs started by hand on the same radios keep running. Stopping a set is the operator's decision: use it only when the request names the set, or you started it whole in this run (a `set_start` that answered `existing` members leaves `set_stop` to the operator). Through `ask` the run must allow stops, else the call is refused as `not_allowed`: report that, do not retry. Report how many stopped, those that had already `ended`, and any `failed`; a failed stop keeps the instance, so a second `set_stop` finishes it.

### modes_show

One mode's row as loaded, with its `state` and `reason`.

- id: string; an id from `modes list`

### handler_policy_set

Rank the handlers of mode `mode`, or with `mode: null` of every mode (the node-wide ranking), for the policy that picks a mode's handler (`modes_list`'s `handler`): among the mode's ready handlers, one lacking an output the start needs is passed over; then the mode's ranking leads, then the node-wide one (only for a handler giving every output the row's own decoder gives: one giving less, an events-only handler on a voice mode, is ordered as if it did not name it), then an in-process handler goes before a program, then the row's own before the handler files' (by id). `order` lists handler ids (`modes_list`'s `handlers[].id`), first preferred; an id it leaves out goes after those it names, and an empty `order` clears that ranking. A ranked handler that is not ready is passed over, never an error. Checked before anything is written: `mode` naming no mode is `unknown` on `mode`, and an id the mode (with `mode: null`, every mode) has no handler of is `unknown` on `order`, listing the ids it has. - order: array; handler ids of the mode (`modes list`'s `handlers[].id`), first preferred; `[]` clears the ranking

### classify

Run every registered classifier over the selection's band and span of the source ring (no upstream features).

- selection: object (Selection: source, span{start_ns,end_ns: integer (ns since epoch)}, center_hz, bandwidth_hz)

JSON: `{"op":"classify","selection":{"source":"<id>","span":{"start_ns":1760000000000000000,"end_ns":1760000001000000000},"center_hz":144800000,"bandwidth_hz":12500}}`

CLI: `zeta classify --source <id> --start-ns 1760000000000000000 --end-ns 1760000001000000000 --center-hz 144800000 --bandwidth-hz 12500`

Layer 1 labels the measured band (`wfm`, `fm`, `am`, `ssb`, `fsk`, `psk`, `ook`, `carrier`, `noise` or `unknown`; an `ssb` label's evidence gives the dial frequency). Layer 2 first sweeps the decoder modes (`modes_list`; the demodulator rows, `role: demodulator`, are never in it) as decode-to-identify: each ready or unavailable row is scored against the layer-1 measurement (0.4 for the measured centre within `band.bandwidth_hz` of one of its `band.centers_hz`, or, for a row that lists no centres, inside one of its `band.range_hz` spans, or always when it has neither; a row with a `range_hz` is not tried at a centre outside every span and away from its centres; 0.3 for a measured bandwidth within 0.5-1.5 times its `band.bandwidth_hz`; 0.3 for the layer-1 label in its `modulation`; plus its best catalogue score, below) and the best 5 are considered in score order (ties by `identify.priority`, highest first, then `family`, then `id`); a graph row with no quick attempt (`m17_decode`) is not considered at all, since only `identify` can try it. A row whose `identify.when_named` is true (`dvbs_ip_decode`) is passed over by this sweep, by `identify`'s own choice of rows and by a `watch` with default modes, unless the caller names it (a `watch`'s `modes`, a set or plan member, or the `candidates` a watch hands its identify run); a job started by hand is unchanged. The result is `{labels, tried, allocations, origins, register, features, choice}`; `origins` is `origin_lookup`'s answer for the band, scored on the measured layer-1 label (`[]` when none), and `register` the register's whole answer for the band (`null` when no provider describes it), all three read from one register lookup per run. `register` holds `provider`, `region`, `status` (`state` `ok`; `partial`, with the queries that failed in `failed`; or `unreachable`, with its `reason`), `as_of` (the register's data date: quote it), `plan` (the band plan segments and their services), `candidates` in rank order (each a `device`, its `site`, `licence` and `holder`, the `geometry` from where it was heard (`distance_km`, `bearing_deg`, `horizon_km`) and the `expected` reception (path `mode`, `level_dbm`, `in_range` `yes`, `no` or `possible`, and the `unknown` inputs), with `related` channels for the top three, and `network_sites`, how many of the answer's sites send the same thing on the frequency: over 1 is a same-frequency network, whose sites the register cannot tell apart, so name the count and the site's `polarisation` instead of naming one site as the source), `area_candidates` (area-wide licences), `matched`, `truncated`, the `assumptions` the estimate used, and `verdict`, the node's reading of the answer against the measurement: `kind` `agrees` (a candidate in range fits the measured width and modulation), `disagrees` (candidates are in range and none fits; the summary names what is licensed and what was measured; in an `identify` verdict whose decoder proved, the comparison is with what was decoded instead: the row's `modulation`, and the width the proving event names as `bandwidth_hz` when it has one, since the first-layer measurement has no label for many signals and under-reads a wide flat one), `unlicensed` (no candidate in range; the summary gives the band's primary services and how many area-wide licences cover it) or `unknown` (the register could not be asked: nothing is known, which is not the same as nothing licensed); `weak` is true when range cannot be bounded (a skywave band, or no position to measure from), and `summary` is one plain line. An `expected` level is the register's estimate from its records and the `assumptions`, never a measurement: say "expected about -95 dBm". The node measures only a signal-to-noise ratio, so the verdict does not compare levels. A row's `power_w` is the transmitter's power and `eirp_w` its radiated power, each `null` when the register holds none (a broadcast licence holds only the EIRP: say "50 kW EIRP", never "0 W"); `knowledge_lookup` and `origin_lookup` rows carry both, with `expected_level_dbm`, and sites that tie on score are ordered by it, strongest first. `tried` lists those 5 as `{mode, score, outcome}`, `outcome` one of `proved` (its quick decode passed its CRC/BCH check), `no_frame` (tried, nothing decoded), `skipped_span` (the span is shorter than the row's `identify.min_span_ms`, 1000 ms for the built-in rows), `skipped_quick` (the row has no quick attempt: a program row such as `adsb_decode` is tried only by identify, never by `classify`; use `adsb_decode`), `skipped_band` (the selection is narrower than the row's `band.min_hz`, else its `band.bandwidth_hz`: `rds_decode` needs 150000 Hz, `adsb_decode` 2000000; on a whole block the measured occupied band counts, read as 150000 Hz once it reaches 100000) or `unavailable` (its program is missing). A proof adds a layer-2 label named by the row's `label` (`APRS`, `POCSAG`, `ACARS`, `RDS`, `AIS`) at confidence 1.0, evidence `decode <mode>: ...`; a protocol is labelled only then. A `no_frame` does not prove the protocol absent: the span may have held no frame. Layer 2 also adds up to three signal names from the catalogue (evidence `catalogue <id>: ...`), scored 0.4 for the measured centre lying in one of the signal's frequency ranges (required), 0.3 for a matching bandwidth (required for signals wider than 50 kHz) and 0.3 for a matching layer-1 modulation. Layer 3 is an empty slot. `features` is layer 1's measurement as fields (`bandwidth_hz`, `center_hz`, `snr_db`, the burst shape, `symbol_rate_baud`, and when measured `power99_hz`, the width holding 99 % of the power, `audio_rms_hz`, the audio's rms deviation, and `ssb: {sideband, dial_hz}`); `null` when layer 1 could not measure the band. `choice` is the one job the band answers, `{job, row, step, settled, evidence, runner_up, could_prove, not_tried, reason}`: `job` is `{kind, center_hz, bandwidth_hz, params}`, what to `job_start` (`kind`, centre and width as given; `params` holds `deviation_hz`, `sideband` and the row's other defaults), `row` the mode row it is of, `step` 1, and `settled` one of `proved`, `best_guess` or `cannot_tell`. A row a quick decode proved wins (`settled: proved`; the row's own width, on the measured centre). Otherwise the demodulator row whose `modulation` holds the label is the job (`settled: best_guess`): `fm_demod` for `fm` and for an `fsk` no wider than 25000 Hz, `wfm_demod`, `am_demod`, `ssb_demod`, each sized and centred by its `band.width_rule` and given its `decoder.params` (`modes_show <id>`). With no demodulator for the label (`ook`, `psk`, a wider `fsk`), the best ready decoder row that fits is the job, still `best_guess`: say it is not proved. Otherwise it cannot tell: `job: null`, and `reason` says why (`the band holds noise only`, `no row serves <label>`, `layer 1 did not measure the band`). The centre is the measured one (the dial for `ssb_demod`), never a channel raster's; a channel plan of the station's region at the centre gives `fm_demod` its deviation, and the channel's width when the measured width is under the row's floor and not trusted. `evidence` holds `<source>: <line>` lines: `layer 1: <label> <width> Hz`, `plan: <id> deviation <d>`, `decode <row>: <summary>`, `catalogue: <name>` for a catalogue entry the row lists (a catalogue name only ranks: it never proves a row nor overturns the label). `could_prove` lists, in score order, the ready decoder rows that fit the label, the band and the width and could still prove it (start one, or `identify`, to try); `runner_up` (`{job, row, evidence}`, or `null`) is the first of them when it scores within the weights table's margin of the demodulator, else the next demodulator row; `not_tried` lists `{row, reason}`, a fitting row that is not ready as `not tried: <row> is not ready: <reason>`. Report a `best_guess` as what to listen with, never as an identification. `capture_classify` answers `choice: null`. On the CLI, `zeta classify` prints `choice: <kind> <center> Hz <width> Hz (<settled>, step 1)` or `choice: cannot tell: <reason>` on stderr, before the JSON answer. A span older than the source's ring fails `ring` with `detail.cause` `too_old` and `detail.earliest_ns`, the ring's first retained sample (`source_list` gives its `ring.seconds`): re-issue on a span at or after it, never guess. A span that crosses a gap in the capture fails `ring` with `detail.cause` `gap` and `detail.gap_start_ns`, `detail.gap_end_ns`: re-issue on one side of it.

## Mode rows

The built-in decoder rows with notes (`modes_show` has every row in full; an operator row's notes reach `modes_show` only):
- `acars_decode`: A downlink (a digit block id, downlink true) whose text is a position report (labels H1, 80, 16, 3L, QQ) carries lat, lon, sometimes alt_ft, and a position: the aircraft's own report, typically a few minutes old by the time it is relayed. Uplinks are never parsed. An uplink lights the register's transmitter sites on the channel as `heard`; `job_context.stations` counts uplinks under `*`.
- `ais_decode`: AIS on 161975000 Hz (channel A, 87B) and 162025000 Hz (channel B, 88B), 25000 Hz band, one job per channel. A moving class A ship reports every 2-10 s, one at anchor every 3 min, class B every 30 s; names arrive in separate static messages, so a vessel's row fills over a few minutes.
- `am_demod`: The AM demodulator a choice falls back to when no decoder is proved: it turns the signal to audio and proves nothing.
- `aprs_decode`: APRS at 145 175 000 Hz in AU, 144 800 000 Hz in EU, 144 390 000 Hz in the US, 12 500 Hz band (identify tries it on 2 m only from half a channel below the lowest centre to half a channel above the highest, and on 70 cm in the catalogue's 430.3375-434.6625 MHz: its band.range_hz); one job hears every station on the channel. Positions in the three common formats (uncompressed, compressed, Mic-E) land on the map; objects and items are named, not placed.
- `ble_decode`: Bluetooth Low Energy advertising (LE 1M PHY, GFSK), decoded by OnAir's receiver through the onair-rx handler; the row has no decoder of its own, so only a handler runs it. One job reads one advertising channel: start it on 2402, 2426 or 2480 MHz (channels 37, 38 and 39) with a band of 2 MHz; the handler takes 4 MHz of IQ (OnAir's own minimum, a decimation to 4 samples a bit), so the node resamples to it. Each event is a frame: `home_id` (8 hex digits, the network), `src` and `dst` (node ids as integers; 255 is the broadcast; a multicast has no `dst`), `frame_type` (`singlecast`, `multicast`, `ack`, `routed`), `rate_bps` (9600, 40000 or 100000), `freq_hz`, `secured` (an S0 or S2 payload, which stays encrypted) and `len`. OnAir's packet carries the data rate and not the channel, so `freq_hz` is inferred from the region and the rate and is null where the band holds two channels of one rate (Japan, Korea). Nothing is decrypted; the MPDUs (a byte for the data rate, then the frame) go to a packet capture. OnAir writes them as link type 148 (USER1), which the node names for Mode S, so the entry remaps them: the node's captures carry Z-Wave as USER2 (149), and Wireshark needs its DLT_USER table pointed at OnAir's Z-Wave dissector (`onair-rx --lua`) for that type. Ranges and bands: the regions (EU, US, ANZ, HK, IN, RU, CN, IL, JP, KR) and so the ranges 865 to 870 and 908 to 927 MHz are the channel tables of the ITU-T G.9959 regional frequencies as OnAir carries them; the channels at 9.6, 40 and 100 kbit/s fit a 100 kHz band. Listing bar: measured on the build host (12 cores) through a scratch node's release build, 30 s of the generated capture looping on a file source and fed in real time; the job skipped no input, onair-rx used 0.03 of a core and the node 0.08 of a core (load average 4.4 to 3.8, with another build running).

## Field craft

Measured facts first, then method. Verify against the node's `knowledge lookup` before relying on any of this.

### Where to look

- Radiosondes: 400-406 MHz. RS41 is GFSK at 4800 baud, about 10 kHz wide.
- APRS: 145.175 MHz in AU, 144.800 MHz in EU, 144.390 MHz in the US. AFSK at 1200 baud. Identify tries `aprs_decode` on 2 m only in 144.38375-145.18125 MHz (the centres ± half its 12.5 kHz channel), not on the rest of the band, and on 70 cm in the catalogue's 430.3375-434.6625 MHz (its `band.range_hz` lists both).
- POCSAG: the preamble is 576 bits of alternating 1/0, then the 32-bit sync word 0x7CD215D8. Common rates are 512, 1200 and 2400 baud.
- ADS-B: 1090 MHz, PPM at 1 Mbaud, 112-bit extended squitter.
- AIS: 161.975 MHz (channel A, 87B) and 162.025 MHz (channel B, 88B), worldwide. GMSK at 9600 baud, 25 kHz channels; HDLC frames with a CRC-16.
- Digital video links (WHDI, WiFi HDMI kits, DJI): a 20-40 MHz OFDM carrier at 5 GHz with no line structure; `video_decode` never locks on it. Report it as not yet decodable; do not try another demod. That is a different answer from `insufficient bandwidth`, which names the source's cap.
- MeshCore: LoRa around 915 MHz in AU and 869 MHz in EU, 250 kHz wide. Not decodable without the network key; classify and report, do not try to decode.
- Licensed bands: with the ACMA register attached (`--knowledge-acma`) and a station set (`station_set`), call `knowledge_lookup` on the band first, before demodulating anything. Report the nearest `tx` assignment's `licensee`, `site`, `distance_km`, `power_w` and decoded emission, and the answer's `as_of` (the register is as fresh as its last sync); say so when `as_of` is `null` or old. Read its `status` before reporting an empty band: `unreachable`, or `partial` with `candidates` among its `failed` queries, means the register could not list licences, which says nothing about the band; only an `ok` answer with no assignment says nothing is licensed there. An assignment whose `reach` says the site cannot plausibly arrive here is context, not an explanation. A register match is a hypothesis about who transmits, never a proof of what a signal is: only a CRC-clean decode proves a protocol. For a running job, ask `origin_lookup` with its `job` before guessing who transmits: it scores the register's rows on the job's band (width, the modulation the job implies, reach), publishes one `origin` event and keeps `job_context.origins`, and the page lights the sites on the map. Report a lit site as "the register's Example Water Authority at Example Hill is consistent with this signal", never "it is", and quote its `agree` (`fits`, `disagrees`, `unknown`). A site with `heard` (a VDL2 or ACARS job: a station's own frame, grade `from`, or a frame addressed to a station, grade `to`; `job_context.stations` counts them) is consistent with the channel's decode and still not identified: say "consistent with, and heard", and treat `from` as the stronger. A site `confirmed` by a decoded identity (an APRS packet whose source callsign equals the register's callsign) is still a register match, so say "consistent with, and the packet's callsign matches", not "it is". The register may lack callsigns: the acma provider then reads them as null and nothing is ever confirmed, so an unconfirmed site is the normal case. An `origin` summary of `no licensed transmitter on <MHz> MHz` is a finding (the register lists none there); `register gave no rows` and `no register provider` are not (the register was empty or absent), nor are `register unreachable: ...` and `register could not list licences: ...` (the register could not be asked, or could not list its licences). The band form (`source`, `center_hz`, `bandwidth_hz`) answers without publishing or keeping anything, and with no measurement it scores the modulation as unknown: run `classify` first when the label matters. `origin_lookup` refuses both forms at once or neither, a job kind with no band (`mix`, `spectrum`, `scan`), a source the node does not have in the band form, and a band of no width. A `bits` job's `origin` event stays on the job's own stream, not on a radio's feed or in `events.log`: read the op's answer, or `job_context.origins`, rather than waiting on a feed. A remote source such as a KiwiSDR is queried from its own position (reported by the Kiwi, else `--source-position`), so the distances and the reach cut count from the receiver, not the station; with neither, `from_note` says `remote source without a position` and the rows are not cut by reach. `classify` and an `identify` verdict also carry `register`, the register's whole answer for the signal with the node's `verdict` on it (`agrees`, `disagrees`, `unlicensed`, `unknown`, and `weak` where range cannot be bounded): quote its `as_of` beside it, and give a candidate's `expected.level_dbm` as "expected about -95 dBm", the register's estimate from its records and the stated `assumptions`, never a measured level. Report `agrees` as "consistent with the register's Example Water Authority at Example Hill", and `disagrees` as what the register licenses there beside what was measured. An `unlicensed` verdict is not evidence of wrongdoing: class-licensed devices and mobile or portable stations are not in a register by site, so say "nothing in the register in range", never "an unlicensed transmitter". `unknown` means the register could not be asked or could not list its licences (`register unreachable: ...`, `register could not list licences: ...`), which says nothing about the band.

### Decoding APRS and reading measurements

To decode APRS from a source, start the job and tail its events in one call: `zeta job start --kind aprs_decode --source S --center-hz 144800000 --bandwidth-hz 12500 --then-tail 1,5000`. It prints `[job_result, frames_result, {"stopped": true}]` (the job is stopped after the tail; add `--keep` to leave it running); each frame's `payload` is one decoded packet (`src`, `dst`, `info`, `fcs_ok`). A packet with a position in any of the three common formats carries `lat`, `lon`, `alt_m`, `course_deg`, `speed_kt` and `position`, so the station lands on the map and in the Subjects table; `data_type` says what the packet was. An empty frame list means no packet arrived within the timeout, not that none exist. Exit 2 with `[job_result, job_record]` means the job is not running: read `state.reason` (e.g. a stage that failed on the source's blocks). A `measure` job emits one event per second of IQ: `center_hz` and `bandwidth_hz` are the occupied band (spectrum bins at least 6 dB above the noise floor, the 15th-percentile bin of the band), `snr_db` is the peak above that floor, `burst` is true when the loudest 10 ms is more than 3 times the median 10 ms power, `symbol_rate_baud` is the keying rate when a symbol-rate line stands out and `null` otherwise, and `label.name` is one of `noise` (SNR under 6 dB), `carrier` (steady envelope, no modulation), `fm` (steady envelope with deviation), `fsk` (two tones 500-3000 Hz apart, on RF or in FM audio), `psk`, `ook` or `unknown`. Report `unknown` as unknown, with the measured fields. A `measure` event with `partial: true` covers a window cut short by a gap, lag or retune and spans only its samples; `partial: false` is a full second. `classify` and `measure` analyse only the selection/job band (a `measure` event's `center_hz` is absolute RF, within that band); `spectrum` covers the whole source band. A `spectrum` event is one row of power-averaged spectrum (20 per second of signal time) with `size` bins lowest frequency first, `bin_hz`, `center_hz` and the levels quantised as `q` (0-255 per bin): the dB of bin k is `floor_db + q[k] * step_db`; `floor_db` sits 5 dB under the row's 2nd-percentile bin, so a `q` near 10 is the noise floor and 255 means at least 127.5 dB above `floor_db`. A row may carry `masked: [[lo, hi], ...]`, bin index ranges (`lo` inclusive, `hi` exclusive) the receiver could not see honestly (a scan step's DC notch, its band edges): read them as no data, never as a quiet band; the `q` under them is present only so an older reader sees a whole row. A scan's steps alternate between two grids a quarter step apart, so a step's notch and its edges in one sweep fall a quarter of the way into a row of the next, clear of its mask: judge a frequency from two consecutive sweeps. On a local hardware receiver a `measure` job ignores the bins within 25 kHz of the capture centre (`job context` shows `measure.dc_mask_hz`, 0 when none), unless the box is centred on it (a lone job's capture: then the box is measured as today), so a box that sits beside the DC spike in a wider capture measures the signal.

A `measure` event also carries the burst features, always: `duty` (the share of the window the signal is on), `bursts`, `burst_ms` and `period_ms` (`null` when there is no burst train), `power99_hz` (the width that holds 99 % of the excess power over the noise floor of the band around the strongest line: bins at least 3 dB over the floor, a separate neighbour not counted; `null` when no bin clears that, and absent from an older node), and, when a keying line or tone clusters stand out, `order` (the FSK or PSK order: 2, 4, 8) and `tone_spacing_hz`. When the window holds a burst train (at least two on-runs, or one of 3 ms or more, with the signal off between them: the quiet chunks within 6 dB of the in-band noise floor, so clicks over a continuous signal do not count) the band, SNR, label, `symbol_rate_baud` and `order` are measured over the on-time only, not averaged into the silence. So a low `duty` means the features were measured over the bursts: report the burst timing (`duty`, `burst_ms`, `period_ms`) with them and say the measurement is over the bursts, never that the band is quiet or `noise` on the strength of a whole-window average. `symbol_rate_baud` comes, for on-off keying whose envelope sits at two levels, from its run lengths (the chip: the unit every on and off run is a whole multiple of, so pulse-width keying such as a 433 MHz remote reads its chip rate, not its bit rate; fitted over the whole window even when it gated as bursts, in the measured band or, for a weak signal whose measured band is mostly noise, a narrower one, and such a window labels `ook` with no tones), else from a cyclostationary line (the |x|^2 spectrum, or the envelope edges for on-off keying); `symbol_rate_line` says which (`runs`, `cyclo` or `keying`; `null` without a rate). A run-length rate is dropped for the other lines when its off runs are signal rather than the noise (a PSK burst's envelope dips), twice its band holds FSK tones, or the band carries a PSK order. A rate is a hypothesis about the keying rate, and a short burst may give none (`null`).

### Decoding pagers, aircraft and FM data

Each of these is a mode row: `zeta modes list` gives its id (the `kind` to start), the `band` it expects with well-known `centers_hz`, and whether it is `ready`. `zeta modes show ID` prints the whole row. Read the band from the row, not from memory; the built-in rows say:

- POCSAG (`pocsag_decode`): 148-149 MHz in AU (148 637 500 Hz among them), 466 075 000 Hz in much of Europe, 929-932 MHz in the US. 12 500 Hz band. Identify tries it only in the catalogue's 138-175, 450-470 and 927.34-936.66 MHz (its `band.range_hz`).
- FLEX (`flex_decode`): 1600, 3200 or 6400 bps pagers, 929-932 MHz in the US, 151.8-153.4 MHz elsewhere per the catalogue; no built-in centre, start it on the measured one. Identify tries it only in the catalogue's two ranges, 151.837-153.363 MHz and 927.278-936.598 MHz (its `band.range_hz`). 25 000 Hz band. It needs multimon-ng on the node's host.
- ACARS (`acars_decode`): 131 550 000 Hz (worldwide primary), 131 725 000 and 131 825 000 Hz (Europe), 130 025 000, 130 450 000 and 131 125 000 Hz (North America), 131 450 000 Hz (Asia). 10 000 Hz each. An event whose text carries a position report (ACARS labels H1, 80, 16, 3L and QQ, downlinks only, never an uplink) carries `lat`, `lon`, sometimes `alt_ft`, and `position`: the aircraft's own report, minutes old.
- VDL Mode 2 (`vdl2_decode`): 136 975 000 Hz worldwide (136 725 000, 136 775 000, 136 825 000 and 136 875 000 Hz in Europe), 25 000 Hz band. It needs dumpvdl2 on the node's host (the install hint names it; the OpenWebRX+ apt repository packages it). An event is one AVLC frame keyed on the ICAO address `icao` (`addr_type` tells an aircraft from a ground station): report its `summary`. A ground-station row's ACARS columns (`reg`, `flight`, `label`, `text`) name the aircraft of each uplink, and an ADS-C report gives the frame a `position`; an aircraft frame whose ACARS text carries a position report (labels H1, 80, 16, 3L, QQ) gets `lat`, `lon`, sometimes `alt_ft`, and `position` too, the aircraft's own report, minutes old, never over a decoder's structured fix.
- HFDL (`hfdl_decode`): see "Remote HF receivers (KiwiSDR)"; 6 000 Hz band at a listed dial frequency, 2 800 000-22 100 000 Hz.
- AIS (`ais_decode`): 161 975 000 Hz (channel A) and 162 025 000 Hz (channel B), 25 000 Hz band, one job per channel (identify tries it only there, its `band.range_hz` 161.9625-162.0375 MHz); `plan_start` with `plan: "ais_vhf"` runs both in one 75 000 Hz capture. "Decode AIS" or "track the ships" is the named set `ais` (`sets/ais.json`; see "Starting a named set"): `set_start` with `set: "ais"` and `radios` mapping `radio` to a source, which is that plan stored. Never a `watch` here: an AIS message is one burst of about 27 ms, too short for the watch's detector to announce, so a watch on these channels reports no signals and starts no decoder however busy the channel is. In-process, nothing to install. An event is one message keyed on the vessel's `mmsi` (`msg_type`, `channel`, `nmea` the `!AIVDM` sentences, and per type the position, `sog_kt`, `cog_deg`, `name`, `callsign`, `destination`); vessels land on the map and in the Subjects table, one row per vessel across both channels' jobs (the row merges on `mmsi`). A moving class A ship reports every 2-10 s, one at anchor every 3 min, class B every 30 s; names arrive in separate static messages, so a vessel's row fills over a few minutes.
- RDS (`rds_decode`): any FM broadcast station, 200 000 Hz band. The first event takes a few seconds.
- ADS-B (`adsb_decode`): 1 090 000 000 Hz with a 2 400 000 Hz band; under 2 000 000 Hz is refused. It needs dump1090 on the node's host: when it is missing, the startup handler report names it with its package and `modes_list` shows `adsb_decode` `unavailable` with the reason.

"Set up a background decoder for all ACARS and ADS-B activity" is the named set `airband` (`sets/airband.json`; see "Starting a named set"): `set_list`, then `set_start` with `set: "airband"` and `radios` mapping `wide` (a radio that captures 130-137 MHz at once) and `second` (1090 MHz, 2.4 MHz) to sources. It starts one `acars_decode` on each of the seven channels, `vdl2_decode` at 136 975 000 Hz in the same capture, and `adsb_decode` on the second radio. Without dump1090 or dumpvdl2 on the host that member is `refused` and the rest start. By hand, `plan_start` with `plan: "acars_vhf"` and `kind: "acars_decode"` is the ACARS part alone (`channels` narrows it, `[5]` for 131 550 000 Hz), and VDL2 on the same radio needs the pin first: `source_pin` at 133 500 000 Hz / 8 000 000 Hz, then `plan_start`, then `job_start --kind vdl2_decode --center-hz 136975000 --bandwidth-hz 25000` (started the other way round it is a `conflict` naming the ACARS jobs). A radio serves one band at a time, so ADS-B waits for a second radio. With one radio, the named set `airband_vhf` (`sets/airband_vhf.json`) is `airband` without its ADS-B member: one role, `wide`, the seven ACARS channels and VDL2 in one `set_start` with `members: null`. `airband_vhf_and_sos` adds the 121.5 MHz distress (guard) channel as an `am_demod` to listen to (voice, not a data link: nothing from it reaches the map) in a 16 MHz capture instead of 8. It is the set for "aircraft telemetry on VHF", and the one to start when `airband`'s `second` role has no radio (`set_start airband` is then a `conflict` on `radios.second`, or `other` when both roles name one source).

When rows declare `subject.merge` (`acars_decode` and `vdl2_decode` both do), the page shows one aircraft table across the links, with a `Via` column listing the protocols heard. `merge_skip` names the subjects a row keeps apart (a VDL2 ground station, whose `reg` is the last uplink's aircraft). The seven `acars_vhf` jobs share that one table too: an aircraft heard on two ACARS channels is one row, and the heading lists the jobs.

`knowledge_lookup` says which decoder proves a band's signature (`decoder` names the mode id, the job kind; `null` when no mode proves it yet). `classify` tries the best-scoring modes with a quick attempt (APRS, POCSAG, ACARS, RDS, AIS, and frame rows) as decode-to-identify and lists each under `tried` with its outcome; it never runs a program row such as ADS-B (`skipped_quick`: use `adsb_decode`). A CRC-clean decode is the strongest layer 2 evidence there is. A signature match without one is a guess: say so.

### Decoding modes

A decoder is a row, not code. `zeta modes list [--family F] [--state S]` shows every row with its `state`:

- `ready`: the node can start it. `job_start --kind <id>` takes the row's id.
- `unavailable`: the row is fine but its program is not on this host. `reason` names the program.
- `broken`: the row did not parse or validate. `file` is the file to fix and `reason` is `<field>: <error>`. A broken row never stops the node: it is reported at startup as `zeta: mode <id> (<file>): <field>: <error>` and starts nothing.

Never invent an id: `job_start` with a kind that is neither a built-in nor a row's id fails with an `unknown` error (`field: "kind"`, `known` the built-in kinds and every row id), and a row that is not ready fails `mode <id> is <state>: <reason>`.

**Handlers.** A program row (`adsb_decode` running dump1090, `flex_decode` running multimon-ng, and others) needs an external program. At startup the node prints one line per program: `zeta: handlers: <program>: found <path> (<version>)`, or `zeta: handlers: <program>: missing (apt install <pkg>; <url>) — modes: <ids>`. A missing handler is not an error and is never fetched or built by zeta. To install it, run the package command from the line (`apt install dump1090-fa` for dump1090), then restart the node: the row turns `ready`. A program outside `PATH` is named with `ZETA_HANDLER_<PROGRAM>` (`ZETA_HANDLER_DUMP1090`; `ZETA_DUMP1090` still works). Programs run with a cleared environment, as plugins do. A graph row may list helper programs (`decoder.handlers`), programs a stage of it needs on the host; a missing one makes the row `unavailable` like a program row's program. A helper program is not a handler of the mode (next section): the row's own decoder still runs, the program inside one of its stages.

**Audio-input rows.** A program row can take demodulated audio instead of IQ. Its `decoder.demod` (`{kind: nbfm, deviation_hz, audio_rate_hz}`) names the demodulator and `input.container` (`raw` or `wav`) how the audio reaches the program; the node expands it to `channel → nbfm_demod (squelch off) → external_decode`. The sonde rows are the example: `rs41_decode`, `dfm_decode` and `m20_decode` run the rs1729 decoders (`rs41mod`, `dfm09mod`, `m20mod`; package `sonde-decoders`, <https://github.com/rs1729/RS>) over a 12 500 Hz channel anywhere in 400.05-406 MHz (`band.range_hz`, no `centers_hz`: a sonde's frequency varies by flight, so start the job on the measured centre). Their rows map the decoder's fields to `position` (`lat`, `lon`, `alt_m`) and name the GPS-time field in `time`, so events carry `position` and `t_ns`, and `summary` reads `{id} {lat?:.4},{lon?:.4} {alt?:.0} m {vel_v?:+.1} m/s` (a `?` field the decoder left out is dropped with its separator). One sonde per job. `zeta modes check --strict` passes `rs41_decode` and `m20_decode` against the real `rs41mod` and `m20mod` on a host that has them; `dfm_decode` has no synthesised test yet, so it prints `skipped: no test` (and `--strict` fails a row without one).

**Checking a row.** `zeta modes check [ID] [--strict]` runs each row's test on a local node over a synthesised capture (APRS, POCSAG, RDS, ACARS, mode S identity, NBFM tone, RS41 (`rs41`: `serial`, `lat`, `lon`, `alt_m`, `vel_v`, `frames`), Graw DFM (`dfm`: `serial` as `DFM-<n>`, `lat`, `lon`, `alt_m`, `vel_v`, `frames`; `dfm_decode` has no row test yet, since `dfm09mod` never reads the serial back), Meteomodem M20 (`m20`: `serial` as `M20-YMM-S-NNNNN`, `lat`, `lon`, `alt_m`, `vel_v`, `frames`), AIS (`ais`: `mmsi`, `lat`, `lon`, `sog_kt`, `cog_deg`, optional `name`, `repeat`, optional `gap_ms`), FLEX (`flex`: `capcode`, `text`, `baud` (1600 only), `repeat`), M17 (`m17`: `src`, `dst` (callsigns of at most nine base-40 characters, `ALL` for broadcast), `can` 0-15, `frames` 1-250 of 40 ms), P25 phase 1 (`p25`: `nac` 0-4095, `src` 24 bits, `dst` a talkgroup of 16 bits, `superframes` 1-20 of 360 ms, `encrypted`, `control` for a control channel), DMR (`dmr`: `color_code` 0-15, `src`, `dst` 24 bits each, `superframes` 1-20, `origin` `repeater` or `handheld`, `second` a call on slot 2, `encrypted`, `idle`, `control`, `talker_alias`) and the generic `fsk`, `psk` and `ook` families, whose `bits` are hex or `pattern:<hex>`; impairments `snr_db`, `offset_hz`, `ppm` and `echo` `{delay_us, gain_db}`) and prints `<id>: ok`, `<id>: fail: <reason>` or `<id>: skipped: <reason>`. Skipped means no test, or the program is missing; `--strict` makes that a fail. It exits 0 when no row failed. A pass is recorded (`checked` in `modes list`) for program rows and graph rows with helper programs. `--handler H` checks the mode's handler `H` instead of the row's own (every mode that has it, without an `ID`): a handler file's prints and records as `<id>@<H>`, its `checked` in `modes list`'s `handlers`. A row missing only optional helper programs (`p25_decode` and `dmr_decode` without `zeta-mbe`, `m17_decode` without `c2dec`) runs its test without them and passes, records no `checked`, and fails only with `--strict`. It is local only: it is refused with `--node` and while `zeta serve` owns the state directory. Run it after writing a row and before trusting it.

**Writing a row.** Put one `*.json` file in the operator directory (`--modes-dir PATH`, default `$XDG_CONFIG_HOME/zetasdr/modes`, else `~/.config/zetasdr/modes`; the node reads it at startup). A row whose `id` matches a built-in replaces it; a new `id` adds a mode. Every field is required unless the schema marks it optional, and unknown fields are rejected. The simplest row is a copy of a built-in with a changed centre. Take `zeta modes show pocsag_decode`, keep the whole row, give it a new `id` and `name`, and put the centre you measured in `centers_hz` (148 812 500 Hz below is only a placeholder):

```json
{
  "id": "pocsag_local",
  "name": "POCSAG, local pager channel",
  "family": "pagers",
  "band": { "bandwidth_hz": 12500, "centers_hz": [148812500] },
  ...every other field of pocsag_decode unchanged...
}
```

Then `zeta modes list --state broken` must not list it, and `zeta modes check pocsag_local` must print `ok`. Centre the row on the measured signal, not on a raster. A graph row like this one reuses a built-in decoder at another centre; a program row declares its program, input format and output parser (`json_lines`, `sbs`, `nmea`, `kiss`, `text`, `multimon`); read `adsb_decode`'s row for the shape.

**What the events look like.** Every decoded event carries `protocol`, `t_ns` and `summary`, the row's one-line rendering (`{address}: {text?}` for POCSAG). Report `summary`; the other fields are the decoder's own. An event carrying `access: "restricted"` is content a later access control may gate (pager text): treat it as you would a private message, and report what the operator asks for, not every word.

**Subjects.** A row may name what its events are about: `subject` is `{key, name, waterfall, columns, heading, label, track_points, track_min_m}`. `key` is the event field naming the subject (`icao` for an aircraft, `id` for a sonde, `src` for an APRS station), so the page keeps one table row per key rather than one ribbon per event; `name` is the plural noun ("aircraft"); `waterfall` is `summary` (one line for the job) or `fold` (one line per subject); `columns` are the event fields shown, each with a `label` and a `unit` (`ft`, `m`, `kt`, `km_h`, `m_s`, `deg` or `null`) that the page shows as the operator reads it; `heading` and `label` name the event fields holding the heading in degrees and the name it is called by, or `null`; `track_points` (100 when left out, at least 4) and `track_min_m` (0 when left out, not negative) shape its track on the map: a fix joins when it is at least `track_min_m` metres from the last kept point, altitude counted where both have one, or when `heading` has turned more than 10 degrees from that point's, the marker and the line's end always at the latest fix, and at `track_points` the older half loses every other point, its first kept. A bad one is `broken` naming `subject.track_points` or `subject.track_min_m`. Every named field must be in the event schema, else the row is `broken` naming it (`subject.key`, `subject.columns[<i>].field`, `subject.heading`, `subject.label`), and a word outside `summary|fold`, the unit words or `m|ft` is `broken` naming `subject.waterfall`, `subject.columns[<i>].unit` or `position.alt_unit`. A mode that reports altitude in feet says so in its `position` with `alt_unit: "ft"` (`m` when left out): the event keeps its field, and `position.alt_m` is converted. A row without `subject` keeps one ribbon per event; an operator row may add one, as it may add a `position`.

**Quick answer or thorough.** `classify` is the quick answer: it scores every row against the layer-1 measurement and tries the best 5 with a short decode, listing each under `tried` with `proved`, `no_frame`, `skipped_band`, `skipped_span`, `skipped_quick` or `unavailable`. It never runs a program row, and it leaves out `m17_decode` (no quick decode), which only `identify` tries. A `no_frame` means nothing decoded in that span, not that the protocol is absent. When `classify` leaves the answer open, or the signal may be ADS-B, use `identify`: `job_start --kind identify` on the box, or one-shot `zeta job start --kind identify ... --then-tail 3,10000`. The tail is capped at 10 000 ms (a larger timeout is `out_of_range`), so a one-shot `--then-tail` only sees a verdict that lands inside that window, while the dwells run in sequence (5 s for APRS, POCSAG and the sondes, 10 s for RDS and ACARS, 15 s for ADS-B). For anything longer, start `identify` against `zeta serve` (`--node`) and read `job_context` (`identify.verdict`), or `stream tail` the `candidate` events. It holds the radio, measures 1 s, then runs each fitting ready row as a child job in score order for the row's dwell. Read its `candidate` events in order: each has `mode`, `score`, `outcome`, `evidence`, `summary` and the child's `job`. A `proved` candidate ends the job with the verdict in `job_context.identify` and leaves that decoder running under `verdict.job`; stop it with `job_stop` when done (`--then-tail` already stops it unless `--keep`). An exhausted list ends with `verdict.mode: null` and the layer-1 features: report that as unknown, with those features. Do not guess a protocol from a `no_frame` list.

### More than one decoder for a mode

A mode can have several handlers, each decoding the same signal into the row's events: the row's own decoder (`builtin` for a graph or frame row, its program for a program row, `dump1090` for `adsb_decode`) and one per handler file that lists the mode (`--handlers-dir`, `handlers/README.md`). `modes_list` gives each mode's `handlers` (`id`, `name`, `outputs`, `state`, ...) and `handler`, the one a start with no `handler` runs now; `zeta handlers list` prints them one line each. They differ in what they output: one may give packets (`outputs` lists `packet`) where another gives only events.

- Leave `handler` `null` unless the operator names one or asks to compare two: the policy picks a ready one (the operator's ranking for the mode, then the node-wide one, then an in-process handler before a program, then the row's own). The node-wide ranking counts only for a handler that gives every output the row's own decoder gives: on a voice mode it does not put OnAir's events-only handler first. What a plain start will run is `modes_list`'s `handler`, not the ranking as stored. Two jobs of one mode on one band with different handlers are two jobs, not a duplicate.
- To capture a decoder's packets, start it with `needs: ["packet"]` (`--needs packet`): the policy then passes over every handler without a packet output, whatever the ranking, and the start is refused naming each handler and why when none is left. Then `job_attach` `packets` to it (Open decoded frames in Wireshark below). A job started without it may run a handler that gives none: `job_attach` then says which handler of the mode does.
- An `adsb_decode` capture (dump1090's Beast output or OnAir's) has `link_type` `mode_s` (`DLT_USER1`, 148): each packet is one Mode S frame as received, 7 or 14 bytes with its parity. Wireshark reads it with the node's dissector, `docs/wireshark/zetasdr.lua` (downlink format, address, type code, parity).
- To compare two decoders on one signal, start the second beside the first: `job_start` with `beside: <the running job>` and the other `handler` (`zeta job start --beside <job> --handler <id>`). It takes the same band and source, tunes and stops nothing, and both records carry a `group`. Read each job's events side by side: a decoder silent beside a busy one is the decoder, not the band. The same start gets a capture from a handler that gives packets when the running one gives none: add `--needs packet` and attach `packets` to the sibling. A retune of either moves both; `job_stop` stops one.
- A row with no decoder of its own (`decoder_kind` `null`; `decoder: null` in the file) is run only by a handler file's entry: `zigbee_decode`, `thread_decode`, `wisun_decode`, `ble_decode`, `lorawan_decode`, `zwave_decode`, `wifi_decode`, `tetra_decode`, `gsmr_decode`, `lte_decode` and `dvbs_ip_decode`, all OnAir's through `onair-rx` 0.4.0. It is `ready` while an entry is, and otherwise `unavailable` with `no decoder of its own, and no handler for it is ready` and each entry's reason; a start is refused with that text. A job of it always records its handler. Each carries `content: network_traffic` (on `modes_list`, the job's context and a capture's record), which nothing reads yet; do not treat it as a restriction. The packets are the point: start with `needs: ["packet"]` and read the capture in Wireshark. These rows give events for what a receiver reads, not decoded payloads: no key is loaded, and traffic to a terminal on TETRA, GSM-R and LTE is not decoded. Z-Wave's capture is link type `USER2` (149), since 148 is the node's Mode S; it needs Wireshark's DLT_USER table pointed at OnAir's Z-Wave dissector (`onair-rx --lua`). One job reads one channel for Bluetooth LE, Zigbee and Thread (a second channel is a second job); Wi-Fi and LTE need 20 MHz and a source that holds that rate without dropping samples (read the dropped count and `input lagged` on the node's stderr). LTE's entry runs `--drop` (it cannot keep real time without), so a replay is read at real time and a faster feed misses. `dvbs_ip_decode` is tried by identify, classify and a watch only when named (`identify.when_named`); started by hand it runs anywhere. Install `onair-rx` 0.4.0 before the node: an older wrapper is probed `ready` and these modes then fail at launch with `onair-rx: no mode <m>`. See RECIPES.md, "Modes only OnAir decodes".
- A job's record names what runs: `handler`, and `handler_named` (asked for, or the policy's). Its events carry `handler`. Judge what a job outputs by that handler's `outputs`, not the mode's: the mode's `outputs` are the union over its ready handlers. A handler without `audio` (OnAir's, on DMR, P25 and M17) gives the calls as events only: they cannot be heard, and a transcriber attached to that job is refused (`job <id> has no audio stream`). To listen or transcribe, start the mode with `needs: ["audio"]` (`--needs audio`), which passes over such a handler.
- `handler_policy_set` (`zeta handlers policy set --mode <mode> <id>...`; no ids clears it, no `--mode` is the node-wide ranking) is the operator's standing choice, kept across restarts: set it only on their word. A running job keeps its handler; a restarted one whose chosen handler is no longer ready is chosen again, and its context says why.
- To check a decoder, or two handlers, against a stored recording instead of the air, replay it: `capture_decode` with `capture` (an id from `capture_list`), `kind` (a mode id from `modes_list`), `handler` (`null` for the policy's) and `packets` (`zeta capture decode --capture <id> --kind <mode> [--handler <id>] [--packets]`). The capture's whole set is played once, in real time, from its first sample, into the mode's graph; the job holds no lease and tunes no radio, so it never disturbs a live job, and it ends `stopped` with a note of how many events it decoded (`job_context.replay` names the captures and the radio that recorded them). A local `zeta capture decode` waits for the replay to end and prints its record, note included; with `--node` it answers the job at once. It proves nothing live: it supersedes no signature, keeps no session, tallies nothing at the station and uploads nothing. Its events go only to the `replay` feed (the source `replay`, a name no radio may take), not a radio's feed or `events.log`; every decoded event (each event a decoder gives in the mode's envelope) carries `replay: <capture>`, and its events carry the recording's own time in `t_ns`, so read them against the capture's `start_ns`, not the clock. A replay never resumes: after a restart run it again. A second replay of the same recording, mode and handler while one runs is a `duplicate`. A silent replay says the decoder found nothing in that recording, not that the band is empty, and a recording too narrow for the mode is refused by the mode's own range error. To compare two handlers, replay the same capture once per handler and read each job's events. To get a capture file of a replay's packets, ask with `packets: true` (`--packets`): the capture is started before the first sample, whereas a `job_attach` of `packets` to a running replay misses what was already decoded. The handler must output `packet`; a mode with none is refused.
- A row's `decoder.handlers` are helper programs, not handlers: programs one stage of the row's own decoder needs (`zeta-mbe` for DMR and P25 voice). They do not appear in `handlers`.

### Frame rows and signatures

A frame row (`decoder.kind: frame`) decodes a framed burst in-process. Its `decoder` has `demod` (`{modulation, symbol_rate_baud, order, tone_spacing_hz}`), `framing` (the `frame_decode` params: `sync`, `length`, `crc`, `encoding`, `whitening`, `bit_order`) and `parser`. `parser` is `opaque` by default: the frame's bytes in hex, with `crc_ok`. Each cut frame is one event.

`zeta modes check` tests a frame row over the `framing` family: it synthesises a framed capture from the row's own demod and framing and expects a CRC-clean frame back.

A learned signature is such a row, written by the operator's accept (`learned_` and the id lowercased, in the node's modes directory; the record's `decoder` field names it). A node with no modes directory writes no row and says so. An existing row is kept as it is. A built-in or operator row that proves an overlapping signal supersedes the learned one.

Parsers read a frame's bytes into fields, each behind the protocol's own check, and publish an event only when the check passes. Four exist, named by `decoder.parser` of an operator frame row: `dnp3` (every CRC-16/DNP), `iec101` (the repeated length, the checksum and the end byte; the variable-length frame only), `iec104` (the APCI and the ASDU header) and `modbus_rtu` (CRC-16/MODBUS). No built-in rows ship for them: a row with no well-known centre would be tried on every band, and `iec104` has no check strong enough to keep noise from proving it. The operator names the band, the centre and the framing in use. Modbus RTU frames carry no sync word of their own (they are UART characters delimited by silence), so its row names the modem framing. For `dnp3`, `iec101` and `iec104` the frame starts with the framing's sync word (`05 64`, `68`), and the parser is handed the sync and the frame's bytes together.

The boundary the parsers keep is the spec's:

This decodes clear, unencrypted, standards-based framing that the node is lawfully receiving. It never attempts to break encryption, never targets a specific operator's link as the deliverable, and emits no transmit path. An encrypted or proprietary payload is reported as `framed, opaque` with its length and CRC status, not decoded.

### Watching a band for sondes

Radiosondes are rare: Brisbane Airport launches about twice a day (the synoptic 00Z and 12Z releases, roughly 10:00 and 22:00 local, a flight of two to three hours), and a sonde on 400-406 MHz is there for that flight only. Nobody sits watching for one; a `watch` job does. It holds a band, spots a new signal in it, runs `identify` on the signal, and keeps the decoder that proves.

One radio: pin or start the watch on the band and let the decoder share the capture.

1. `job start --kind watch --source S --center-hz 403025000 --bandwidth-hz 5950000` (400-406 MHz; the centre sits off any channel of interest because the receiver's DC spike is there). It holds a rigid lease on the band, so other jobs on that source conflict until it stops.
2. `stream list`, then `stream tail` the watch's event stream. A `signal` event (`state` `new` or `gone`, `center_hz`, `bandwidth_hz`, `snr_db`) says something appeared; the watch's own events follow it: `identifying`, then `decoding` (`mode`, `job`, `placed`), or `unknown` with the layer-1 `features`. Report an `unknown` as unknown with those features; the watch tries the signal again after a minute, three times at most.
3. `job context --job WATCH` holds `watch.signals`, `watch.decoding` (the kept decoder's `mode`, `job`, `source`, `since_ns`) and `watch.current` (the identify run in progress). The decoder is an ordinary job in `job list`; its events carry `id`, `position` and `summary`. The watch's own identify runs are owned by it (`owner` in `job list`) and leave no history.
4. `job stop` on the watch stops its identify run and every decoder it keeps. A decoder whose signal is `gone` and silent for 120 s is stopped by the watch (a landed sonde).

The detector counts a bin occupied when it stands `threshold_db` (6) over the row's median bin, not its floor, and a run as a signal only when its energy, the sum over its bins of dB over that median, reaches `energy_db` (30): a synthesised RS41 at 6 dB channel SNR clears both, and on a noisy receiver raise `energy_db` (with `graph put` on the `detect` node) before `threshold_db`.

`--then-tail` on a watch tails its event stream: frame 1 is the `signal new`, frame 2 the watch's own event.

The identify run is tuned on the detector's centre, which is good to about one fft bin (about 1.5 kHz at 6 MHz), and `rs41mod` decodes only within about 1 kHz of the sonde's centre (measured on synthesised frames: ok at ±1000 Hz, nothing at ±1500 Hz). `identify` therefore re-centres each trial on the layer-1 measured centre (the verdict and the `unknown` record carry `recentred`), but only when the shifted band still fits inside the capture and the label is not `noise`. When a sonde shows as `signal new` and still ends `unknown`, run a `measure` job on the signal's band and start `identify` (or `rs41_decode`) yourself on the measured `center_hz`.

Two radios: with a second source, for example the field host's B210 attached as `--source-node b210=b210@http://field-host:7374,max_bandwidth_hz=...`, the watch keeps the first radio on the band and puts the decoder on the other one. `zeta source free --center-hz C --bandwidth-hz B` lists which sources could take a band now; it is a suggestion, not a reservation. Then `graph get` the watch, set `decode_on` to `free` (and `prefer` to the source ids you want first) on its `detect` node, and `graph put`; the decoder lands on a free source, and falls back to the watch's capture, saying so in the `decoding` event's `summary`, when none takes it. `prefer` takes ids from `source list` only: an unknown one is refused (`prefer[<i>]: unknown source <id>`). A limitation: the watch skips a new signal that another job already decodes only when that job holds a band on the watch's own source; a decoder you started yourself on the second radio is not seen, so the watch may identify the same sonde again and start a second decoder on it.

The page shows a watch as an outline on the waterfall with its signals marked ("Watch this band" in the box menu starts one; a `signal` is a mark, not a ribbon). Its owned identify jobs are hidden. A watch's `unknown`, `decoding` and `lost` events and an `identify` job's `verdict` are also kept as transcript lines (`<kind> <id tail>: <summary>`, the register's nearest transmitter in an unknown's), and What is this on a box ends with the register's answer: its verdict (`register agrees:`, `register disagrees:`, `nothing licensed in range;` or `register unreachable:`, which is never "nothing licensed") with the register data's date, the band's purpose (`band: …`), the top three transmitter candidates (holder, site, distance and bearing, the emission in words, `expected about <n> dBm`, `pointed away` when the station is off the antenna's beam) and what the first belongs to (`belongs to: licence …, paired with … MHz`); on a capture it ends with the verdict line. The map is a tab beside the radio tabs, in the waterfall's place while it is selected (`view set main map|rf`; `view set map on|off` is the alias). Events with a `position` appear on it: a marker and track per subject for a row that names one (thinned by the row's `track_points` and `track_min_m`, the marker turned to its heading and labelled with its name and altitude), per job otherwise, whichever source it runs on (the decoder on the second radio included), and with `view set home LAT,LON` (`none` clears it; while it is `none` the page uses the station's position, read once at page load, when `station_set` gave one) the jobs pane shows distance and bearing from home for a job with one marker. A row with `subject` columns also shows on the Subjects tab of the pane strip beside the radio tabs (one pane at a time under the waterfall, chosen by its tab or `view set pane subjects|none`; `view set subjects on|off` is the same choice, `auto` only shows the tab while such a job runs), one table row per subject in metres and km/h, climb rate in m/s; a subject silent for `subject_dim_s` (60) dims and for `subject_drop_s` (300) goes, and a click on a table row selects its marker and the reverse. This state lives on the page, so a refresh refills from live traffic. The map uses vendored Leaflet and fetches its tiles only when the browser is online; `map_tiles` picks the provider (`auto` is the theme's choice, else OpenStreetMap darkened by a filter under a dark theme and plain OpenStreetMap under a light one). The Origins button on a running job's row and in the Bits header runs `origin_lookup` for that job and lights the sites on the map: one circle per register site, its brightness the site's score times its freshness (the later of the signal's last activity and the lookup, fading to nothing over `origin_fade_s`, 300 s), a line from where the query was made (the station, or the Kiwi marked with its id) to each site that fits or is unknown, and a dashed ring with no fill for a site whose emission disagrees with the measured modulation. A confirmed site has its own ring. A click on a lit site also selects it, as a subject is selected (one selection for the page, a second click or Escape clears it): the Subjects tab names it under `Site` with its holders and the register's count of its channels (`register_site`, asked once per site; `no channel list` for a site without an id or a lookup that failed), and the waterfall marks those of its channels inside the band shown; selecting a subject marks the sites its job's answer matched. A lit site is a hypothesis; read its tooltip (licensee, site, emission, score and agree, distance and bearing) before saying anything about it, and say "consistent with". The selected pane docks under the main view or, with `view set dock right`, as a third folding section of the side column (`auto` follows the theme's `layout.dock`). The box menu's "Capture bursts" starts a `capture` job on the box (fitted to the signal first, as a demodulator is), and the Explore tab of the pane strip (`view set pane explore`, shown once a capture exists and selected the first time one appears) lists the captures newest first with What is this (`capture_classify`), Download (both SigMF files) and Delete (a second click within 3 s), and a Delete all above the rows that removes every capture not pinned (also a second click within 3 s). The Jobs pane's Clear all (a second click within 3 s) is the typed `stop all`, one `jobs_stop` that keeps the page's spectrum, and then drops the finished rows.

SondeHub is a feed out of the node, so nothing uploads unless the operator gave a callsign. Put `sondehub: {callsign}` (with `lat`, `lon`, `alt_m` only to override the station) on the watch's `detect` node (`batch_ms` and `url` are optional; it is shorthand for `sink: {kind: sink_sondehub, params: {callsign}}`) and every decoder it keeps gains a `sink_sondehub` node (with no station set and no position given, the decoder is kept without the sink: its `decoding` entry carries `sink_error` and the summary says `no station set`; a hand-placed sink in that state idles, `job_context.sondehub.idle` true with `last_error`, and never fails its job); or `graph put` a `sink_sondehub` node on any sonde job yourself. `job_context.sondehub` counts `sent` and `failed` and keeps `last_error`; events SondeHub would reject (no position, no `datetime`, no `frame`, no numeric altitude) are skipped, not counted, so `failed` means transport trouble. `lat`, `lon` and `alt_m` may be left out: the node's station (`station_get`) supplies them, and the sink fails `sink.params.lat: no station set` when there is none. Do not invent a callsign or a position.

### Decoding every channel of a band

A watch can decode every channel that carries a signal across a span, not only identify one signal at a time: the pager carriers of 148-149 MHz, say. It is a watch with `modes` on its `detect` node, the list of mode ids it may start. A watch without `modes` behaves as "Watching a band for sondes" says.

Two ways to start one:

- The set: `set_start` with `set: "pagers_au"` and one radio that captures 148.0-149.0 MHz (see "Starting a named set"). Its `pocsag_decode` watch is stored in `sets/pagers_au.json` with the detector's policy set.
- By hand, two operations: `job_start` with `kind: watch` on the span; `graph_get` the watch; on the `detect` node set `modes` (`["pocsag_decode"]`), `persist_ms` (500 for a pager's bursts), `width_hz` (`[6000, 25000]`) and any of `gone_ms`, `hold_ms`, `cooldown_ms`, `confirm_ms`, `max_decoders`; `graph_put`. The page's "Decode across this band" in the box menu does the same and sets `width_hz` to 0.5x to 2x of the first listed row's channel width. A `modes` entry the node cannot run, a row the watch's band is narrower than or a bad field is refused naming it, before anything starts or restarts.

What the watch does, and what you read of it:

- A signal is matched to the listed rows by width: it fits a row when its measured width is within 0.5x to 2x of the row's channel width (a strong signal reads wider than its channel, which is why the fit is tolerant). A signal read at the detector's `width_hz` floor (within 10 % of it) fits from 0.4x instead: the detector drops narrower runs, so a clean pager that reads narrow shows at the floor, and a 6 kHz floor still reaches a 12.5 kHz row. The nearest ratio starts a decoder directly, on the signal's measured centre, never on a raster or a register centre: the `decoding` event says `via: modes` and starts no `identify` run. Rows tied for nearest run an `identify` restricted to them. A signal no row fits is `unknown` with its measured features and is retried as for any watch.
- A steady spur at a fixed RF reads as a signal the watch keeps starting a decoder on; centre the capture on it so the DC mask hides it (pagers_au sits on the b210's 148.500 MHz spur for this reason).
- `decode_on` stays at `capture` (the default) for a span: the radio does both. `decode_on: free` is honoured and the cap bounds it, but a span's decoders are many and a free source holds few: leave it.
- A watch never retunes, widens or pins the radio, and never stops a job it did not start. A decoder you started by hand inside the band is left alone, and a signal it already decodes is not started again.
- At most `max_decoders` (16) decoders at once, on any source. A signal over the cap is `waiting` (one event per signal); a slot freed by a `lost` decoder goes to the present waiting signal that ranks highest (a known channel first, then score, then SNR). Nothing is pre-empted. `jobs_stop` of the decoders' kind frees the slots.
- A decoder is `lost` with a `why` from a closed set: `gone and silent` (its signal is gone and it sent no event for `hold_ms`, 120 000 ms by default), `not seen again` (a known channel seeded at start that no signal appeared on within `hold_ms`), `unproven` (a direct start that published no event within `confirm_ms` while its signal was present; `confirm_ms` 0 turns this off) and `relaunch failed`. A lost decoder's channel, and that of one you stopped, is cooled for `cooldown_ms` (30 000 ms; `job_context.watch.cooled`): a signal on it is tracked but not started until the cooldown passes. A signal still present after a loss the watch raised, or after its decoder failed (`cooled` `why: "failed"`), counts a try, so after 3 tries a carrier no decoder proves is left alone until it goes and comes back; a decoder you stopped counts none. These cooldown and retry rules apply to span watches only.
- `job_context.watch` holds, beside `signals`, `decoding` and `current`: `cap` (`max`, `decoding`, `waiting`), `known` (`{providers, assignments, channels}`: what the knowledge providers were asked and answered, the licensed transmitters whose emission fits a listed row, and the listed rows' centres in the band; an unreachable register cannot be told from an empty one, so say "the register gave none", not "nothing is licensed") and `cooled` (the channels in cooldown). A known channel ranks first for a slot; `seed_known: true` on `detect` starts a decoder on each at once. A known channel never moves a decoder.
- A node restart or `graph_put` re-adopts the decoders: one whose signal does not reappear within the longer of `gone_ms` and `hold_ms` is stopped.
- `job_stop` on the watch stops its decoders too; that is the operator's call, as for any stop. The page folds the decoders under the watch's row and merges their subjects into one table with a Channel column.
- The pager rows (`pocsag_decode`, `flex_decode`) carry `access: restricted`: see "Legal" in the README and the rule above on decoding pager traffic; the watch does not change it.

### Remote HF receivers (KiwiSDR)

A KiwiSDR source covers 0-30 MHz and delivers 12 kHz of IQ per connection, so `bandwidth_hz` is at most 12 000: work one HF channel at a time with `measure` jobs or `classify` selections inside the band you tuned (e.g. 7 100 000 Hz with 10 000 Hz for 40 m), not wide `spectrum` sweeps. A Kiwi has a limited number of user slots; when they are all taken the source faults with `too_busy` and the job fails with that reason: report it, do not retry in a loop. The connection opens on the first tune and holds a slot until the node exits. Reception is site-dependent: the receiver's location, antenna, local noise and the time of day decide what is audible, so an empty band on one Kiwi says nothing about the band elsewhere.

`source_list` gives each source a `position` `{lat, lon, alt_m, from}`: `from` is `status` when the source reported it (a Kiwi with GPS reads `gps=` and `asl=` from its status page once per connection) or `configured` from `--source-position ID=LAT,LON[,ALT_M]`; `null` otherwise. A signal heard through a Kiwi was received there, not at the station: do not measure its range or bearing from the station.

HFDL (`hfdl_decode`, needs dumphfdl on the node's host) works on a Kiwi unresampled: `center_hz` is the listed (dial) frequency and `bandwidth_hz` 6 000. The signal sits 1.44 kHz above the dial frequency, so a `measure` box on the carrier reads 2.4 kHz of PSK offset up. A ground-station squitter every 32 s proves the channel (an identify dwell of 40 s holds one). Frequencies come from a list (dumphfdl's `etc/systable.conf` upstream, or the operator's own), not a raster. Events are keyed on `icao`, known once the aircraft's logon was heard, with `gs` the ground station, `pdu`, `flight` and a `position` from performance-data PDUs.

### Sources on another node (federation)

A `--source-node` source is a receiver attached to another ZetaSDR node, typically a Raspberry Pi at the antenna. That node ships narrowband IQ by default (250 kHz at most), which a LAN or WiFi link carries comfortably: work one channel at a time with `measure`, `aprs_decode` or `classify` inside it. Widen it only when the job needs it, with `max_bandwidth_hz=N` on the flag, and expect a slow link to drop blocks rather than slow down. A `bandwidth_hz` over the cap is `out_of_range` with `suggested` set to the cap. Each tune runs a `passthrough` job on the remote node, so that node's `source list` and `job list` show the source as held: another caller there sees the lease conflict instead of a silent retune. If the remote node goes away, the local source faults naming its URL and the job fails with that reason: report it, do not retry in a loop.

### External stages

A plugin registered with `--plugin KIND=PATH` is a stage kind like any other: it is listed in `schema` under `stages` with its `params_schema`, and you use it by adding a node of that `kind` to a job's graph with `graph get`, edit, `graph put`. No job kind starts it on its own. A plugin that crashes or misbehaves fails its job with a reason naming the plugin.

A plugin speaks wire protocol 1 or 2; its `hello` names the version and the node answers `run` with the same one. Protocol 2 adds the `video` stream: a frame carries one image, `{"width", "height", "format", "frame": N}` in its header (`format` `rgb8`, `gray8` or `png`, `N` the body's byte count) and the raw bytes as its body, `width x height x 3` for `rgb8`, `width x height` for `gray8`, any non-zero length for `png`. A body that does not fit its format is refused. A protocol-1 plugin that declares a `video` port is refused at startup; a `stream tail` of a video stream shows each frame as `{"width", "height", "format", "bytes": N}`. `sink` is carried by neither protocol.

### Bit streams

A layer-4 decoder (a signal with no known decoder, worked by hand) reports the bits it sliced as `event` frames of this shape: `{"protocol": "bits", "rate_baud": N, "bits": "<hex>", "count": N, "t_ns": N}`. `bits` is the sliced bits packed most significant bit first and written in hex, `count` how many bits it holds (the last byte is padded with zeros), `rate_baud` the symbol rate it was sliced at, `t_ns` the time of the first bit. An event is at most 64 KiB. No stage emits it yet; it is the shape a layer-4 stage will.

### Transcribing a channel

Start the demodulator, then attach the transcription to it; the attached job reads the
demodulator's audio, holds no radio lease and ends when that job stops:

1. `job start --kind wfm_demod --source S --center-hz 100500000 --bandwidth-hz 200000` (for a voice channel, the demodulator row for its layer-1 label: `classify`'s `choice.job` when that names one of the demodulator rows, `modes_list` with `role: demodulator`). Note the job id.
2. `job attach --kind transcribe --job THAT_ID`. Its chain is `stream_in → denoise → vad → transcribe` (without the `denoise` when the demodulator already denoises its own audio, below).
3. `stream list` shows two event streams on the attached job (`vad`'s and `transcribe`'s); `stream tail` them. A `transcript` event is one utterance (`text`, `language`, `start_ns`, `end_ns`); `vad` events mark where speech starts and stops. An empty tail means no utterance ended in the window, not that nothing was said.

`stream_tail` the source's feed (`stream_list`: the `event` stream with that source and no `job`) shows every transcript, `vad` and `squelch` event of every job on the radio in one call, each frame naming its job.

Transcription is per demodulator: a `mix` (see "Listening to many channels") is not transcribed unless the operator asks for it.

The node needs a speech backend (`--stt-socket` or `--stt-node`); without one the attached job fails naming it, so report that and do not retry. Language: the attached job transcribes `en` unless it was attached with `language`; a language the backend does not list (see `GET /stt/languages`) fails the job naming the languages it has. Do not guess a language from the band.

Music and noise are gated, not separated: `vad` passes any loud audio, so a music station or a broadcast with a bed under the voice yields poor or empty text. Say so rather than reporting the text as the speech. Separation is a slot: an external audio-to-audio plugin (`--plugin separate=PATH`, a Demucs wrapper for instance) replaces the `denoise` node with `graph get` of the attached job, edit, `graph put`. The job restarts on `graph put`. `docs/speech.md` has the daemon install and the plugin stub.

`queued_ms` on a transcript is how long it waited for the speech daemon (at most 4 calls at once); `dropped` with `reason: busy` means the daemon had no slot for 30 s, `reason: queue` that the job's own queue of 4 was full. Utterances under `min_utterance_ms` (700) are not sent at all; the job's context counts them under `transcribe.short`.

An `fm_demod` shapes its audio as a voice receiver does: a 3.4 kHz low-pass (`audio_lowpass_hz`) and a 6 dB per octave de-emphasis (`deemphasis_us`, 530) after the discriminator take out the hiss above the voice that a weak signal carries; the audio-input decoder rows keep the flat discriminator they decode from (`null` for both). Every voice demodulator (`fm_demod`, `am_demod`, `ssb_demod`) also takes `denoise: true` on its node (`graph get`, edit, `graph put`; the page's outline menu offers "Denoise on/off"): RNNoise runs on its audio output, so the page, a `--then-tail` and any attached transcriber all get the cleaned audio, and a `transcribe` attached to such a job runs without a `denoise` stage of its own. It is a speech model: off by default, and never on a decoder row (a tone or a data burst comes out mangled). It adds one 10 ms frame of delay, which the audio frames' spans account for, so transcripts and ribbons keep their time. These params are carried like the squelch: a `graph put` that changes only them keeps the job re-expandable, and a `job retune` keeps them.

A `fm_demod` or `am_demod` has an automatic squelch: an idle channel publishes no audio, so a quiet transcript is normal. `squelch` events say why a row is quiet (idle, or open). It opens 6 dB over the tracked noise floor (`squelch_db: null`, the default) and closes after 300 ms under it. To fix or disable it, `graph get`, set `squelch_db` (an absolute threshold in dBFS, -120..=0, not dB above the floor) or `squelch: false` on the demodulator's node, `graph put`; such a put keeps the job re-expandable at later capture changes. A `--then-tail` of an idle squelched channel is empty: that is the squelch, not a fault.

### Decoding digital voice

Three rows decode digital voice in the node: `m17_decode`, `p25_decode` (P25 phase 1) and `dmr_decode`. Each takes a 12.5 kHz channel on the measured centre, with no band or channel raster assumed: `job start --kind p25_decode --source S --center-hz HZ --bandwidth-hz 12500`, the same with `m17_decode` or `dmr_decode`. All three are 4FSK at 4800 baud, so a measurement does not tell them apart: when the mode is not known, `identify` tries them (P25 and DMR dwell 2 s each, after any row whose centre matches). D-STAR, NXDN and System Fusion have no decoder row.

M17 runs on a 2 m or 70 cm channel. Each stream gives two events: one when its link setup is in hand (at its first frame, or within six frames from the LICH when the job joins mid-stream; `frame` says which) and one at its end (`eot: true`, the last frame number). Both name `src`, `dst`, `can`, `type`, `encryption` and `codec`, and `lat`/`lon` when the stream carries a GNSS position. Its speech is ordinary job audio: the page plays it, and `job attach --kind transcribe --job THAT_ID` transcribes it as it does a demodulator's. An encrypted stream (`encryption` not null) is reported with its fields and never decoded, so it has no audio. The speech comes from `c2dec` (package codec2) on the node's host. It is optional, as `zeta-mbe` is for P25 and DMR: without it the row stays `ready`, lists `c2dec` in `missing`, and every stream is reported with its events and no audio, `job context` saying so once under `m17.vocoder` with how to install it (the job looks for `c2dec` when it starts, so restart a job to use one installed meanwhile). When `c2dec` exits mid-stream, the events keep coming, that stream's audio stops, and `job context` says why under `m17.vocoder`; the next stream starts it again.

**P25 and DMR calls.** Each call gives two `type: call` events. The opening one comes when the call's link control and its encryption are both in hand: on P25 at the first LDU1 after the header, on DMR at the first burst after the voice header. A job that joins mid-call gives it later: on P25 within about one and a half superframes (about 540 ms at worst: an LDU2 for the encryption, then an LDU1 for the radio); on DMR within one superframe (360 ms) of the first sync of any kind heard on the channel, up to about 420 ms on a repeater. The closing one (`eot: true`) comes at the terminator, or when nothing has come for more than a superframe. Both name `src` (the calling radio's ID), `dst` (the talkgroup or the called radio), `call` (`group` or `private`), `encrypted`, `emergency`, `frames` (voice frames so far), `errors` (bits the protocol's own codes corrected so far), `audio`, `silent`, `stream` and `program`. P25 adds `nac`, `mfid`, `algid` and `kid` (`algid` and `kid` are null on an opening event that only the link control marked encrypted). DMR adds `color_code`, `slot` (1 or 2; null for a handheld), `origin` (`repeater` or `handheld`) and `fid`. A channel that carries no call, a P25 control channel or an idle or control-only DMR repeater, gives one `type: channel` event instead, when its network is first decoded and again only when it changes: `nac` or `color_code`, `control: true` once trunking signalling has been seen, and `network`, the line its summary shows (`control channel, NAC 291`). It has no `src`, so it adds no row to the Subjects table. P25 trunking and packet units are counted in `job_context.p25`, not parsed. A P25 call whose link control is itself encrypted names no radio and gives no event.

**Their speech.** It is ordinary job audio, as M17's: the page plays it, and `job attach --kind transcribe --job THAT_ID` transcribes it. It needs `zeta-mbe`, a small program the operator builds on the node's host with `bash tools/install-vocoders.sh` from a source checkout; `docs/vocoders.md` has the steps and what the build leaves to the operator. Like M17's `c2dec` it is optional: without it both rows are `ready`, `modes_list` names it under `missing`, every call is still reported, and `job_context.p25.vocoder` or `job_context.dmr.vocoder` says how to install it. It is looked up at each call (M17's `c2dec` only when its job starts), so one installed while a job runs is used from the next call. A call event's `audio` says whether the call is heard; when it is `false`, `silent` says why: `no_vocoder`, `encrypted`, or `vocoder_failed` (the vocoder exited, or gave nothing for 2 s, mid-call; the next call starts it again). The row's summary and the Subjects table's Silent column show it. A clear call's speech starts once its encryption is known, so a P25 call joined mid-call is heard from its first LDU2.

**Encrypted calls** (P25: an algorithm other than `0x80`, or a protected link control; DMR: the privacy bit in the link control's service options, or a privacy header) are reported with both events and never decoded. The node accepts no keys of any kind, DMR basic privacy included. On DMR, a clear voice header licenses the call's speech from the next burst, so a link control that turns the call encrypted mid-superframe stops it from that burst; by then at most bursts A to D of that superframe have reached the vocoder, as ciphertext, never decrypted. On P25, an encrypted transmission that follows a clear one on the same network within 10 ms, with no terminator or header between them and a first link control that does not decode, is taken as the same call: up to nine frames of it (180 ms) reach the vocoder, as ciphertext, before its encryption sync stops it. A radio that scrambles its speech without marking it (no privacy bit, no algorithm) cannot be told from a clear one: its speech is fed and heard as noise, which is not a fault of the node.

**Two slots.** A DMR repeater can carry a call in each time slot, and both are decoded, each by its own vocoder. A `dmr_decode` job has three audio streams: `slot1` and `slot2` (a handheld's speech is on `slot1`), and the main stream, which play, the mix and a plain `job attach` read. `job start --audio-policy` says what the main stream carries:
- `first_active` (the default): the call that started first, until it ends; a call that began meanwhile never joins it.
- `follow`: that call, then the one still going when it ends, from that moment.
- `all`: both calls, mixed. A call whose speech is held waits in the mix at most its hold (about 250 ms) and loses none of it.

A call with no audio (encrypted, or no vocoder) never holds the main stream, so an encrypted call does not keep a clear one off it. Each call event's `stream` names its slot's stream, and `program` says whether its speech is on the main stream. The policy is set at the start: a second start on the same channel with another policy is refused as identical, so to change it start the job again with `--replace` naming the running one. To transcribe a slot, `job attach --kind transcribe --job THAT_ID --stream slot1` (or `slot2`); transcribing both slots is two attached jobs. On the page, the picker beside the job's play button chooses the stream that Play plays and Transcribe attaches to.

**Delays and the receiver.** A call's first speech can wait a little: the receiver holds up to about 98 ms of symbols at a P25 call's start and about 67 ms at a DMR call's, once per call. After one lost burst, a DMR call's speech is released superframe by superframe for the rest of the call, each superframe waiting for its own link control: about 240 ms of added latency from then on. Talker alias and GPS embedded messages are recognised and do not split a call. `job_context.p25.receiver` and `job_context.dmr.receiver` count `locks`, `false_locks`, `losses` and `off_deviation`. One or two `false_locks` near a call's start are normal (about 1 call in 500 at 15 dB); only a count that keeps rising with no calls points to noise or a bad antenna. A rising `off_deviation` means a transmitter far off its declared deviation. A weak transmitter well off its deviation (about 20 % under, at 10 dB) loses about 0.5 % of its bursts, and lone very short bursts there lose more.

### Reading transcripts

Every transcript event of an attached job is also written to the node's `transcripts.log`. `zeta transcripts tail --lines N --job ID` reads the last lines (default 50, one JSON line each: `job`, `source`, `center_hz`, `bandwidth_hz`, `start_ns`, `end_ns`, `text`, `language`, `dropped`, `error`), so you can answer "what was said on 476.4 MHz" after the fact without a live `stream tail`. It reads the state directory, so it does not work with `--node`. A line with `error` set is a failed utterance, not silence.

### Reading past events

Every event of every job on a source (every decoded frame, detection or transcript the source's feed carried, whether or not a page or a `stream tail` was open) is also written to the node's `events.log`. `zeta events tail --lines N [--job ID] [--source ID] [--protocol NAME]` reads the last lines (default 50, one JSON line each: `t_ns`, `source`, `job`, `channel`, `center_hz`, `bandwidth_hz`, `start_ns`, `end_ns` and the event under `event`), so "what did ACARS hear overnight" is `zeta events tail --protocol acars --lines 500` after the fact, and "which aircraft were up on 131.450" is the same filtered by `--job`. It reads the state directory, so it does not work with `--node`. The log holds the last 32 MiB plus one rotated file; a job's events before that are gone.

### Taking the radio from another job

A source holds one tuning, and a second job that needs a different one gets a `conflict` error. Read it before acting: it names the holders (job ids, kinds and what each is doing) and lists options, the last being `retry with replace: [<ids>]`. Decide whether the holders matter. If they do not, or the user asked for the new job, retry the same request with `--replace ID[,ID]` (`job start`, `source ensure`; `replace` is an array in the op). The named jobs are stopped and the new job started in one step under the source's gate, so nothing else can slip in between. Replace is not transactional: if a holder you did not name still conflicts, the jobs you named stay stopped and the new conflict names the remaining holders. Every id must hold that source as a rigid lease (`unknown_job` or `job <id> does not hold source <src>` otherwise); naming an elastic job is that error and nothing is stopped, the elastic job keeps running. Never replace a holder you have not read, and say in the report what you stopped. Stopping or replacing a job is the operator's explicit decision; hand-made jobs survive any request that did not name them.

The web page's own `spectrum` job is elastic (`job start --elastic`, `spectrum` only): it never conflicts, never blocks a retune and follows each retune of its source, so it is not a holder to wait for or replace. `source list` shows such jobs under `elastic`, not `holders`. A scan on the source stops it, and the page restarts its view afterwards. After a restart of the node the capture is restored (the band bounding a source's rigid jobs, when the radio can capture it) and the jobs resume in it, widest first, the elastic ones next and a scan last (it waits for the radio if the others hold it). `zeta ops tail --lines N` (default 50) shows the last applied ops with the transport that sent them (`local`, `http`, `ui`, `agent`): use it to see who changed the radio.

### Holding a band

To keep many channels running on one radio, pin the capture instead of letting each job retune it: `source pin --source S --center-hz C --bandwidth-hz B` (add `--replace ID` for the jobs in the way). Centre the pin between the channels you want, not on one of them, so no channel sits on the DC spike. Example: UHF CB (80 channels) is held by `--center-hz 476918750 --bandwidth-hz 1000000`; the lease may round up (1 024 000 Hz) and every channel fits. The pin retunes the radio to its band, even one inside a wider capture the page's spectrum holds (the spectrum follows); only when a decoder already holds the source inside the band does the pin join the current capture instead. Jobs started inside the pin run on it without a retune; the pin and the gain (`source gain --source S --db N`, or `--auto`) are saved and come back after a restart, and one-shot commands, read-only ones included, restore the pins and the gain of the sources they attach.

A pin admits jobs inside it: `source_free` lists a pinned source free for a band the pin holds whole (with no job holding it), and a set's `null` role may pick it. A start outside the pin is a `conflict` offering `unpin source S (source_unpin)` (and `stop one of the holders` only when jobs hold the source). A pin is not a holder and is not in `--replace`. Unpinning frees the radio for other work and does not stop the jobs that were inside it; they conflict with the next retune. Read the conflict, and unpin only when the user wants the pinned channels given up.

### Channel plans

`channel_plans` (CLI `zeta plans`) returns the plans the node knows with every channel's `number` and `center_hz`. Name a channel to the user by its number ("ch20", not 476.9 MHz) and start jobs at its `center_hz` with the plan's `bandwidth_hz`. The AU UHF CB plan interleaves two rasters: ch1-40 sit 25 kHz apart and ch41-80 fall halfway between them, so every channel has neighbours 12.5 kHz either side. A strong ch20 transmission leaks into ch59 and ch60 and used to open both squelches and echo the same words three times. An `fm_demod` on a plan channel therefore carries a guard: its squelch stays closed while a neighbour `guard_hz` away is more than `guard_db` stronger, and the `squelch` event says so with `guarded: true` and `adjacent_db`. When a quiet channel shows `squelch` and no transcripts, read `guarded` before concluding it is broken. The guard needs the squelch on (it is inert with `squelch: false`) and `graph put` with `guard_hz: null` turns it off. `transcribe` ignores utterances under `min_utterance_ms` (700) and a busy speech daemon drops with `reason` `queue` or `busy`; `queued_ms` on a transcript is the time it waited.

Plan ids come from `channel_plans`: read it before naming a plan. A band with no plan takes one `job_start` per measured station; never invent a plan. Broadcast FM is the example: it has no channel plan, so measure the band and start on each station found the job its `classify` `choice` names.

To run demodulators on active channels only, not on all 80, use `examples/python/cb_watch.py` (`--dry-run` shows which channels the capture holds): it keeps one elastic `spectrum` job, starts `fm_demod` plus `transcribe` on a channel that stands 10 dB over the floor and stops them after 60 s of quiet. For every channel at once, `plan_start`.

### Stopping many jobs

"Stop all jobs" is one `jobs_stop` with `source`, `kind` and `plan` all `null`, not one `job_stop` per job: there are not enough turns for that. Name a `source`, `kind` or `plan` when the request does. Report how many stopped and any `failed`. `not_allowed` means the run may not stop jobs: tell the operator, do not retry.

### Starting a whole plan

"Transcribe all the UHF CB channels" is one operation, not 80 starts:

1. `source_list`: note the `holders` other than `elastic` (the page's spectrum job is not one) on the source you will use. A holder outside the plan's band will make the start a `conflict`.
2. `plan_start` with the plan, `channels: null` (or the numbers asked for, or a named `group` of the plan in their place), the `kind`, the `source`, and `attach: "transcribe"` when transcripts are wanted. Leave `deviation_hz` `null`: an `fm_demod` then takes the plan's own deviation (`uhf_cb_au` 2500). A part of a plan that has a name is its group, never a list you type: `channel_plans` lists each plan's `groups` with their channels. "Transcribe the lower 40" is `plan_start` with `plan: "uhf_cb_au"`, `group: "lower40_voice"`, `channels: null` and `attach: "transcribe"` (1-40 less the data channels 22 and 23); the upper 40 is `upper40_voice` (41-80 less the reserved 61-63), both are `voice`, the repeater outputs `repeater_outputs` and the data channels `data`. `jobs_stop` with `plan` takes the same `group` to stop only those channels.
3. Read all four lists of the result and report them: `started` (with each `attached` and any `attach_error`), `existing` (channels already running an identical job, left alone), `refused` (channels whose own start failed, each with its error) and `warnings` (repeat them to the operator, the speech backend's capacity among them).
4. A `conflict` names the holders and starts nothing. Report it and stop: the operator decides whether those jobs go. Do not retry with `replace` or `job_stop` them unless the request named them.
5. A partial set is completed by running `plan_start` again: running channels come back as `existing`.

A result of `not_allowed` means the run may not do that: the agent is not allowed to stop jobs, or to put any in `replace`, unless the operator unlocked it for the run. Do not retry and do not work around it with other calls. Tell the operator to say `allow stops on` (`allow deletes on` for a refused `capture_delete`), or press the retry button, then ask again.

### Starting a named set

"Start the airband set" or "decode every pager carrier" is one `set_start`, not its members by hand. A set is a stored recipe: roles (`radios`), never sources, and members that are `job_start`, `plan_start` or a watch.

1. `set_list` first: the ids, each role's `note` (what radio it needs), the members, and `running` (on which sources, and each job's state; `ended` for one stopped or failed since). A set that is `broken` names the field; report it, never work round it. `set_list` only reads.
2. `source_list`: note the holders other than `elastic` on the sources you would use.
3. `set_start` with `set`, `radios` mapping every role the chosen members use to a source that can capture the role's band, or to `null` to have the node pick the first free source in role order (it keeps that source while the set runs; report the picks from the result's `radios`), `members` (`null` for all) and `replace` (`[]` unless the request named jobs).
4. Read the four lists: `started`, `existing` (already running, skipped), `refused` (a member this node cannot run: `unavailable` or `unknown` for a decoder whose program is missing or whose kind it lacks, or a start that failed; the others went on) and `warnings` (repeat them).
5. A `conflict` names the role, the source and the holders, and nothing started anywhere. A `null` role the node could not fill is a `conflict` too: `options[0]` reads `radios.<role>: no free source covers ...; busy: ...`, `source` is the first source covering the band and `holders` every covering source's holders (`other` with the same text when no source covers the band). Report it and stop: the operator decides. `members` narrows the next request to what is free. Never retry with `replace` unnamed or `job_stop` the holders. A watch member on a band another watch holds with a different policy is `other` naming that watch: report it, never stop or `graph_put` it unasked.
6. Run it again to complete a partial set: running members are `existing`.
7. `set_stop` is the operator's: use it only when the request names the set, or you started the whole set in this run. It stops only the jobs the instance started, those on a radio first; jobs started by hand on the same radios keep running. Report `stopped`, `ended` (already stopped by hand or failed) and `failed`; when a stop failed the instance is kept, so a second `set_stop` can finish it. Through `ask` a set started with `existing` members leaves `set_stop` to the operator: a run may stop only a set it started whole.

A set file never names a source: the operator's own sets (`--sets-dir`) are refused at load when they carry `source`, `replace` or `params.prefer`. A row the host lacks does not break a set at load; that member is refused at start. A `job_start` member of a row with several voices (`dmr_decode`) may carry `audio_policy` as `job_start` takes it (absent: `first_active`); its job's record keeps it, and on a kind with one voice the set is broken at load (`members[<i>].audio_policy: <kind> has one voice`).

### Listening to many channels

"Let me hear everything" is one `mix_start`, not a player per channel. `sources: null` mixes every source of the node, a list only those; one mix spans any set of tuners. It takes no lease, tunes nothing and stops nothing, so start it whenever; running it twice on the same set answers the same job.

1. `mix_start`, then play the job's audio or `stream tail` its streams (`stream list` shows an `audio` and an `event` stream with provenance source `node` and the mix's `job`; the `ops` stream is the one with no `job`).
2. Its `event` stream publishes `active` (`job`, `source`, `center_hz` of every channel being heard) whenever that changes; a channel stays active for 500 ms after its last audio. `job_context.mix` holds `inputs` (how many jobs it mixes), `active`, `last` (the last channel heard), `muted`, `dropped_ms` and `underruns` (each per job), and `skipped` (jobs whose audio is not 48 kHz mono, each named once).
3. `dropped_ms` counts audio the mix threw away because a channel's queue ran over 200 ms; `underruns` counts the times a channel ran dry after it had started feeding. Both are per job, not per channel. Either means the mix could not keep time with that channel: report it with the job, do not hide it.
4. A mute is a channel, `{source, center_hz}`, not a job: `graph get` the mix, add it to `muted` on the `mix` node, `graph put` (this restarts the mix under its id). It matches any job on that source centred within 1 kHz, so it outlives the job: a channel muted and restarted stays muted, a fit that moves the centre a little keeps it, and a retune elsewhere is heard again. Mutes live in the mix, so stopping the mix (`stop all` included) forgets them.
5. `wfm_demod` and `ssb_demod` have no squelch: they always produce audio, so a mix holding one is open all the time until that channel is muted. Say so rather than calling the mix broken.

On the page, many idle plan channels fold into one `<n> idle <kind> on <plan>` group (more than 8 idle), but only on evidence the page has: a kind with no squelch, a job on the shown source (all are watched, through its feed) whose squelch is known closed for 60 s, or an unwatched job on a source covered by the mix the page is playing that the mix has not heard for 60 s. Idle plan channels on the shown source therefore fold on their own squelch evidence, with no mix playing; only jobs on other sources need the mix's evidence. An unfolded idle channel is not broken. `view set side both|transcript|jobs|none` picks which side panes show (`jobs` gives the job list the whole column) and `view set theme <id>` the look, the ids being the ready themes of `themes_list` (`console` the default); in `console` job tags sit on a rail left of the frequency axis, in `plain` on the outlines.

View settings live on the page, for the tab that asked (`radio_policy` and `radio_prefer` are the exception, kept in the browser for every tab); they are not node operations. From the page, change one with the `view_set` tool (`{"key": "theme", "value": "terminal"}`; read `themes_list` first for a theme, never invent an id), never with a `graph_put` or any job operation. It takes the presentation keys only: `theme`, `side`, `dock`, `main`, `map`, `pane`, `subjects`, `finished_rows_s`, `subject_dim_s`, `subject_drop_s`, `plan`, `follow`, `origin_fade_s` and `map_tiles` (the map's tiles: `auto`, `osm`, `osm-dark`, `opentopo`, `esri-street` or `esri-imagery`); `zoom_out`, `scanner`, `auto_scan_stop` (they drive the page's scans) and `home` are the operator's to type, and any other key is refused with the list. A `view_set` takes effect only when the run's answer reaches the page: a failed run applies nothing. Without that tool (`zeta ask`, MCP) answer with the command to type, for instance `view set theme terminal`. The default radio is the one the page has focused: its tab carries an accent dot (hover: `default radio for the agent (policy <p>)`), on the RF view and on the Map's kept tab. `view set radio_policy focus|focus-fallback|free-first|ask` chooses what the agent does with it (default `focus`) and `view set radio_prefer none|a,b` sets the preference order for the fallback; both are saved in the browser across tabs and restarts, `view reset` clears them, and the agent cannot set them (they are the operator's to type). Under `focus` use only the default radio: when it cannot take the band, say why, name the free radios and ask which; never start on another unnamed radio (the gate answers `policy`). Under `focus-fallback` use the first free radio in the preference order and say which and why. `free-first` is the first free radio, and `ask` asks before starting. A radio the request names always wins. The box menu's Send to agent names its radio (`... on <source>, from ...`), and after an answer the page notes `ran on <src> (<tool>), not the default radio <radio> (<policy>)` when the run used another radio. Changing a view setting never needs a job stopped or replaced: running jobs do not block it. When the operator says the map is blank or black, its tiles are not loading (the map says so in its corner): set `map_tiles` to another provider, say `osm` or `esri-imagery`.

Transcription happens per demodulator. Starting a mix attaches no transcript; `job_attach` a `transcribe` to each channel you want transcribed, as under "Transcribing a channel". Attaching a `transcribe` to the mix's output is the operator's option, alongside the per-demodulator ones: it runs overlapping voices together and names no channel (its log shows `node` and 0 Hz): attach it there only when asked.

### Fitting a demod to a signal

A box drawn by hand over a 12.5 kHz channel is about 100 kHz wide: 10 dB of extra noise in the audio and a centre a little off the signal. Fit the band to the signal, never to a raster (channels do not sit on a grid; a plan's channel numbers are names, not truth):

1. Measure the box: `job start --kind measure --source S --center-hz C --bandwidth-hz B --then-tail 1,3000`. Read `label.name`, `center_hz` (the occupied band's centre, absolute RF) and `bandwidth_hz` (the occupied width) from the event; an `ssb` label's `evidence` carries the dial frequency (`dial ≈ N Hz`). Started without `--then-tail`, the `measure` keeps running: `job_stop` it when you have read it.
2. A `noise` label (or `unknown` under 6 dB SNR) means nothing to fit: start at the box as drawn and say so.
3. Otherwise start the job `classify`'s `choice.job` names on the box (its kind, centre, width and `params`). A demodulator row's job was sized by that row's `band.width_rule` (`modes_show fm_demod`): the measured centre (an `ssb_demod` on the SSB dial), the occupied width scaled and floored, and, because a weak voice signal measures only its carrier line (the occupied band is the bins 6 dB over the floor), a plan channel's width, `power99_hz` or the box when the measured width is under the floor and not trusted. An `ssb_demod`'s channel passes half its 6000 Hz band either side of the dial, and USB voice reaches 2.7 kHz above it.
4. A job already running is moved the same way with `job retune --job ID --center-hz C --bandwidth-hz B`: same id, its attached `transcribe` relaunched with it, its squelch settings kept, its channel-plan guard derived again at the new band. Inside the current capture nothing retunes the radio; outside it the radio moves when no other rigid job or pin holds it, else the `conflict` names the holders and `--replace` is the answer when they may stop.

The receiver's DC spike sits at the capture centre. On a local device `measure` does not measure the bins within 25 kHz of it when the box contains the centre but is not centred on it (a box the radio was tuned for is centred on the DC and is measured as today, spike included). So a box that contains the capture centre cannot fit a signal within 25 kHz of that centre: under the UHF CB pin at 476 918 750 Hz that is ch20, ch21, ch60 and ch61. Fit such a channel from a box that does not contain the centre, or with the outline menu's "Fit to signal" on a job whose band excludes it (a 12.5 kHz band on ch20 holds no DC and is measured unmasked: that fit measures a box of twice the job's width, but only the job's own band where the wider box would take the centre in, or when the wider box finds no signal). Pin the capture between the channels you listen to and box away from its centre.

The web page does this on its own: a demodulator started from a box is fitted first (the transcript says `fitted <kind> to <centre> MHz, <width> kHz (<label>, <rule>)`, `<rule>` being `occupied`, `plan <id> ch <n>` (with `, capped by the capture` or `, capped by the box` when that cut the channel's width), `99 % power` or `kept` (on a running job `kept: the signal reaches past the job's band` or `kept: the signal fills the band` when it is at least as wide as the job), or `no signal found in <lo>-<hi> MHz; started <kind> at the box as drawn`, with `(the capture centre <mhz> MHz is in the box: the 50 kHz around it are not measured)` before the `;` when the box holds a local radio's capture centre), a running job's outline is dragged by its edges or its body and retuned on release, and a demodulator's outline menu offers Fit to signal (a running job is never widened by it except to a channel plan's width, and its centre stays in its band) and, under Width, the 2.5, 5, 6.25, 12.5 and 25 kHz widths about the current centre (every job's menu offers its next steps under Next, What is this?, Identify, a measure job and Watch on its band, and Stop; the job's row opens the same menu from its ⋯).

### Reading a source's health

`source list` gives each Soapy source a `stats` record (`null` for a recording, a KiwiSDR, a `--source-node` and a `--source-vrt` source; `worker` shows the child that owns the device (`pid`, `restarts`, `since_ns`, `transport` and `transport_dropped`; `null` when the source runs in the node)): `measured_rate_hz`, the samples per second the device actually delivered (an integer, `null` until two blocks have arrived), and `overflows`, `timeouts` and `restarts`. Compare `measured_rate_hz` with the pinned rate: within 1 % is healthy. `restarts` counts clock-guard stream restarts, each logged as `zeta: soapy <id>: samples ran <n> ms ahead of the clock; stream restarted`; more than 5 in 60 s fault the source with `soapy: samples arrive faster than <rate> Hz`. `overflows` and `timeouts` are zeta's counts of the driver's read results, not the device's own. `bank.dropped` in the same record counts input blocks the shared channel bank dropped under load; a number that climbs means the node cannot keep up, so drop jobs or narrow the pin. `worker.transport.path` is `shm` when the worker hands its blocks over through a shared-memory ring (`ring_bytes` long) and `pipe` when they travel in the pipe itself (a worker of an older build gives `null`); `worker.transport_dropped` counts what the worker could not hand over: on the ring, 2 MiB pieces the node had not yet released; on the pipe, or when the worker's own broadcast lags, whole blocks its pump could not take. Like `bank.dropped`, a number that climbs means the node cannot keep up; it starts again from 0 when the worker is respawned.

`GET /health` carries `stages_running`, the live stage tasks: every graph stage plus one IQ forwarder per job on the radio, none for an attached job, and one loop for a scan whatever its graph. A number that keeps climbing after jobs are stopped is a leak: report it with the job history, do not restart quietly.

A `measure` job's `job context` carries `measure: {discarded, partial, last}`: windows discarded, windows emitted short, and the last cause (`gap`, `lag` or `retune`). A `measure` event with `partial: true` spans only the samples it held (at least 250 ms); read its fields with that in mind.

### A radio that comes back

A Soapy device runs in a `zeta soapy-worker` child that the node spawns, so a driver crash or a pulled cable faults the source and never ends the node. Expect this on a cable pull: within about a second `source list` shows `fault` as `no samples for 1000 ms (device unplugged?)` (the worker's exit 5), every job on the source fails with `source <id>: <fault>`, and `job_start` is refused with `source <id>: <fault>` (`source_ensure` and `source_pin` still answer `io: <fault>`). A driver crash reads `soapy worker for <id> died: signal 11 (SIGSEGV)` (or `exit code N`); a device that is not there reads `device not found: <args>`, and an open that fails `soapy open failed: <last stderr line>`. Nothing needs restarting: the node respawns the worker (1 s doubling to 5 s, reset after 60 s alive; every 5 s while the device is absent), logs `zeta: soapy worker for <id>: <fault>; waiting for the device` once and, when the device is back, `zeta: soapy worker for <id>: back after <n> attempts, <s> s`. Then it restores the gain and the pin and relaunches every job that failed with that fault, under its own id (widest first, a scan last; an attached `transcribe` after its input; the `watch` re-adopting its decoders), logging `zeta: source <id>: recovered: pin <c>/<bw> Hz, gain <g> dB, <n> jobs relaunched`. A healed fault stays in `source list` until recovery has seen the jobs end, normally up to one poll (200 ms) after the hello; during that hold a `job_start` is accepted, and its job may fail with the fault and be relaunched under its id. Jobs you stopped, jobs that failed for their own reason and jobs that failed in an earlier episode stay as they are. The node awaits the worker's hello for up to 150 s (`soapy worker for <id>: no hello in 150 s`); on the field host the B210 says hello in 2-4 s from cached figures, and a first start that measures every sample depth takes about 70-110 s. A live worker writes its status every second; one that writes none for 10 s (a driver stuck under its status task) reads `soapy worker for <id>: no status for 10 s` and is killed, then respawned and recovered as above. The worker hands its IQ to the node through a shared-memory ring the node creates for each spawn (64 MiB by default, slots of 2 MiB in bytes holding `cf32` or, from a device whose samples are 16-bit, `sc16` (twice the samples, so twice the time), inherited by the child as fd 3; `worker.transport.format` says which, and the node converts `sc16` with the one function a capture's `cf32` uses), and the pipe carries only control and small block descriptors, so a burst of samples never delays a fault or a status. A worker without a ring (`memfd_create` unavailable) sends the blocks on the pipe, and `worker.transport.path` says which (`shm` or `pipe`).

`worker` in `source list` is `{pid, restarts, since_ns, transport, transport_dropped, starting, attachment, link_measure}` (`null` for a source that runs in the node; the last three are in "Measuring a radio's link" below): `restarts` counts respawns since the node started, `since_ns` is when the live worker said hello, and a `restarts` that climbs while the device is healthy means the driver keeps crashing: read the worker's own stderr lines, prefixed `zeta-soapy-worker[<id>]: `. A source that stays faulted while `restarts` rises is waiting for a device that is not on the bus. A device absent at startup attaches faulted (`device not found: <args>`) when an earlier start saw it, else the flag is refused (`device not found: <args> (never seen on this host; plug it in once)`, exit 1); a worker that crashes opening a device an earlier start saw (`soapy worker for <id> died: signal 11 (SIGSEGV)`, UHD still releasing it from a node that just stopped) faults the source the same way and is respawned with backoff. `--soapy-in-process` opens the device in the node as before, for diagnosing the worker only: a crash then ends the node.

### A radio's ceiling

A radio can be asked for more than it can stream: a B210 will tune 61.44 Msps over USB 3 and then fall 16 % short with more than a thousand overflows a minute, so every job in the capture sees gaps. At open the worker therefore probes the device's rate candidates from the top (a UHD ladder's rungs, at most 6; `max`, `max/2`, `max/4` for a range device), each for a 1.5 s settle after the retune (a device may drop and overflow for a second or two after a rate change, a B210's master-clock switch among them) and then a 1.5 s dwell, and reports the first rung with at most one overflow in the dwell and at least 98 % of the nominal rate delivered as `capabilities.max_bandwidth_hz: {measured: N}` (one overflow is allowed because a healthy B210 still overflows now and then at every rate; a rung rejected for overflows gets one more settle and dwell before the probe moves down). The probe runs for every sample depth the link carries (below) inside the worker's 150 s to say hello. It logs `zeta-soapy-worker[<id>]: rate cap <N> Hz measured (<k> rungs tried)`. If no rung is clean nothing is measured: the worker keeps the driver's asserted cap, logs `rate cap not measured: no rung clean (<k> rungs tried, lowest <hz> Hz); set max_rate_hz=<hz> to pin one`, and probes again at every respawn. A rung that loses the device ends the probe with `rate probe: device lost at <rate> Hz: ...` in the journal, and the worker keeps the asserted cap too. A request wider than a measured cap is refused `out_of_range` with `why: "insufficient bandwidth: <source> delivers at most <N> Hz (measured at open)"` (`why` is `null` for other refusals): the radio cannot do it, so narrow the request or take a second radio. That is a different thing from a digital link the node reports but does not yet decode, which is not a bandwidth problem. A measured cap is kept with the capabilities in `sources/<id>.json` and passed to every respawn (`--rate-cap-hz N`), so healing never re-probes; a respawn that measures a cap where the first open could not replaces the asserted one.

To state a ceiling yourself and skip the probe, put `max_rate_hz=N` among the `--source-soapy` args (zeta's own item, stripped before the driver sees it, like `gain=` and `ppm=`). That is the remedy for `no rung clean` and for a top rung that reliably kills the device (`rate probe: device lost at <rate>` at every open). An asserted cap is never cached: it is read from the args at every start, so changing or removing the item takes effect at the next one. To probe again instead (a new cable, a faster host, devices added around the radio), the operator runs `source_measure` (below); there is no state file to edit. An agent that meets `insufficient bandwidth` reports it to the operator with the source and the cap, and never deletes or edits the node's state files.

### Measuring a radio's link

A link that carries more than one sample depth (a B2xx over USB: `sc16`, `sc12` and the lossy `sc8`) is probed at each depth at open, so `source list` shows `capabilities.depths` (`bits`, `lossless`, `max_bandwidth_hz` for each, a `measured` claim once probed) and `depth`, the one in force, whose cap is the top-level `max_bandwidth_hz`. The source runs the narrowest lossless depth that measures as wide as the widest (a B210's `sc12` carries all its 12-bit converter gives, in fewer bytes than `sc16`, so it wins when it measured as wide; one that measured narrower, or was never measured clean, does not, so the source's bandwidth never shrinks under a resumed job) unless `bits=N` among its `--source-soapy` args names another; a lossy depth is chosen only that way, or for a `scan`'s run. The probe streams the radio flat out, so a start with no cached figures says so first, in the journal: `measuring what this radio's link can sustain (up to about <N> s; the host will be busy; max_rate_hz= skips it)`, then `measured in <N> s`. A node's first start shows only those two lines (it serves after its sources' first hello). A respawn that measures (a replug onto another link speed, `source_measure`) also shows `worker.starting` (`what`, `detail`, `step`, `of`, `eta_ms`) in `source list`, the page's notice on the source's tab and `measuring` and `measured` events on the source's feed; its line then opens the parentheses with `link speed changed (<old> to <new>)` or `as asked`. Tell a user whose system stalls for a minute right after a start that this is what it is. `max_rate_hz=N` skips the probe.

The figures belong to the link's speed: `worker.attachment` is `usb:<bus>-<path>@<speed>` (Mb/s, `null` where the source cannot tell) and `worker.link_measure` the latest hello's figures with `at_speed`. A source measures again by itself only when its negotiated speed differs from the one its figures were measured at (a USB 3 radio now on a USB 2 port, or the reverse); another port at the same speed keeps the cache. `source_measure` (the page's "Run link diagnostics" on the radio's tab) measures again on request, about a minute: use it when the system stutters after devices were added around the radio, and only when the operator asks. It is a `conflict` naming the holders while a job or a pin holds the radio (retry with `replace` only on the operator's word: stopping a job is theirs to decide), and `other` for a source with no worker. Its figures govern tunes at once through `depth` and are cached for the next start; `capabilities` is set once a run (the first hello of the run that differs from it replaces it, later ones leave it), so read `depth` and `worker.link_measure` for the figures in force.

`stats.tune_gaps` counts the overflows the reader's own blocked tune caused: they fall among the samples a tune discards, so `overflows` stays the figure for loss while streaming. Compare `overflows` at a rate measured clean; a climb there is the system, not the sweep.

### Sweeping a span

`scan` steps the source across a span wider than one capture and paints one spectrum row per step (`job start --kind scan`, see the `job_start` notes). The pace is the radio's: each step is the source's whole capture (`context.scan.rate_hz`), advancing by its usable part (`step_hz`; 0.9 of the capture on a SoapySDR device, `usable=F` among its args to change it), taking 20 ms of settled samples (`dwell_ms`) and tuning on; the FFT of one step runs while the next tune happens. Report how long a sweep takes from `context.scan.timing.sweep_ms`, not from step counts or a guess, and a calibrating tune from `timing.slow_tunes` (a B210's AD9361 calibrates about every fourth tune and a tune that does costs over ten times a plain one; the node reports it and does not remove it). A source settles for `settle_ms` after a tune (1 ms on a B2xx, `settle_ms=N` among the args to change it); the first row of a step should match its later ones.

A stepped scan is secondary: it never blocks anything. Start the decoder (or pin, retune, start a set) on the source as if the scan were not there; the request is granted, no job is stopped, and the scan stops tuning and waits, `running`, with `context.scan.waiting` saying who holds the source (`source <id> is held by <kind> <id>, ...`, `pin` for a pin) and `source list` listing it under `scans_waiting`. It takes the source back by itself, starting a new sweep, once no rigid job, no pin and no other scan holds it (it then stops the elastic jobs, as its start does). A scan started on a held radio waits the same way instead of failing. So never stop or `replace` a scan to decode, and report a waiting scan as waiting, naming its holder, not as stuck.

Choose the look by what the operator wants to find. The default (`dwell_ms` 20, `average` 1) is the fastest sweep and catches a burst. Many quick looks averaged (`average` 16 at 20 ms) lowers the noise ripple as one 320 ms dwell does and still revisits every step each sweep: it shows a weak steady carrier. A long look (`dwell_ms` 250) sees a faint steady signal in one dwell and sweeps slowly. A row carries `sweeps`, how many sweeps it averages so far, and `bits`. Change the look on a running scan with `graph put` on its `fft` node (`dwell_ms`, `average`, `bits`); the page's scan row has a select for it.

`bits` takes a lossy depth for the scan's run (8 on a B210), steps at that depth's wider capture and puts the source's depth back at the end. At 8 bits a weak signal beside a strong one in the same capture is lost in quantisation noise: it is for a coarse survey of occupancy, never for faint signals, and never the default. Such a scan (a lossy depth, or any depth other than the one in force) does not give way: every holder would get the coarser samples, so it is refused as a `conflict` naming the other holders unless it is the source's sole holder, a job started while it runs is a `conflict` naming it, and it is refused naming the depths for one the source does not carry.

A source that sweeps for itself sweeps for a `scan` without the stepping. Read `source_list`: a source whose `capabilities.sweep` is not `null` (a KiwiSDR's waterfall; `min_hz`, `max_hz`, `bin_hz_min`, `rows_per_s_max`, `calibrated`) and holds the span is swept by the source, `context.scan.method` `source`: the scan takes no lease and no IQ, leaves the source's capture and its holders alone, and shows under `source_list[].sweeps`, never `holders`. A demodulator on the same source keeps playing. `method` `stepped` forces the stepped scan; `source` never steps. `bin_hz` asks the source for a bin width, which picks its zoom and step count; the default is the coarser of 6 kHz and the source's `bin_hz_min`. `bits` beside `source` or `bin_hz` is refused (`bits applies to a stepped scan`). `replace` on a scan is honoured only if the scan has to step: a scan the source sweeps for itself stops nothing; if a refusal makes the scan step, the named jobs are stopped before it takes the radio; `source` with a non-empty `replace` is refused (`replace applies to a stepped scan`). Pass `replace` only when a `conflict` named those holders. A `source` scan's `context.scan` has `method`, `steps`, `step_hz`, `bin_hz`, `dwell_ms` (`dwell_ms_asked`), `average` (`average_asked`), `alternate`, `mask`, `calibrated`, `waiting` and `timing`, and no `rate_hz` and no `bits`; while it is `waiting` it holds only `method`, `mask`, `calibrated` and `waiting` (the plan's keys arrive when the source grants the sweep, `timing` after its first sweep). Its rows are `calibrated` (absolute dBm at the antenna), which a local radio's rows are not: never compare levels across the two. The first pixels of each of the source's views are masked. A span that fits one of the source's views is one step that holds still (`alternate` `null`): a Kiwi then sends a row every frame of its waterfall, about 23 a second. To look elsewhere on such a scan, `job_retune` it (`--center-hz`, `--bandwidth-hz`, `--bin-hz` for the zoom): the source re-aims its running sweep under the same job and stream, a Kiwi on its open waterfall socket, with no reconnect; a span outside `capabilities.sweep` is refused naming its range.

A refused sweep at a first start makes the scan step and `context.scan.fallback` says why; when the source's IQ channel is held the stepped scan waits for it, as any stepped scan does. A sweep refused while another scan already sweeps the source (a KiwiSDR has one waterfall connection; the page's scan of the Kiwi's tab holds it while the tab is open) does not step: the start fails naming that scan. Re-aim it with `job_retune` instead, or ask `method: stepped` for the source's IQ channel. A scan that ran as `source` and is restarted (a node restart, a `graph_put`, a look change) never steps: if the source refuses then, the scan stays up with `context.scan.waiting` set to the reason and asks again after 1, 2, 4, 8 and 16 s, then every 16 s; report `waiting` and the reason, never start a stepped scan to get round it. On a KiwiSDR the sweep takes one more user slot while it runs and none otherwise, paints the whole band about once a second at the default, and a second scan on the same KiwiSDR runs stepped or is a `conflict` (the node holds one waterfall connection). A `--source-node` source does not forward a far source's sweep: a scan on it steps. For a `scan`, a source whose `capabilities.sweep` holds the span can be used while a job holds it, whatever `source_free` says.

A HackRF at `usable=1.0` shows its edge spur at every capture's +-fs/2; the default 0.9 masks it. A row's `masked` ranges are no data, not low power.

Running a second node that owns the radio and attaching it with `--source-node` is federation (a radio on another host), not crash protection; one node with `--source-soapy hackrf=driver=hackrf,gain=32` is the form for a local HackRF.

### Watching analog video

Analog video (an FPV VTX, a reverse camera, a 1.3 GHz or 5.8 GHz link, an HDMI sender that is really analog) is wide FM carrying a composite signal. `video_decode` (family `tv`) is `channel`, then `video_fm_demod`, then `composite_decode`: it centres where it is started, so centre it on the measured carrier (`classify`, or the waterfall's box), never on a channel grid. The default band is 24 MHz (at least 6 MHz). On the field host's B210 a 24 MHz band lands on the 30.72 Msps rung (the cap plan 28.1 measured); a 20 MHz band keeps the 20.48 rung. A source that cannot carry the band refuses it `insufficient bandwidth`, naming its cap, and the page greys Decode › Video with those words: take a second radio or narrow the band.

The job's `event` stream carries `protocol: "video"` with `system`, `lock` (`locked` or `no lock`), `standard`, `line_hz`, `fields`, `snr_db` and `dropped` (input the decoder lost: blocks its own queue or input dropped, plus one per gap in the composite's time from a block lost upstream, in the `channel` stage or the demodulator; each costs a field, not the lock). `locked` with a sensible `snr_db` is a picture. `no lock` looks like a noise thumbnail and an `snr_db` roughly under 10 dB (a rule of thumb, not a threshold the node applies): the carrier may be off-centre, too weak, too narrow a band, or not analog at all. Brightness is referenced to the measured sync depth, so the `deviation_hz` setting does not dim the picture. The composite stream carries `role: composite` and is not audio: it is never a job's audio for `job_attach`, the mix or `--then-tail` (a `stream tail` on it still reads it).

To look, open the pane's tab (labelled `video`, shown only while a `video_decode` job runs on some radio) or click the live thumbnail in the job's tag on the waterfall (hidden whenever the rail collapses the tag to a thin segment, which happens when tags overlap and is common in the narrow footprint's short rail; a hidden thumbnail holds no socket). The full view fills the main area with the selected feed, a status line and a strip of every running feed across radios. `view set video smooth|sharp` picks the profile: `smooth` follows every field at 360 x 288 (every line: a field is already anamorphic and the page stretches it to 4:3), `sharp` is full width at a few frames a second; the tag's thumbnail is 120 x 96. To keep a still, run `zeta stream save --stream <id> --path still.png --node URL` (take the id from `stream list`; it writes the next frame as a `sharp` picture).

A digital video link never locks; see the verdict under "Where to look". The audio subcarrier is not decoded yet.

### Reading a DVB-T multiplex

A DVB-T multiplex is a flat-topped block 5 to 8 MHz wide, usually the strongest thing in a broadcast band. `dvbt_decode` (family `tv`) reads its signalling only: there is no picture, sound or service list yet. It needs the external `dvbt-rx` on the node's `PATH`; without it the row is `unavailable` (it is a small wrapper the operator builds around SDRangel's `modemdvb`, which `modes_show` points at). `identify` and `classify` offer the row only between 174 and 862 MHz; started by hand it runs anywhere.

Centre the job on the measured middle of the block (`classify`, or the waterfall's box), never on a channel raster, with a band that covers it (the default is 8 MHz). The capture must be at least that wide, so a narrow radio refuses it `insufficient bandwidth`. The channel width is not a parameter: the receiver tries 8, 7, 6 and 5 MHz in turn and reports the one that locks as `bandwidth_hz`.

The job's `event` stream carries `protocol: "dvbt"`: one event when lock is gained or lost, one every 2 s while locked and one every 5 s while searching. `locked: true` comes with `mode` (`2K` or `8K` carriers), `guard` (the guard interval, such as `1/16`), `constellation`, `code_rate`, `hierarchy` and `lp_code_rate` (`null` unless the multiplex is hierarchical) and `cell_id`. Many multiplexes send no cell id, and `cell_id` is then `null`: that is the broadcaster's choice, not a fault. Lock normally takes under a second on a clean signal, so `locked: false` after ten seconds means no DVB-T at any width: the block may be DVB-T2 (not looked for), another standard, or off-centre by more than the receiver follows.

`offset_hz` is how far the multiplex's carriers sit from the job's centre and `clock_ppm` the sample clock error; both are mostly the radio's own reference error, so `clock_ppm` agrees across the multiplexes one radio hears. Three fields say how good the reception is, and none of them is the level over the noise floor:

- `snr_db` is the mean error of the equalised pilot carriers, unweighted across the multiplex. Carriers in a fade count as much as the rest, so a strong multiplex with multipath reads low, and can read below 0 dB while still locked. It moves by several dB from event to event on a steady signal. Compare it between multiplexes only together with `ripple_db`.
- `ripple_db` is the spread of the channel's frequency response across the multiplex. A few dB is a flat channel; 15 dB or more is multipath, or two sites of a same-frequency network arriving together. A low `snr_db` beside a high `ripple_db` is the channel, not a weak signal.
- `resyncs` counts the timing jumps the receiver recovered from without losing lock, since it last acquired. Each is usually samples lost before the program (compare the source's `stats.overflows` and the job's `channel.dropped`); a count that climbs while `overflows` stands still points at the signal instead.

The job's context reads `channel.filter: none` when the band is most of the capture: the node then hands the program the capture as it is, neighbouring multiplexes included. That is expected. `dvbt-rx` low-passes its input to the channel width it is trying, sharply enough to remove a neighbour 40 dB stronger, so a weak multiplex beside a strong one still locks cleanly; a `dvbt-rx` older than that filter mis-times on such a neighbour and shows it as a very low `snr_db` with `resyncs` climbing. Report the signalled parameters as measured facts about the transmission; the register says who is licensed there.

`identify` on a multiplex proves this row by its lock, and its verdict then judges the register against what was decoded (`ofdm` at the locked width) and not against the first-layer measurement, which has no label for a multiplex and reads it far narrower than it is. "What is this?" on the page still uses the measurement, so it can say `disagrees ... measured unknown` on a licensed multiplex: run identify before reporting a disagreement there. Identify re-centres its trials on the measured centre, which on an uneven multiplex can be the middle of the stronger half, a megahertz or more from the multiplex's own; this row is marked `identify.as_asked`, so identify tries it on the band as it was asked. Draw or give the band over the whole block, then: about the channel width, roughly centred.

### Open decoded frames in Wireshark

A running APRS job (`aprs_decode`) or a frame row's job can write its frames to a pcapng file that Wireshark opens. Attach the capture to the decoder's job; it is its own job with its own id:

```json
{"op":"job_attach","kind":"packets","job":"<decoder job id>","language":null,"stream":null}
```

From the CLI, against a running `zeta serve` (`--node`): `zeta job attach --kind packets --job <decoder job id>`, then `zeta packets list` and `zeta packets delete --capture <id>`.

Read the capture's id from `packets_list` (or the new job's context: `capture`, `packets`, `bytes`). The file is served while it is still written, so download it at any time:

```bash
curl -O -H "Authorization: Bearer $ZETA_SECRET" http://<node>/captures/<id>.pcapng
```

APRS packets are written as `LINKTYPE_AX25_KISS` (202), so Wireshark dissects AX.25 and APRS with no setup. A frame row's frames are `LINKTYPE_USER0` (147): the bytes are visible, and Wireshark shows them as data until a user dissector is bound under Edit, Preferences, Protocols, DLT_USER (a `USER0` entry naming the dissector for that row's frames). Each packet carries the frame's own time, and its comment reads `job=<decoder job> handler=<its handler> source=<source> freq_hz=<centre>`.

The attach is refused for a stream (`stream` must be `null`), a job with no packet output, a restricted row, a row that cannot be read (after a modes reload), a job already captured and an attached input. Stop the capture with `job_stop` on the packets job; it also ends when its decoder stops, and it follows a retune into a fresh file. A capture rolls to a fresh id at 256 MiB. The packet store keeps 4 GiB of captures, its own budget apart from the IQ captures', dropping the closed captures written longest ago first, then any not written to for the burst store's `keep_days` (7 by default): a capture is aged by its last packet, so one that ran for days is kept from its end. A capture being written is never dropped. A node restart does not resume it: the job is `stopped` with the note `packet capture does not resume: attach again`, and the file is kept. `packets_delete` removes a file once it is no longer written. Phase B (a live feed into Wireshark) is not built: download the file and open it.

### Exploring an unknown signal

A signal nobody has named goes up a ladder; stop at the first rung that answers, and report what each rung found.

1. Direct. Layer 1 measures the band (`measure`, `classify`) and labels it; layer 2 scores the catalogue, the seed signatures and every mode row. `classify` tries the quick rows; `identify` runs each fitting row for its dwell, in score order, and publishes a `candidate` event as it reaches each row. A proof (a CRC-clean decode) ends the ladder and leaves the decoder running under `verdict.job`.
2. The register and the decoders it suggests. With the register attached, `knowledge_lookup`, `classify` and `identify` list the licensed assignments overlapping the band, nearest first, and a row whose width fits the licensed channel scores 0.2 higher, so the decoder that fits is tried before one that does not. The allocations ride along in the result whatever happens next. The `reach` of the answer (`km`, `class`, `antenna`, `note`) says how far a site can plausibly be heard on the station's antenna: skywave is not cut, tropo and UHF are; give it when the register is empty or the nearest site is out of reach.
3. Features and the register, as an `unknown`. With no proof the answer is `unknown`, never a guess: `verdict.mode` is `null` and the verdict carries the layer-1 features and `allocations`; the watch's `unknown` summary pairs the measurement with the register as `register says <EMISSION> (<bw> kHz <modulation> <info>) <licensee>, <site>, <d> km`. Report both together, for instance "unknown at 404.025 MHz: burst fsk, 16 kHz, 4800 Bd, 1 % duty every 1.0 s; the register says 16K0F1D (16 kHz FM data) Example Water Authority, Example Hill site, 17 km". Say which numbers were measured over the bursts (a low `duty`). A match between the measurement and the register's emission is a coincidence of features, not a decode: say "consistent with", never "is". When the measurement matches a signature the operator accepted (layer 2's `learned <name>`, a match score of 0.5 or more, features-only signatures included), the unknown verdict says so: `verdict.label` is `learned <name>` and `verdict.learned` gives its `id`, `name` and `confidence` (the label's: the signature's confidence times the score; `null` otherwise); the watch's summary reads `learned <name> at <MHz>: <measurement>` and it neither captures nor proposes that signal again, though it keeps retrying identify. Report it as "matches the learned signature <name>", still not a decode.
4. Captures. The explore policy of a watch, `on_unknown: capture` on its `detect` node (default `report`), writes an unknown signal's bursts to disk once per run (the count resets when the watch restarts) as a `capture` child, and publishes `capturing` and `captured`; `job_context.watch.signals[].captures` lists the ids. By hand, `job_start` a `capture` job on the signal's measured band, or use the box menu's "Capture bursts". `capture_list` shows the store newest first, `capture_show` one record, `capture_classify` classifies the band a capture recorded, so a signal that was gone before anyone looked can still be asked "what is this?", and `capture_delete` removes one (an agent run needs `allow.delete_captures`). The store keeps 256 MB and 7 days by default (`--bursts-keep-mb`, `--bursts-keep-days`); pinned captures are never expired. The page's Explore tab (`view set pane explore`) lists them with What is this, Download and Delete.
5. A signature. The node proposes one itself when a capture job ends with features only (confidence 0.3) or a bits or graph job reads five CRC-clean frames (0.9; a mode row's job, a frame row's included, proposes nothing: its frames prove the row): the `signature` event and `job_context.proposal` (the proposal's id; `signature_show` gives the rest) carry it. A hand `signature_propose` with a framing is 0.6. The operator accepts or rejects it (`signature_accept`, `signature_reject`), and takes a wrong accept back with `signature_retract` (the record kept, `retracted`; it labels nothing more, its `learned_` row and capture pins undone on the running node) or removes a record with `signature_delete`. A framed one becomes a `learned_` mode, named by the record's `decoder` field (read it with `signature_show`; never build it from the id), so the next encounter is proved by `identify` or decoded by `job_start --kind <decoder>`. A features-only one only labels later encounters `learned <name>`: a layer-2 match, not a decode. The ladder ends here.

When `classify` answers `too_old` the ring has moved on: the error carries the ring's earliest start in its detail; re-issue on the latest span it still holds, and say so. When it answers `gap` the span crosses a break in the capture (the source lost samples there): the detail's `gap_start_ns` and `gap_end_ns` are the last sample before the break and the first after it, so ask again on either side of it. For a "last N seconds" read, check `source_list`'s `ring.run_s` first: it is the length of the newest run with no gap, and N above it will cross one.

The playbook ends at classification and, when the operator accepts one, the signature written back so the next encounter is a layer 2 match or, for a framed signature with a CRC and a symbol rate, a decode. It stops before decoding the content of a third-party transmission: measuring, classifying, capturing a few bursts to identify the signal and saying who the register says is licensed is in scope; recovering and reading the messages of someone else's link is not, and interception law varies by country, so that is the operator's decision and legal responsibility. State this legal line once when a request goes that way, and do not repeat it. A known public protocol the node has a decoder row for (APRS, POCSAG, ADS-B, ACARS, AIS, radiosondes, M17, P25, DMR) is the ordinary use of the radio and is not held back by it. The P25 and DMR rows decode clear speech on public protocols; whose traffic it is, and whether listening to it is lawful where the node sits, is the operator's responsibility: say so once when a request goes that way. Bits and frame hypotheses are ops now (below), and so is the signature write-back (item 11 below).

### Working layer 4

When a signal has no known decoder and a capture of it exists, work its bits with the ops, in this order:

1. `capture_list` (narrow with `signal` when the band is known); take the capture's id from it, never invent one. No capture: start a `capture` job on the signal's measured band first.
2. `bits_start` with `capture`, `modulation`, `symbol_rate_baud` and `order`, each `null` to take it from the capture's feature record and its layer-1 label (`fsk` and `fm` give `fsk`; `psk` and `ook` themselves). It takes every capture of the capture's `set` in time order and builds `capture_in → resample → <demod> → clock_recover → slicer → bit_view`; a signal off the capture's centre whose measured band reaches past the resampler's passband (offset plus half the measured width over 0.45 times the chain rate: a wide capture) is shifted to its measured centre first by a `channel` stage, unless layer 1 labels it `noise` (`job_context.bits.shift_hz` says by how much); the channel's band is the measured width × 1.25, at least 4 × the baud, cut to what the capture holds about the measured centre (a weak signal's measured band reaches into the noise). fsk takes order 2 or 4, psk 2, 4 or 8, ook 2. It refuses with `other`: `no symbol rate measured; give symbol_rate_baud`, `no modulation measured (label <x>); give modulation`, `symbol_rate_baud <r> needs <4r> Hz; the capture holds <rate> Hz`, `symbol_rate_baud: at least 1` for a rate of 0, a measured centre the capture holds under 4 × the baud about (`the measured centre <c> Hz leaves <room> Hz of the capture <lo>..=<hi> Hz about it, under the <floor> Hz the chain needs (4 x <baud> Bd)`), and a set of mixed rates or centres (`capture <id>: <rate> Hz differs from <first>'s <rate> Hz`). Short FSK bursts, real or synthesised, often have no measured rate: give it. On a refusal, report it and the features; do not guess a rate.
3. The chain's rate: about 8 samples per symbol for fsk and ook; for psk the smallest multiple of 4 times the baud that also covers a carrier offset of 2000 Hz (`psk_demod`'s coarse estimate is unambiguous only within the rate over twice the order). A 4-FSK or OOK chain takes `clock_recover` `algorithm: early_late` (the default Mueller and Müller mistimes 4 levels and reads no timing across an OOK pulse's flat top); `bits_start` sets it, a chain built by hand must too, or it mistimes.
4. The replay loops (`loop: true`, `realtime: true`, a 500 ms pause between passes) and the job runs until stopped. A one-pass chain (`loop: false`) drains to its end, its last chunk delivered, and ends `stopped`. An unpaced loop (`loop: true`, `realtime: false`) needs `loop_pause_ms` of at least 100.
5. Read, with `job_context`: `bit_view` (the hypotheses over the whole set: line code, frame period, sync-word candidates, CRC candidates, each with its counts; its window spans the set's captures, each a segment no word or frame crosses, the counts summed over them, and a looping replay's next pass starts it afresh, so a pass is never counted twice), `clock` (`rate_est_baud`, `locked`: a clock that is not locked, or an estimate far from the rate, means the rate or the modulation is wrong) and `slicer` (`symbols`, `events`, `stream`). Never tail the whole bits stream: `stream_tail` of `job_context.slicer.stream` with `max_frames` at most 4. A CRC candidate with `period_bits` 0 means the frames run from each sync to the next.
6. Change a running chain with `graph_get`, edit, `graph_put`: a `slicer` with `differential: true` or another `mapping`, or a `correlate` node (`{pattern, bits, max_errors}`) between the slicer and `bit_view`. `correlate` forwards every event and adds `sync` hits, so the hypotheses keep coming. A node's output feeds one edge: there is no fan-out. When a hypothesis checks (a sync word, a length rule, a CRC), `graph_put` a `frame_decode` node (`{sync, length, crc, encoding}`) after the slicer and read `job_context.frame_decode` (its counters) and the `frame` events' `crc_ok`. Use `length: {to_next_sync: true}` for a CRC candidate with `period_bits` 0.
7. PSK's phase ambiguity is not resolved: a BPSK stream may come out inverted and a QPSK stream rotated. `slicer` `differential: true` is the answer; try it before calling a PSK stream noise.
8. Report the hypotheses with their counts (`sync` hits, matching frames out of tried, CRC passes), and say which are guesses. When nothing checks, stop at "unknown" with the measured features: do not claim a protocol, a framing or a payload from a hypothesis without a CRC-clean check.
9. A chain of your own: `graph_start` runs a graph that has no radio (a `capture_in`, `stream_in` or `mix` at its root) on the node source (`zeta graph start --file`). `graph` and `bits` are reserved kind names, so `job_start` refuses them (an operator mode row with either id cannot be started).
10. You may stop your own `bits_start` and `graph_start` jobs when done (`job_stop`); never one you did not start. `jobs_stop` with a plan filter skips them (their centre is the capture's, not a channel they hold).
11. The node proposes a signature itself: a capture job's end with features only (confidence 0.3), a bits or graph job on five CRC-clean frames (0.9). A mode row's job (a frame row's, a `learned_` row's) proposes nothing: its CRC-clean frames prove the row, and its session says `proved`. It publishes a `signature` event and sets `job_context.proposal` (the proposal's id; a capture job's is `job_context.capture.proposal`). A hand `signature_propose` with a framing is 0.6. `signature_list {state: "proposed"}` lists the proposals; `signature_show` gives one's evidence. Report a proposal to the operator with its confidence and evidence. `signature_accept` and `signature_reject` are the operator's (`allow.accept_signatures`): never call them unasked. `signature_propose` is for when the operator names a framing by hand. An accepted framed signature (a CRC and a symbol rate) becomes a `learned_` mode like any other, named by the record's `decoder` field (take it from `signature_show`; never build it from the id): the next encounter is proved by `identify` or decoded by `job_start --kind <decoder>`. A features-only one labels later encounters `learned <name>` (an identify verdict with `learned`, the watch's summary). That is a layer-2 match, not a decode: say so.

### The rule

When nothing matches, say "unknown" and report the measured features (centre, bandwidth, modulation, symbol rate, burst timing). Do not guess.
